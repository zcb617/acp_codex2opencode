# 可交付开发设计文档编写指南（团队版）

> 目的：统一团队文档写法，确保 A/B/C 开发者在同一规范下工作，避免实现偏差导致系统不可运行或鲁棒性下降。  
> 适用范围：服务端、客户端、工具链、数据流水线等所有研发文档。  
> 文档语言：中文（强制）。
> 输出形式：必须保存为 Markdown 文档文件，默认路径为 `docs/superpowers/specs/<YYYY-MM-DD>-<session_alias>-design.md`；禁止只在对话中输出一段方案文字。

---

## 1. 文档定位（先定性）
本指南要求输出的不是“想法文档”，而是“可执行规范文档”。

一份合格文档必须同时满足：
1. 开发可执行：开发者可按文档直接编码，不依赖口头补充。
2. 测试可验证：测试可据此编写用例并判断通过/失败。
3. 运维可操作：发布、回滚、异常处理有明确步骤。
4. 评审可追责：每条规则有明确触发条件与处理动作。

---

## 2. 编写原则（强约束）
1. 无歧义：禁止“尽量/适当/视情况”等模糊描述。
2. 可验证：每个关键要求都要有量化验收标准。
3. 可回滚：每个关键流程都要定义失败回退路径。
4. 可观测：关键步骤必须定义日志、指标、告警。
5. 可演进：技术选型要有升级路线与触发条件。

---

## 3. 文档标准结构（缺一不可）
以下章节建议作为模板固定下来：

1. 背景与目标
2. 非目标（明确不做什么）
3. 范围与术语
4. 架构与模块职责
5. 技术选型与约束
6. API 契约（请求/响应示例）
7. 数据模型（含字段中文作用）
8. 主流程与状态机
9. 异常处理策略矩阵
10. 幂等与去重规则
11. 测试策略（unit/integration/e2e/并发）
12. 验收标准（量化）
13. 发布与回滚 Runbook
14. SLO 与告警
15. 数据保留与清理策略
16. 环境配置矩阵（dev/staging/prod）
17. 开发实施规范（目录、分层、函数拆分）

---

## 4. 必写模板（可直接复用）

### 4.1 API 契约模板
每个接口至少包含：
1. 路径 + 方法 + 用途
2. 请求体示例（JSON）
3. 成功响应示例（JSON）
4. 失败响应示例（JSON）
5. 错误码说明（可重试/不可重试）

示例结构：
```text
POST /v1/xxx
- 输入字段：
- 成功响应：
- 失败响应：
- 幂等键：
- 限流规则：
```

### 4.2 数据表字段字典模板（强制含中文作用）
每张表必须使用如下表格格式：

| 字段名 | 类型 | 必填 | 约束/默认 | 字段作用（中文） |
|---|---|---|---|---|
| example_id | BIGSERIAL | 是 | PRIMARY KEY | 该字段在业务中的用途说明。 |

并在表后增加：
- 本表核心职责：一句话说明这张表在全链路中的定位。

### 4.3 异常处理策略矩阵模板
必须统一记录“触发条件 -> 动作 -> 结果 -> 记录位置”：

| 异常层级 | 典型场景 | 处理动作 | 是否丢弃记录 | 是否重试 | 记录位置 | 对主流程影响 |
|---|---|---|---|---|---|---|
| 记录级 | 字段非法 | 丢弃该条并记录 | 是 | 否 | reject_log | 批次继续 |
| 系统级 | DB不可用 | 整批失败并重试 | 否 | 是 | 系统日志 | 暂时降级 |

### 4.4 测试与验收模板
必须覆盖四层：
1. 单元测试：规则正确性
2. 集成测试：模块协同
3. 端到端测试：业务链路闭环
4. 并发/稳定性测试：高压与故障恢复

验收必须量化，例如：
- 上传成功率 >= 99.9%
- P95 响应 <= 300ms
- 发布校验失败时不切换 active 版本

### 4.4.1 交付测试对齐设计方案（强制）
交付测试不是独立清单，也不是为了“跑过测试”而补的仪式。交付测试必须证明设计方案里的承诺已经在真实业务链路中成立。

设计文档必须给出“设计承诺 -> 交付用例”的映射，至少包含：

| 设计承诺 | 来源章节 | 项目类型 | 真实入口 | 用例卡 | 证据要求 |
|---|---|---|---|---|---|
| 用户保存设置后重启仍生效 | 配置项 / 状态机 / 验收标准 | 桌面端 | 设置页保存按钮 | DT-01 | 保存前快照、保存后快照、键级 diff、重启后结果 |

项目类型只决定真实入口和证据采集方式，不能替代设计承诺：

- 服务器端程序：按设计中的 API 契约、鉴权规则、数据模型、配置项、后台任务、队列或定时任务逐项验证。
- 桌面端程序：按设计中的窗口、菜单、按钮、托盘、快捷键、本地配置、安装升级和启动规则逐项验证。
- APP 端程序：按设计中的页面流、权限弹窗、账号状态、本地存储、前后台切换、离线和网络变化规则逐项验证。
- 网页端程序：按设计中的页面路径、表单契约、前后端接口、权限控制、刷新登录状态和部署入口逐项验证。

发布、打包、容器交付是交付测试前置门禁：

- 客户端程序：必须按照项目中约定的打包流程完整执行，打包命令、产物生成、安装或启动验证必须全部通过。打包流程未跑通，交付测试结论必须是“不通过”。
- 服务器端程序：如果项目通过 Docker 容器交付，必须按照项目中约定完成镜像制作（`docker build`）和镜像运行（`docker run`）。必须基于新构建的新容器完整执行交付测试；镜像不能构建、容器不能运行、或新容器内业务链路不能跑通，交付测试结论必须是“不通过”。
- Web 程序：必须按照项目中约定完整执行发布流程，发布命令、发布产物、部署入口或发布环境验证必须全部通过。发布流程未跑通，交付测试结论必须是“不通过”。
- 未找到项目约定的打包、容器或发布流程时，必须停止判定通过，并要求用户提供流程；或者由用户明确确认本次交付测试不包含对应发布、打包或部署流程。没有用户提供流程或明确豁免，禁止声明交付测试通过。

每个交付用例必须有用例卡：前置条件、操作步骤、预期结果、持久化或配置变化期望。涉及保存、配置、状态、数据库、本地文件、缓存或用户设置的用例，必须先备份原状态，测试后恢复，避免污染现网或个人配置。

每个用例都必须产出证据：执行前状态快照、执行后状态快照、键级或字段级 diff、实际结论。交付测试必须跑真实链路，不使用 monkeypatch、不 mock 保存逻辑，不能直接改内部状态代替真实入口。除单元测试外，还必须覆盖 UI/CLI/API/任务入口等真实触发级测试，并核对最终落盘或落库结果。

通过门槛是全量矩阵：任何 1 项失败，整体结论就是“不通过”。最终结论只能是“逐项通过（附证据）”或“逐项失败（附原因与修复项）”。

#### 4.4.1.1 交付测试细化规则（按业务功能分类，强制）

交付测试必须先按业务功能分类再编排用例，不允许只给“一组总测试”。分类方式可以是增/删/改/查，也可以是更贴近业务的功能分组，但必须覆盖本次设计范围内的全部功能。

每个功能分类下必须至少定义 1 条主流程用例和 1 条异常流程用例，并明确该分类要验证的业务流程边界。

#### 4.4.1.2 交付用例卡（强制字段）

每个交付测试用例都必须完整写清：

- 测试场景（对应哪个功能分类、哪个业务目标）。
- 前置数据（账号、权限、配置、初始状态、依赖数据）。
- 操作步骤（真实入口、真实操作顺序）。
- 预期业务结果（用户可感知结果与系统业务结果）。
- 异常分支（触发条件、异常流转、回退或接手路径）。

异常分支必须强制覆盖“写方案前已确认的代码异常控制点”。如果某个已确认异常控制点未被任何用例覆盖，交付测试设计判定为不合格。

#### 4.4.1.3 每个用例的通过/不通过判定（强制）

每个用例必须单独给出明确的通过/不通过判定条件，至少包含：

- 接口返回码/错误码。
- 关键状态迁移（包括进入失败态、恢复态、终态）。
- 数据库落库结果（新增/更新/删除/无变更的期望）。
- 幂等与重复提交结果（重复请求是否被正确去重或拒绝）。
- 日志证据（关键日志、错误日志、链路日志可追溯）。

禁止使用“结果正常”“基本符合预期”这类模糊描述。未给出上述判定条件的用例，不能作为交付测试通过依据。

### 4.5 按钮交互契约模板（客户端强制）
每个可点击控件（按钮、开关、下拉触发项）必须按下表描述：

| 控件 | 触发事件 | 实现目标 | 前置条件 | 数据来源 | 数据处理步骤 | UI 反馈 | 异常显示 | 日志/指标 |
|---|---|---|---|---|---|---|---|---|
| 检查更新 | clicked | 判定是否有新版本 | 无并发更新任务 | 本地meta + 远端meta | 比对版本 -> 更新状态 | 按钮禁用/恢复 | 网络失败提示 | request_id / latency |

规则：缺任一列视为“不可执行文档”。

### 4.6 非按钮字段模板（客户端强制）
每个展示字段（标签值、徽标、进度文本）必须按下表描述：

| 字段 | 数据来源 | 刷新时机 | 格式化规则 | 空值显示 | 异常显示 | 联动关系 |
|---|---|---|---|---|---|---|
| 当前版本 | 本地meta.rules_version | 页面打开/导入成功 | 原样 | 未初始化 | 读取失败 | 影响状态徽标 |

规则：字段若无来源或刷新时机定义，视为“实现歧义”。

## 5. 规范写作要求（必须/禁止）

### 5.1 必须
1. 每条规则写清触发条件与处理动作。
2. 每个字段写明中文作用，不能只列类型。
3. 每个错误码写明是否可重试。
4. 每个任务写明输入、输出、幂等键。
5. 每个发布步骤写明失败后的回滚步骤。

### 5.2 禁止
1. 禁止用“后续再补”“待定”替代关键规则。
2. 禁止缺失异常处理策略。
3. 禁止只写“有测试”，不写测试覆盖范围。
4. 禁止跨层职责描述（例如路由层做业务决策）。

---

## 6. 开发实施规范（落地执行）
文档中必须包含以下开发规则：
1. 目录归属规则：哪些代码放哪一层。
2. 分层调用规则：允许调用链与禁止越层。
3. 函数拆分规则：何时必须抽函数、何时必须拆分。
4. 异常落地规则：记录级/批次级/系统级/发布级。
5. 测试门禁规则：新增逻辑至少 unit+integration，关键链路必须 e2e。

---

## 7. 评审清单（Review Checklist）
提交文档评审前，作者必须逐项自检：
1. 结构是否完整（第 3 章全部覆盖）。
2. API 是否有成功/失败示例。
3. 数据库每个字段是否有中文作用说明。
4. 是否有统一异常矩阵，且口径与错误码一致。
5. 是否定义幂等键与重复数据处理规则。
6. 测试策略是否覆盖成功路径和异常路径。
7. 验收标准是否可量化、可执行。
8. 发布/回滚步骤是否可由非作者独立执行。
9. 客户端页面布局是否可唯一还原（位置、顺序、尺寸、间距、显隐规则）。
10. 每个按钮/开关是否定义了触发事件、前置条件、失败分支与用户提示。
11. 每个非按钮字段是否定义了数据来源、刷新时机、空值与异常显示。
12. UI 状态机与任务状态机是否无冲突（按钮可用性与状态迁移一致）。
13. 是否明确主题复用、国际化口径与跨平台差异处理方式。

## 8. 客户端程序设计专项指南（强制）
> 本章用于约束客户端文档写法，目标是“不同开发者按同一文档实现出同一界面与同一交互行为”。

### 8.1 客户端专项原则
1. 布局可还原：必须给出页面位置、区块顺序、关键尺寸、间距、对齐和显隐策略。  
2. 交互可追踪：每个控件必须能追踪到触发事件、数据来源、处理步骤与异常反馈。  
3. 状态可验证：UI 状态与后台任务状态必须双轨定义并互相映射。  
4. 异常可落地：每个错误码必须映射用户可见文案、按钮状态、是否可重试。  
5. 体验一致：主题、文案、国际化、禁用/隐藏边界必须统一。

### 8.2 客户端文档必备章节（在通用结构外新增）
客户端文档除第 3 章标准结构外，必须额外包含：
1. 页面地图与入口（位于哪个页面/导航/弹窗）。  
2. 布局规范（区块顺序、尺寸、间距、按钮顺序）。  
3. 控件交互契约（按钮/开关/下拉触发）。  
4. 非按钮字段规范（数据来源、刷新时机、异常显示）。  
5. UI 状态机 + 任务状态机 + 迁移对照表。  
6. 异常展示矩阵（错误码 -> 提示文案 -> 交互动作）。  
7. UI 回归验收标准（分辨率、主题、语言、缩放）。
8. UI 视觉规范（整体风格、按钮风格、色彩体系、主题色、DPI 兼容）。

### 8.2.1 客户端 UI 视觉规范（APP/Web/桌面强制）

只要交付物包含 APP、Web 或桌面客户端，方案文档必须写 UI 部分，不能只写业务逻辑和交互流程。

必须明确：

- 整体风格：信息密度、视觉层级、页面节奏、是否偏工具型/内容型/消费型。
- 按钮风格：主按钮、次按钮、危险按钮、禁用态、加载态、图标按钮、悬停/按下/聚焦状态。
- 色彩体系：主色、辅助色、背景色、边框色、文本色、成功/警告/错误/信息色，以及暗色模式下的对应色。
- 主题色：是否跟随系统主题色；如果不跟随，必须说明原因和固定主题策略。
- DPI 与缩放兼容：Windows DPI、macOS Retina、浏览器缩放、移动端高分屏下的布局、图标和文字清晰度。
- 字体与间距：字号层级、行高、间距、控件高度、圆角、边框和阴影规则。
- 响应式与窗口尺寸：桌面最小窗口、Web 断点、APP 横竖屏或不同设备尺寸。
- UI 交付证据：截图、录屏、不同主题/缩放/分辨率下的对比，以及与设计承诺的逐项映射。

客户端交付测试必须验证 UI 视觉规范是否成立。只验证按钮可点击或接口成功，不足以证明客户端设计可交付。

### 8.3 布局防歧义规范（必须量化）
1. 必须写“页面位置”：例如“基础设置页第二张卡片”。  
2. 必须写“顺序不可变项”：区块顺序、字段顺序、按钮顺序。  
3. 必须写关键尺寸：窗口尺寸、侧栏宽度、右侧值区宽度、按钮尺寸。  
4. 必须写关键间距：卡片间距、区块间距、按钮间距。  
5. 必须写可见性策略：何时禁用可见、何时隐藏，禁止模糊描述。  
6. 禁止“按实现自由调整布局”。

### 8.4 控件交互契约规范（按钮/开关）
每个可交互控件至少定义：
1. 触发事件（clicked/stateChanged/currentIndexChanged）。  
2. 实现目标（一句话，禁止模糊）。  
3. 前置条件（并发锁、权限、配置状态）。  
4. 数据来源（本地表、配置项、远端 API）。  
5. 数据处理步骤（校验、转换、事务、回滚）。  
6. UI 反馈（loading、禁用、进度、完成提示）。  
7. 异常分支（可重试/不可重试 + 文案）。  
8. 日志与指标埋点（request_id、耗时、失败码）。

### 8.5 非按钮字段规范（展示项）
每个展示字段必须定义：
1. 数据来源（精确到表/字段或接口字段）。  
2. 刷新时机（页面打开、任务完成、定时刷新、手动触发）。  
3. 格式化规则（时间、计数、百分比、本地化）。  
4. 空值显示（例如 `--`、`未初始化`）。  
5. 异常显示（读取失败、解析失败的统一口径）。  
6. 联动关系（字段变化是否触发徽标/按钮状态变化）。

### 8.6 客户端状态机双轨规范
1. UI 状态机：Idle/Loading/Success/Failed 等用户可见状态。  
2. 任务状态机：Queued/Sending/RetryWait 等后台执行状态。  
3. 必须给出事件迁移对照表：`事件 -> 前置状态 -> 目标状态 -> UI动作`。  
4. 按钮可用性必须从状态机推导，禁止硬编码分散在文档多处且口径不一致。

### 8.7 客户端异常展示矩阵（用户可见）
必须至少覆盖：
1. 网络类（429/500/503）  
2. 校验类（400/invalid_*）  
3. 数据类（哈希失败、导入失败）  
4. 配置类（保存失败、权限不足）  

每行必须写：`错误码/场景 -> 用户文案 -> 是否重试 -> 按钮状态 -> 日志位置`。

### 8.8 客户端可测试性要求
1. Unit：控件状态逻辑、错误码路由、格式化函数。  
2. Integration：页面与服务层联动、任务串行与并发互斥。  
3. E2E：完整用户操作路径（点击->状态变化->结果）。  
4. UI 回归：浅色/深色、中文/英文、标准缩放（100%/125%）不破版。  
5. 验收必须量化：成功率、P95、失败回滚率、UI 错位率（目标 0）。

### 8.9 客户端专项评审门禁（通过才可开发）
1. 文档是否可由不知情开发者独立还原同一布局。  
2. 是否每个控件都能追踪到完整数据链路与异常链路。  
3. 是否每个展示字段都定义了空值与异常显示。  
4. 是否状态迁移、按钮可用性、异常矩阵三者一致。  
5. 是否提供 UI 回归清单与截图点位要求。

## 9. 文档完成定义（Definition of Done）
文档达到以下条件才可进入开发阶段：
1. 无 `TBD/TODO` 占位项（关键链路）。
2. 章节齐全且规则可执行。
3. 测试与验收标准可直接落地执行。
4. 发布与回滚流程可由非作者独立完成。
5. 评审通过并冻结版本号。

## 11. 信息获取与需求澄清作战手册（必须执行）
> 目标：解决“模板会写但信息不全”的问题，确保文档内容来自可验证事实，而非个人猜测。

### 11.1 信息源优先级（冲突时按此裁决）
1. 业务负责人/产品 owner 的明确决策
2. 现网数据、日志、监控事实
3. 代码与数据库中的真实行为
4. 已发布的正式文档
5. 个人经验与历史项目类比

规则：低优先级信息与高优先级冲突时，必须以高优先级为准并记录变更原因。

### 11.2 立项必收集信息清单（未齐全不得进入开发）
1. 业务目标与成功指标（如成功率、时延、发布频率）
2. 非目标（明确不做范围）
3. 关键约束（时间、人员、合规、成本、基础设施）
4. 上下游系统与接口边界
5. 数据隐私边界（允许上传字段、禁止字段）
6. 容错策略（哪些错误可丢弃，哪些必须重试）
7. 发布与回滚责任人

### 11.3 需求澄清必问问题（访谈模板）
1. 这件事“完成”的判定标准是什么？
2. 哪类错误可以容忍丢弃？容忍上限是多少？
3. 哪类错误绝对不能丢（例如系统级写入失败）？
4. 是要求“全量准确”还是“统计上稳定”？
5. 版本发布失败后，回滚触发条件是什么？
6. 谁拥有最终决策权（技术/业务）？

### 11.4 信息缺口登记（必须留痕）
每个缺口都必须登记以下字段：
- `问题描述`
- `影响范围`
- `责任人`
- `截止时间`
- `临时假设`
- `风险等级`（高/中/低）

规则：高风险缺口未关闭，不得冻结文档版本。

### 11.5 假设管理规则（允许假设，但必须可回收）
1. 任何假设必须显式标记为“假设项”。
2. 每个假设必须写明：
   - 假设内容
   - 生效范围
   - 失效条件
   - 验证时间点
3. 假设被证伪后必须更新文档并触发变更评审。

### 11.6 ADR 决策记录（Architecture Decision Record）
对关键技术决策必须记录：
1. 决策背景
2. 候选方案
3. 选型理由与权衡
4. 风险与代价
5. 回滚策略
6. 生效日期与责任人

建议每个 ADR 单独成文，文档中仅保留索引链接。

### 11.7 需求冻结与变更控制
1. 文档版本节奏建议：
   - `v0.3`：草案（收集信息）
   - `v0.8`：评审版（闭合关键缺口）
   - `v1.0`：冻结版（允许开发）
2. `v1.0` 后任何关键变更必须走变更单：
   - 变更内容
   - 影响评估（代码/测试/发布）
   - 风险与回滚
   - 审批人

### 11.8 需求到验收映射（防止“说了但测不了”）
每条核心需求必须映射到：
1. 设计条目（文档章节）
2. 实现位置（模块/函数/表）
3. 测试用例（unit/integration/e2e）
4. 验收标准（量化）

若无法映射，说明需求描述不可执行，必须重写。

### 11.9 客户端设计前必采集信息（新增）
1. 现有窗口尺寸、导航结构、页面容器约束。  
2. 主题样式来源（light/dark）与可复用组件边界。  
3. 国际化策略（中英文文案、截断规则、换行规则）。  
4. 运行平台差异（Windows 版本、DPI 缩放、权限模型）。  
5. 性能预算（页面打开时延、按钮响应时延、后台任务占用上限）。  
6. 异常提示策略（toast/状态行/对话框）与统一文案规范。

### 11.10 客户端需求澄清必问问题（新增）
1. 页面入口是独立页面还是现有页面内卡片？  
2. 哪些布局元素“必须固定”，哪些允许自适应？  
3. 哪些控件失败后允许重试，哪些必须终止并提示升级？  
4. 非按钮字段的空值和异常各显示什么文案？  
5. 操作中的按钮是“禁用可见”还是“隐藏”？  
6. 需要覆盖哪些分辨率、缩放比例、主题和语言组合？

# 产品设计 — 场景深度文件

> 为 /ian-think 产品设计场景提供真正的长访谈骨架。
> 不是 6 个大筐，而是 trunk 模块 + 分支模块 + 子分流模块组成的问题树。
> 深度预算：
> - 知识产品：35-60 问
> - 应用产品 / 软件产品：50-80 问
> - 应用产品 / Agentic产品：60-100 问

---

## 操作原则（不可谈判）

**统一产品思维 > 顶层越分越细。** knowledge、software、workflow、skill、agent 都是产品，只是分支不同。  
**前半段通用，后半段分流。** 共同层不锁，后面所有细节都在飘。  
**先锁分支，再谈细节。**  
**最小可售 / 可用结果 > 完整愿景。**  
**Non-goals 是闸门。**  
**验证方式决定产品形态。**

---

## 回应姿态

- 先锁 `知识产品 / 应用产品`
- 若是应用产品，再锁 `软件产品 / Agentic产品`
- 每个模块问到底，再进下一模块
- 不允许用功能清单代替问题定义
- 不允许用"先做完再看"代替验证计划

## 通用 trunk 模块

### Module T1：分支锁定

**映射章节：** Product Branch  
**默认主问题：** 这是知识产品，还是应用产品？

**必追子问题：**
- 它的主要价值是交付内容，还是提供可用系统/链路？
- 用户买的是知识、模板、陪伴，还是一个能跑的东西？
- 如果是应用产品，它更像软件，还是更像 agentic workflow？
- 哪个判断最容易混淆你？
- 一句话分支声明怎么写？

**退出信号：** 公开分支锁定，必要时隐藏子分流也锁定。  
**红旗：** "它什么都沾一点"、"这不是产品，是 skill / workflow / agent"。

### Module T2：问题陈述

**映射章节：** Problem Statement  
**默认主问题：** 这个产品到底在解决什么问题？

**必追子问题：**
- 不是方案，问题本身是什么？
- 如果不做这个产品，用户会发生什么？
- 这是高频问题还是重度问题？
- 问题的边界在哪？
- 问题有没有被你说得过宽？

**退出信号：** 能用一句非方案化语言描述问题。  
**红旗：** "做一个平台/系统/工具"。

### Module T3：用户与使用情境

**映射章节：** Target User & Use Context  
**默认主问题：** 谁在什么场景下遇到这个问题？

**必追子问题：**
- 主要用户是谁？
- 次级用户是谁？
- 买的人和用的人是不是同一个？
- 触发使用的时刻是什么？
- 正常路径走一遍是什么样？
- 异常路径会怎么发生？

**退出信号：** 出现具体用户画像 + 关键场景。  
**红旗：** "所有人都能用"。

### Module T4：现状替代方案

**映射章节：** Current Solution  
**默认主问题：** 用户现在怎么解决？

**必追子问题：**
- 今天不用你，他会用什么？
- 他为什么还愿意忍现状？
- 切换成本是什么？
- 你打败的是产品、人工流程，还是时间成本？
- 现状真正讨厌的点是什么？

**退出信号：** 现状方案和切换成本说清。  
**红旗：** "现在没有任何方案"。

### Module T5：约束与明确不做

**映射章节：** Constraints + Non-goals  
**默认主问题：** 这次的硬约束是什么？明确不做什么？

**必追子问题：**
- 时间约束是什么？
- 资源约束是什么？
- 技术或交付约束是什么？
- 哪些东西这次绝对不做？
- 为什么不做？是因为不重要，还是因为现在做不了？

**退出信号：** 至少有一组清晰约束和 non-goals。  
**红旗：** "都先做出来"、"后面再收缩"。

### Module T6：成功标准

**映射章节：** Success Criteria  
**默认主问题：** 什么算做成？

**必追子问题：**
- 成功看什么指标？
- 使用成功和商业成功是不是同一回事？
- 用户完成什么动作说明产品起作用了？
- 哪些数字是 vanity metrics，哪些不是？
- 如果一周后看数据，你最先看哪 3 个？

**退出信号：** 形成 3-5 个关键成功标准。  
**红旗：** "上线就是成功"。

### Module T7：验证策略

**映射章节：** Validation Plan  
**默认主问题：** 你怎么验证这东西是对的？

**必追子问题：**
- 先验证兴趣、使用，还是成交？
- 最小验证动作是什么？
- 成本最低的错误验证方式是什么？
- 什么结果会让你继续？
- 什么结果会让你停？

**退出信号：** 验证路径成立。  
**红旗：** "先做完再看"。

## 知识产品分支模块

### Module K1：结果承诺（Promise）

**映射章节：** Proposed Solution  
**默认主问题：** 用户买知识产品，买到的最小结果是什么？

**必追子问题：**
- 不是内容列表，而是结果本身是什么？
- 结果能不能一句话说清？
- 结果多快能感知？
- 如果用户学完没做到这个结果，问题出在哪？

**退出信号：** 知识产品的结果承诺被压缩成一句可成交的话。  
**红旗：** "学完会收获很多启发"、"内容很多所以应该值"。

### Module K2：包装形式（Packaging）

**映射章节：** Proposed Solution  
**默认主问题：** 它是课程、文档、模板包、训练营，还是混合？

**必追子问题：**
- 为什么是这种包装，而不是别的？
- 单次消费还是分阶段消费？
- 用户最容易在哪一环掉队？
- 这个包装会不会让交付变重？

**退出信号：** 包装形式与用户消费方式匹配，且理由清楚。  
**红旗：** "先做成系统课再说"、"什么都装进去比较完整"。

### Module K3：交付设计（Delivery Design）

**映射章节：** Core Flow / Delivery Design  
**默认主问题：** 用户从购买到获得结果，要走几步？

**必追子问题：**
- 第一步看到什么？
- 中间哪里最容易断？
- 你需要多少人工介入？
- 交付压力在哪里？
- 有没有必须同步支持的环节？

**退出信号：** 从购买到结果的交付路径能一步一步讲清。  
**红旗：** "卖完以后再想怎么交付"、"用户会自己看完"。

### Module K4：内容边界（Scope）

**映射章节：** MVP Scope  
**默认主问题：** 第一轮知识产品具体包含什么，不包含什么？

**必追子问题：**
- 最小内容单元是什么？
- 哪部分是第一轮必须有？
- 哪部分以后再加？
- 不加哪些内容也不影响 promise 成立？

**退出信号：** 第一轮包含/不包含的内容边界明确。  
**红旗：** "都先做出来"、"先把完整内容备齐"。

### Module K5：成交前置条件（Launch Readiness）

**映射章节：** Success Criteria + Validation Plan  
**默认主问题：** 在开卖前，你至少要准备好什么？

**必追子问题：**
- 核心页面/文档/样例是否准备好？
- 有没有最低信任证明？
- 价格和 offer 是否收口？
- 第一轮交付有没有预案？

**退出信号：** 开卖前的最低准备条件被列清。  
**红旗：** "先挂个价格页试试"、"边卖边补全部材料"。

## 应用产品共用模块

### Module A1：核心任务（Core Job）

**映射章节：** Proposed Solution  
**默认主问题：** 用户打开这个产品，第一件要完成的核心任务是什么？

**必追子问题：**
- 这个任务之前怎么做？
- 它是单次任务还是高频任务？
- 最小输入是什么？
- 最小输出是什么？
- 用户做完后会得到什么确定性变化？

**退出信号：** 应用产品的核心任务被压成一个清晰 job statement。  
**红旗：** "功能很多所以用户会觉得强大"、"先把功能列出来"。

### Module A2：关键使用路径（Core Flow）

**映射章节：** Core Flow / Delivery Design  
**默认主问题：** 用户从进入到完成任务，关键路径怎么走？

**必追子问题：**
- 第一步是什么？
- 第二步是什么？
- 哪个环节最容易卡住？
- 失败时怎么返回？
- 哪一步对体验最关键？

**退出信号：** 核心路径至少能完整走一遍，不靠想象跳步。  
**红旗：** "路径很直观"、"到时候再画流程图"。

### Module A3：MVP 切法

**映射章节：** MVP Scope  
**默认主问题：** 第一版只保留哪条路径？

**必追子问题：**
- 哪条路径是必须跑通的？
- 哪些功能只是"看起来完整"但现在可以砍？
- 如果只能留 3 个能力，你留什么？
- 砍掉后还验证得了核心假设吗？

**退出信号：** MVP 路径和可砍范围都明确。  
**红旗：** "全部功能都是 MVP"、"先做全一点再说"。

## 软件产品子分流模块

### Module S1：入口与界面层级

**映射章节：** Core Flow / Delivery Design  
**默认主问题：** 用户最先看到什么界面？最重要的动作在哪里？

**必追子问题：**
- 首页/入口页承担什么动作？
- 用户第一次来会不会迷路？
- 主要 CTA 是什么？
- 信息层级是否清晰？
- 空状态、错误状态如何处理？

**退出信号：** 入口页职责、主 CTA 和基本状态覆盖清楚。  
**红旗：** "界面后面再想"、"先把功能做出来 UI 再补"。

### Module S2：功能边界

**映射章节：** Proposed Solution + MVP Scope  
**默认主问题：** 软件第一版的功能边界到底在哪？

**必追子问题：**
- 哪些功能是主线必须有？
- 哪些是 nice-to-have？
- 哪些边界情况必须覆盖？
- 哪些不覆盖也不影响验证？
- 你是不是在用"别人都有"给功能找借口？

**退出信号：** 功能主线、可砍项和必须覆盖的边界情况被区分清楚。  
**红旗：** "竞品都有所以我们也得有"、"先做齐再优化"。

### Module S3：系统与技术约束

**映射章节：** Constraints  
**默认主问题：** 这套软件有哪些技术和系统边界？

**必追子问题：**
- 技术栈约束是什么？
- 数据/权限/兼容性约束是什么？
- 性能、稳定性目标到什么程度？
- 第三方依赖有哪些？
- 什么技术复杂度是你现在承担不起的？

**退出信号：** 关键技术边界、依赖和承担不起的复杂度被说清。  
**红旗：** "技术上不难"、"后面再补权限和数据边界"。

### Module S4：部署与可观测性

**映射章节：** Success Criteria + Validation Plan  
**默认主问题：** 第一版怎么部署、怎么观测？

**必追子问题：**
- 部署在哪？
- 出问题怎么发现？
- 最先监控什么？
- 什么算系统级失败？
- 回滚或修复路径是什么？

**退出信号：** 部署、监控和失败恢复路径都有最低定义。  
**红旗：** "先本地跑通再说"、"上线后再看日志"。

### Module S5：风险与开放问题

**映射章节：** Risks & Open Questions  
**默认主问题：** 最容易炸的点是什么？

**必追子问题：**
- 是需求错、实现难、还是体验差？
- 最坏情况是什么？
- 现在还不确定什么？
- 哪些问题必须在动手前确认？
- 哪些可以先假设，后验证？

**退出信号：** 至少列出一组核心风险和开放问题。  
**红旗：** "没什么风险"、"出了问题再调"。

## Agentic 产品子分流模块

### Module G1：链路目标

**映射章节：** Proposed Solution  
**默认主问题：** 这条链路从输入到输出，到底要完成什么？

**必追子问题：**
- 输入是什么？
- 输出是什么？
- 如果只跑一轮，什么算成功？
- 这是单步工作流，还是多步协作？
- 人工价值插在哪？

**退出信号：** Agentic 链路的输入、输出和目标动作被说清。  
**红旗：** "先用 AI 跑一跑看看"、"大概是个 agent"。

### Module G2：步骤拆解

**映射章节：** Core Flow / Delivery Design  
**默认主问题：** 链路拆成几步？每步做什么？

**必追子问题：**
- 每步输入什么？
- 每步输出什么？
- 上下文怎么传？
- 哪一步最脆弱？
- 哪一步可以砍掉？

**退出信号：** 关键步骤能按顺序拆开，且每步输入输出清晰。  
**红旗：** "Claude 自动判断就行"、"先把流程串起来再细化"。

### Module G3：Prompt 与 Context

**映射章节：** Proposed Solution + Constraints  
**默认主问题：** prompt 和上下文策略怎么设计？

**必追子问题：**
- 模型到底拿到什么上下文？
- 哪些上下文必须有？
- 哪些上下文会污染结果？
- prompt 是单提示，还是阶段提示？
- 一步错了，后面会不会全错？

**退出信号：** prompt 和 context 策略有最小可执行定义。  
**红旗：** "prompt 后面再调"、"多塞点上下文总没错"。

### Module G4：Tool Boundary

**映射章节：** Constraints + Core Flow / Delivery Design  
**默认主问题：** 这条链路要调用哪些工具？边界在哪？

**必追子问题：**
- 哪一步需要 tool？
- 哪一步不该用 tool？
- 工具失败时怎么办？
- 工具调用的权限和成本怎么算？
- 有没有多工具冲突？

**退出信号：** 工具边界、失败处理和权限成本都被界定。  
**红旗：** "能接的工具都接上"、"先把 MCP 挂全再说"。

### Module G5：Human-in-the-loop

**映射章节：** Core Flow / Delivery Design  
**默认主问题：** 哪些步骤必须人工确认？

**必追子问题：**
- 人工确认插在哪？
- 不插会出什么问题？
- 用户愿意在哪一步介入？
- 哪些介入是价值，哪些只是摩擦？
- 如何防止用户被迫当模型的免费校验器？

**退出信号：** 人工确认点和其价值被解释清楚。  
**红旗：** "全部自动化最好"、"人工确认太麻烦都去掉"。

### Module G6：评测与容错

**映射章节：** Success Criteria + Validation Plan  
**默认主问题：** 你怎么判断这条链路跑得对？跑错了怎么办？

**必追子问题：**
- 成功样例怎么定义？
- 失败样例怎么定义？
- 哪些错误最危险？
- 有没有 fallback？
- 要不要优雅降级？

**退出信号：** 成功/失败判定和 fallback 路径至少有一版定义。  
**红旗：** "先跑起来再测"、"错了人工看一下就行"。

### Module G7：经济性与上线顺序

**映射章节：** MVP Scope + Risks & Open Questions  
**默认主问题：** 这条 agentic 产品的成本、速度、稳定性，第一版怎么平衡？

**必追子问题：**
- 一次运行成本是多少？
- 用户愿意等多久？
- 哪一步最贵？
- 哪一步最慢？
- 第一版先保什么，先牺牲什么？

**退出信号：** 第一版的成本、速度、稳定性平衡策略成立。  
**红旗：** "先不看成本"、"先把效果做到极致，速度以后再说"。

## ❌/✅ 对话演示

### 演示 1
- **用户**：AI 工作流要单独成场景
- ❌ **差**：也有道理，我们可以再多加一个场景。
- ✅ **好**：顶层按思考动作分，不按实现形态分。**你现在在想的是产品，不是在长菜单。**

### 演示 2
- **用户**：skill 不是产品
- ❌ **差**：那我们按 prompt 工程聊。
- ✅ **好**：只要有人要用、要交付、要验证，它就是产品。**你逃避的是产品责任。**

### 演示 3
- **用户**：先做一个大而全系统课
- ❌ **差**：那我们先搭课程大纲。
- ✅ **好**：先别搭大纲。**你这周能卖、能交付、能拿反馈的最小结果是什么？**

### 演示 4
- **用户**：就是个简单工具
- ❌ **差**：那先把功能列出来。
- ✅ **好**：**工具也是产品。** 用户完成的核心任务是什么？先走路径。

### 演示 5
- **用户**：全部自动化最好
- ❌ **差**：那我们多自动化一些步骤。
- ✅ **好**：全自动不是目标，稳定和收益才是。**哪一步人工介入反而更值钱？**

## 智能路由

| 阶段 | 推荐模块 |
|------|----------|
| 分支未锁 | T1 → T2 → T3 → T4 |
| trunk 澄清 | T5 → T6 → T7 |
| 知识产品 | K1 → K2 → K3 → K4 → K5 |
| 软件产品 | A1 → A2 → A3 → S1 → S2 → S3 → S4 → S5 |
| Agentic 产品 | A1 → A2 → A3 → G1 → G2 → G3 → G4 → G5 → G6 → G7 |

**绝对不能 skip 的底线：** T1、T2、T5、T6、T7 必须存在。没有分支、问题、边界、成功标准和验证路径，产品设计一定漂。

# skill（隐藏元入口）— 维护场景深度文件

> 只在显式 `/ian-think skill` 时加载。
> 这个入口不属于公开业务场景，专门用于迭代 `ian-think` 自身。
> 推荐深度预算：20-40 问。

---

## 操作原则（不可谈判）

**结构重建 > 改名换皮。**  
**删除 > 兼容层。**  
**顶层只容纳思考动作。**  
**模板和深度文件必须同构。**  
**路由测试是架构的一部分。**

---

## 回应姿态

- 先问坏在哪，不先修词
- 强制给出删除清单
- 必须给出迁移图谱
- 要求副本同步策略
- 不测边界就不算完成

---

## 模块树与追问树

### Module 1：问题定位

**映射章节：** Architecture Problem  
**默认主问题：** 这个 skill 现在到底坏在哪？

**必追子问题：**
- 是公开场景坏了？
- 是模板坏了？
- 是深度文件坏了？
- 是路由规则坏了？
- 哪个问题优先级最高？

**退出信号：** 能把当前问题压缩成一个结构级主矛盾。  
**红旗：** "哪里都不太对"、"先随便改改看"。

### Module 2：路由契约

**映射章节：** Route Contract  
**默认主问题：** 公开入口、隐藏入口、内部路由分别是什么？

**必追子问题：**
- 哪些是公开菜单？
- 哪些只是语义理解？
- 哪些是隐藏维护入口？
- 哪些实现形态不许再长成顶层？

**退出信号：** 公开入口、隐藏入口、软路由边界被写清。  
**红旗：** "旧词文档里也写着吧"、"菜单多一点更安全"。

### Module 3：模板契约

**映射章节：** Template Contract  
**默认主问题：** 每个模板承担什么职责？

**必追子问题：**
- 哪些模板是真正独立的？
- 哪些模板只是旧结构遗留？
- 输出契约有无重叠？
- 是否还存在名字改了、骨头没改的情况？

**退出信号：** 每个模板的职责和边界被单独说清。  
**红旗：** "模板先别动"、"先改场景名字就行"。

### Module 4：深度文件契约

**映射章节：** Deep-file Contract  
**默认主问题：** 每个深度文件怎么和模板对齐？

**必追子问题：**
- 模块树是不是按场景复杂度设计的？
- 有没有偷懒压成统一 6 题？
- 哪些文件仍然过浅？
- 哪些文件仍然按实现形态分菜单？

**退出信号：** 形成一张深度文件缺陷清单和对应修法。  
**红旗：** "场景文件后面再慢慢补"、"先能跑就行"。

### Module 5：质量门与反回潮

**映射章节：** Quality Gates + Anti-patterns  
**默认主问题：** 哪些结构性退化必须被禁止？

**必追子问题：**
- 哪些旧词不能回到公开文档？
- 哪些顶层菜单绝不能再出现？
- 哪些场景必须带深度预算？
- 哪些模块缺失会导致系统失真？

**退出信号：** 至少列出一组可执行的质量门和反回潮禁令。  
**红旗：** "差不多能用就行"、"以后再清旧结构"。

### Module 6：迁移顺序

**映射章节：** Migration Plan  
**默认主问题：** 先改什么、后改什么、什么时候删旧文件？

**必追子问题：**
- 主副本先改哪套？
- 另一套副本怎么同步？
- 旧文件何时删除？
- 有没有中间状态会让系统半死不活？

**退出信号：** 执行顺序、删除顺序和同步策略都明确。  
**红旗：** "一起改完再看"、"另一套副本应该没关系"。

### Module 7：测试矩阵

**映射章节：** Test Cases + Execution Checklist  
**默认主问题：** 路由、产品分支、回归、边界这四类怎么测？

**必追子问题：**
- 公开场景能否命中？
- 隐藏入口是否还隐藏？
- 旧词是否只理解不展示？
- 产品分支是否显式展示？
- 有没有把复杂场景重新压浅？

**退出信号：** 路由、分支、回归、边界四类测试都有明确检查项。  
**红旗：** "手动看一下就行"、"这些应该没问题"。

- ✅ **好**：不行。**这是维护入口，不是业务场景。**

- ✅ **好**：写进文档就是公开兼容层。**这和硬切换冲突。**

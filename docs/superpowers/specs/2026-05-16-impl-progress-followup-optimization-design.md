# 实施阶段进展汇报优化 BUG 修改设计文档

## 1. 问题摘要

- Bug 名称：实施阶段进展汇报过长且“接手询问”约束不够显式
- 影响对象：使用团队委派流程推进实施阶段的最终用户
- 影响业务链路：`start -> implementation running -> status 持续跟进 -> 用户感知进展/决策`
- 当前失败结果：
  - 有进展时，`progress_update.text` 可能是较长原文片段，不满足“简短总结”体验目标。
  - “仅在长时间无进展后才询问是否接手”的规则主要体现在逻辑与技能文档，缺少对“摘要优先返回”和“恢复进展后清空旧沉默状态”的交付级约束表达。
- 修复后预期业务结果：
  - 有进展就输出简短、可理解的进展总结素材。
  - 未超过沉默阈值不打断用户。
  - 超过沉默阈值后才询问“继续等待或主会话接手”。
  - 用户选择继续等待后进入新周期，一旦再有新进展，旧沉默计时与询问语义被清空。

## 2. 失败事实

- 触发入口：Codex CLI + 已安装插件 + 自然语言触发团队委派流程。
- 用户输入：
  - “帮我用团队委派流程完成这个开发任务。”
  - “过程中有进展就告诉我，没动静太久再问我是否接手。”
- 实际表现：
  - `status` 返回的 `progress_update.text` 为事件增量原文压缩，内容可能较长，主会话若直接转述会偏离“简短总结”。
  - 决策触发逻辑在实现中正确依赖沉默阈值，但“仅在超阈值才询问”的交付级断言与用户感知约束需要补强。
- 预期表现：
  - 有进展时返回更短的摘要素材供主会话直接播报。
  - 只有进入 `NEEDS_USER_DECISION` 才出现接手询问。
  - 恢复进展后，不应沿用旧沉默窗口继续触发历史询问。
- 复现频率：稳定可复现（有进展文本较长场景可通过事件堆积稳定触发）。
- 证据：
  - `src/session/bridge-service.ts:3436` `trackWorkflowStatusPoll`：有新输出时会重置计数并清空决策窗口；无新输出超时后进入 `NEEDS_USER_DECISION`。
  - `src/session/bridge-service.ts:5518` `collectWorkflowProgressDelta`：当前输出以原始事件文本拼接压缩为主。
  - `src/session/bridge-service.ts:4446` `NEEDS_USER_DECISION` 返回二选一动作。
  - `skills/team-delegate/SKILL.md` 已要求“有进展简短总结、长时间无进展再询问”。

## 3. 影响范围

- 受影响功能：
  - 实施阶段 `status` 跟进的进展可见性输出。
  - `NEEDS_USER_DECISION` 前后的用户打断节奏感知。
- 受影响用户动作：
  - 用户在等待实施时的“读进展、做接手决策”。
- 受影响状态或数据：
  - `progress_update` 输出结构（新增摘要字段，不破坏现字段）。
  - 沉默窗口与决策窗口的可见语义。
- 不受影响范围：
  - 方案/计划阶段判定逻辑。
  - 交付测试/整改闭环的主流程动作集合。
  - `continue_wait` / `handoff_to_main` 动作语义。
- 不修复风险：
  - 用户端持续收到过长进展片段，理解成本高。
  - “何时才会询问接手”缺乏更强交付断言，后续改动易引入回归。

## 4. 根因分析

### 4.1 直接原因

- 进展输出以增量原文文本为主，缺少服务端统一“简短摘要”字段，主会话需要自行二次摘要，存在不一致空间。

### 4.2 深层原因

- 规则层（skill/README）强调了用户体验目标，但状态返回载荷没有给出“默认可直接播报的短摘要”，导致实现与规则之间存在表达层缝隙。

### 4.3 为什么现有测试没有完全发现

- 已有测试覆盖“有进展时不进入决策、无进展超时进入决策”，但对“进展文本长度/摘要优先可用性”的约束不足。
- 对“恢复进展后用户侧不应延续旧沉默询问语义”的交付级断言还可补强。

### 4.4 证据链

1. `status` 调用链：`waitForWorkflowFollowUpDue -> trackWorkflowStatusPoll -> buildWorkflowStatusResponse`。
2. `trackWorkflowStatusPoll` 在 `hasNewOutput=true` 分支会清空决策窗口与默认继续计数，说明机制基础存在。
3. `collectWorkflowProgressDelta` 返回文本为事件原文拼接压缩，缺少显式短摘要载荷。
4. 业务目标要求“有进展简短总结；长时间无进展再询问接手”与当前载荷表达存在改进空间。

## 5. 修复目标与非目标

### 5.1 修复目标

1. 在 `progress_update` 中提供稳定的短摘要字段，优先服务“有进展就简短汇报”。
2. 保持并强化“仅在沉默超阈值后才进入 `NEEDS_USER_DECISION`”的行为断言。
3. 明确验证“出现新进展后清空旧沉默决策窗口”的可见行为。
4. 同步更新团队委派技能/文档中的实施阶段表达，确保实现与流程文档一致。

### 5.2 非目标

1. 不修改模型选择闸门。
2. 不修改整改轮次、交付测试闭环策略。
3. 不改变 `continue_wait` / `handoff_to_main` 的动作定义。

## 6. 修复设计

### 6.1 状态机变化

- 不新增状态枚举，不改变阶段流转。
- 保持：
  - 有新进展：继续 `RUNNING_*`。
  - 无新进展且超阈值：进入 `NEEDS_USER_DECISION`。

### 6.2 用户可见行为变化

1. 有新进展时：
  - 返回短摘要字段（例如 `progress_update.summary`），长度受控。
  - 主会话可直接使用该摘要向用户简短汇报。
2. 无新进展未超阈值时：
  - 不触发接手询问。
3. 无新进展超阈值时：
  - 才返回接手决策提示（继续等待/主会话接手）。
4. 恢复进展后：
  - 清空旧沉默决策窗口并恢复正常进展汇报。

### 6.3 数据结构或接口变化

- `progress_update` 增加兼容字段（新增不破坏）：
  - `summary`: string（短摘要）
  - `summary_truncated`: boolean（可选，指示摘要是否截断）
- 保留既有字段：`text`, `has_new_output`, `event_count`, `silence_seconds` 等。

### 6.4 错误处理变化

- 若无法提取有效摘要，回退到安全短文本（如首行压缩文本），不影响流程推进。

### 6.5 兼容性处理

- 旧调用方仍可继续读取 `progress_update.text`。
- 新调用方优先读取 `progress_update.summary`。

### 6.6 回退方案

- 若摘要字段引发兼容问题，可快速回退为仅保留 `text`（不影响状态流转）。

## 7. 修改范围

- `src/session/bridge-service.ts`：进展增量载荷构建与状态返回增强（摘要字段与行为断言）。
- `tests/unit/bridge-service-workflow.test.ts`：新增/调整单测，覆盖摘要输出与沉默决策行为。
- `skills/team-delegate/SKILL.md`：补强实施阶段“有进展简短汇报、无进展超阈值才询问”的执行表述（如需微调）。
- `README.md`：对外文档同步 `progress_update` 摘要字段与使用建议（如需）。

## 8. 自动化验证目标

- 红灯测试（先失败）：
  1. 有新进展时 `progress_update.summary` 存在且短文本可用。
  2. 无新进展未超阈值时不进入 `NEEDS_USER_DECISION`。
  3. 无新进展超阈值后进入 `NEEDS_USER_DECISION`。
  4. 进入决策后再次出现新进展，状态恢复运行且旧决策窗口被清空。
- 回归测试：
  - 既有实施阶段状态流转测试继续通过。
  - 既有 `continue_wait`/`timeout_default` 行为测试继续通过。

## 9. 交付测试目标

- 真实入口：
  1. 安装当前插件。
  2. 刷新/重启 Codex 环境。
  3. 打开 Codex CLI。
  4. 使用自然语言触发团队委派流程。
- 真实业务语言示例：
  - “帮我用团队委派流程完成这个开发任务。”
  - “有进展就告诉我，没动静太久再问我是否接手。”
- 复测链路：
  1. 进入实施阶段并持续 `status` 跟进。
  2. 当 ACP 有输出时，主会话基于短摘要做简短播报。
  3. 在沉默阈值内，不出现接手询问。
  4. 超过沉默阈值后，出现继续等待/接手二选一。
  5. 选择继续等待后进入新周期；再次出现进展时，恢复简短播报且不沿用旧沉默询问。
- 通过标准：
  - 用户全程通过自然语言即可完成链路，且体验符合“有进展简短汇报、久无进展再询问接手”。
- 失败后闭环：
  - 记录失败位置、用户输入、实际表现、预期表现、复现步骤；修复后重走同链路复测。

## 10. 风险与回退

- 风险：
  1. 摘要压缩策略过度，导致关键信息丢失。
  2. 文档/skill 与实现更新不同步，造成提示口径不一致。
- 回退路径：
  1. 保留原 `text` 字段作为兜底展示。
  2. 出现兼容问题时优先回退摘要字段相关改动，不动状态机主流程。

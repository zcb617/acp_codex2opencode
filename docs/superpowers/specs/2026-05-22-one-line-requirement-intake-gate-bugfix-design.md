# 团队委派一句话需求误入方案阶段 BUG 修复设计

## 1. 问题摘要

- Bug 名称：团队委派一句话需求误入方案阶段
- 影响对象：通过 Codex CLI 用自然语言发起团队委派的最终用户
- 影响业务链路：团队委派入口阶段判定 -> 是否先做任务定位 -> 是否先做需求深挖 -> 方案制定
- 当前失败结果：用户仅给出一句话新增需求时，系统直接进入方案制定或方案执行方选择，没有先完成任务定位，也没有先判断是否需要需求深挖
- 修复后业务结果：一句话需求先进入入口梳理，优先判断任务定位；当最小业务信息不足时，先进入上下文补充/需求深挖，再决定是否进入方案阶段

## 2. 失败事实

- 触发入口：Codex CLI 自然语言触发团队委派技能
- 用户输入：`我要增加一个翻译功能，比如翻译截图里的文字，翻译当前选中行的文字。`
- 实际表现：首屏直接进入方案制定语义，没有先停在任务定位或需求补齐
- 预期表现：系统应先判断这是现有功能升级还是新功能开发，再判断信息是否足够；若只是句子级需求且缺少边界、成功标准、约束、优先级等最小业务信息，应先进入补充上下文/需求深挖，而不是直接做方案
- 失败场景：新增功能的一句话需求入口
- 复现频率：按当前规则高概率稳定复现
- 证据：用户提供的会话截图；`skills/team-delegate/SKILL.md` 当前未把纯一句话新增需求列为入口硬门槛；`tests/plugin/install.plugin.test.ts` 与 `tests/delivery/team-delegate-skill.delivery.test.ts` 也未建立对应护栏

## 3. 影响范围

- 受影响功能：团队委派入口阶段判定、需求深挖分流、方案前置梳理
- 受影响用户动作：用户提出一句话需求后，对当前阶段和下一步动作的理解与决策
- 受影响状态/数据：`start_phase` 的业务语义判定、是否进入 `NEEDS_USER_INPUT`、是否挂起 `requirements_package` 门禁
- 不受影响范围：实施阶段持续跟进、模型选择、交付测试闭环、整改闭环
- 不修复风险：系统会把信息不足的需求过早推进到方案阶段，导致方案建立在缺失边界和验收条件的前提上，后续反复返工

## 4. 根因分析

### 4.1 直接原因

- `skills/team-delegate/SKILL.md` 没有把“纯一句话新增需求”列为硬性入口分流条件，只强调了“参考资料 + 一句话目标”与“缺少最小业务信息”这类原则描述，缺少可执行的首轮判定步骤。
- 当前规则把“任务定位”和“代码证据收集”主要放在进入主会话 `design` 之后执行，导致入口阶段容易被直接判成方案制定。

### 4.2 深层原因

- 入口规则缺少“先定位、再判深挖、最后才允许进方案”的顺序约束。
- 安装测试和交付级测试没有覆盖这类一句话需求的入口规则，导致规则缺口长期没有被自动化抓住。

### 4.3 为什么现有测试没有发现

- `tests/plugin/install.plugin.test.ts` 与 `tests/delivery/team-delegate-skill.delivery.test.ts` 只校验了“参考资料 + 一句话目标”“缺少最小业务信息”等宽泛规则，没有校验“纯一句话新增需求”“先定位再判深挖”的规则存在。
- 单元测试更多覆盖“如果已经判成 need_user_input，状态机会不会继续拦住”，但没有覆盖技能入口文本层的首轮分流要求。

### 4.4 证据链

- [skills/team-delegate/SKILL.md](/var/work/acp_codex2opencode/skills/team-delegate/SKILL.md):159 当前 `NEEDS_USER_INPUT` 规则缺少纯一句话新增需求的硬门槛。
- [skills/team-delegate/SKILL.md](/var/work/acp_codex2opencode/skills/team-delegate/SKILL.md):176 任务类型判定被放在 `design` 前置梳理里，时机偏后。
- [tests/plugin/install.plugin.test.ts](/var/work/acp_codex2opencode/tests/plugin/install.plugin.test.ts):141 当前安装测试未断言一句话新增需求规则。
- [tests/delivery/team-delegate-skill.delivery.test.ts](/var/work/acp_codex2opencode/tests/delivery/team-delegate-skill.delivery.test.ts):44 当前交付级技能测试未断言一句话新增需求规则。

## 5. 修复目标与非目标

### 5.1 修复目标

1. 团队委派入口新增“先任务定位、再判断是否需要需求深挖”的硬规则。
2. 纯一句话新增需求不得直接进入方案阶段，必须先补足最小业务信息或先进入需求深挖。
3. 主会话在进入方案阶段前，要明确区分“现有功能升级”和“新功能开发”；若证据不足，先停在补充上下文。
4. 补充安装级与交付级回归测试，防止入口规则回退。

### 5.2 非目标

1. 不修改 `BridgeService` 的状态机结构和已有 `requirements_package` 门禁协议。
2. 不新增新的业务阶段枚举。
3. 不改实施、交付测试、整改阶段的自动跟进逻辑。

## 6. 修复设计

### 6.1 入口判定规则补强

- 在 `skills/team-delegate/SKILL.md` 的 `NEEDS_USER_INPUT` 规则中增加明确场景：当用户只给一句话新增需求，且缺少业务边界、成功标准、约束、优先级等最小信息时，必须先停在上下文补充，不得直接进入 `design`。
- 新增入口顺序：先任务定位，再判断是否需要需求深挖，再决定是否进入方案。

### 6.2 方案前置梳理时机前移

- 保留 `design` 阶段中的详细前置梳理，但在技能入口处先增加轻量版任务定位门槛，避免用户在信息不足时被提前推入方案阶段。
- 对“现有功能升级”场景，明确要求先收集代码证据；若当前对涉及功能范围都说不清，则先回到补充上下文，而不是强行写方案。

### 6.3 测试护栏补充

- 更新插件安装测试和技能交付测试，断言技能文档必须包含“纯一句话新增需求先定位、再判断是否深挖、不得直接进方案”的规则。
- 保留既有需求深挖门禁测试，确保新规则没有破坏旧门禁。

### 6.4 回退方案

- 若新规则导致已有明确方案/计划输入被误拦截，则回退到本次修改前版本，并保留新增测试样例定位误差点。

## 8. 自动化验证目标

- 红灯目标：先证明当前技能规则未包含“纯一句话新增需求先定位/先补信息”的硬约束，测试应失败。
- 绿灯目标：修复后技能规则与安装产物测试通过，且既有需求深挖门禁测试不回归。
- 回归目标：确保既有 `NEEDS_USER_INPUT` 与 `requirements_package` 流程仍然成立。

## 9. 交付测试目标

### 9.1 真实入口

1. 安装当前插件。
2. 刷新或重启 Codex 使用环境。
3. 打开 Codex CLI，并使用 `gpt-5.3-codex` 模型。
4. 输入真实自然语言一句话需求，触发团队委派流程。

### 9.2 同链路复测

- 复测用语：

```text
帮我用团队委派流程做一个新功能：增加截图翻译和当前选中行翻译。
```

- 通过标准：
1. 首屏不能直接进入方案制定或说“开始做方案”。
2. 先说明当前处于需求深挖前的定位/补齐阶段。
3. 先判断是现有功能升级还是新功能开发。
4. 当业务信息不足时，明确要求补充边界、成功标准、约束、优先级，或询问是否进入需求深挖。
5. 不出现跳过定位直接写方案的现象。

### 9.3 必过项约束

- 每次交付测试必须再次执行并通过 `docs/团队委派交付测试必过表.md` 全部测试项；任一项失败即判定本次交付测试失败。

### 9.4 失败后整改闭环

- 若交付测试失败：记录用户输入、首屏输出、错误阶段判断、预期阶段判断 -> 补充设计与计划 -> 修改技能与测试 -> 重新执行自动化验证 -> 重新执行同一真实入口复测。

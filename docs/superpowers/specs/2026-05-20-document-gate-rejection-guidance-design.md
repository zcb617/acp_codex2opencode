# 文档门禁拒绝缺少指南指引整改设计文档

## 1. 问题摘要

- Bug 名称：方案/计划文档门禁拒绝后缺少对应指南指引，主会话无法按规范完成修订
- 影响对象：通过团队委派流程修订方案文档或计划文档的主会话与最终用户
- 影响业务链路：`自然语言触发团队委派 -> 生成或修订方案/计划文档 -> 门禁拒绝 -> 主会话继续修订 -> 再次提交`
- 当前失败结果：
  - 当方案文档或计划文档被门禁拒绝时，返回结果通常只说明“大类缺项”或给出 `missing_sections`。
  - 主会话无法从首屏业务反馈中直接知道：当前修订的是方案还是计划、属于 BUG 修改还是新增功能、应该回看哪份指南。
  - 结果是主会话虽然知道“不能继续”，但不知道“该按哪套规则补完后再继续”，修订闭环会反复试错。
- 修复后应恢复的业务结果：
  - 方案文档被拒绝时，系统必须明确提示“当前进入方案修订”，并给出对应方案指南路径。
  - 计划文档被拒绝时，系统必须明确提示“当前进入计划修订”，并给出对应计划指南路径。
  - 指南选择必须与开发类型绑定，保证 BUG 修改和新增功能分别回到正确规范。

## 2. 失败事实

- 触发入口：已安装插件的真实 Codex CLI 团队委派流程，以及仓库内对应的门禁测试链路。
- 用户输入：
  - “设计和计划已经确认，直接进入实施。”
  - “请根据刚才的反馈修订方案文档后再继续。”
- 实际表现：
  - 实施前计划门禁失败时，业务返回会提示“计划文档还不满足实施要求”，并附带 `missing_sections`。
  - 方案确认态和计划确认态虽然内部保存了 `phase_gates` 和 `document_profile`，但主反馈未明确告诉主会话当前应回看哪份指南。
  - 主会话只能知道“Task 明细不合规”或“某章节缺失”，但不知道需要回看 `可交付BUG修改计划编写指南-v0.1.md` 还是 `可交付开发计划编写指南-v0.1.md`。
- 预期表现：
  - 当门禁拒绝发生时，首屏业务反馈必须包含“文档类型 + 开发类型 + 对应指南路径 + 下一步修订动作”。
  - 即便仍保留 `missing_sections`，主会话也能立刻按正确指南修订，而不是自行猜测。
- 失败时间或场景：2026-05-20，针对方案/计划文档修订流程的业务评审与代码核查。
- 复现频率：稳定复现。
- 证据：
  - `src/session/bridge-service.ts:2045-2070`：实施前计划门禁失败只返回“计划修订 + 缺项”，没有明确指南指引。
  - `src/session/bridge-service.ts:4438-4458`：`WAITING_DESIGN_APPROVAL` / `WAITING_PLAN_APPROVAL` 只返回阶段与动作，没有把修订依据翻译成业务反馈。
  - `src/session/bridge-service.ts:2240-2252`：系统内部已经能解析出 `document_profile` 与设计/计划指南路径，说明缺的不是数据，而是反馈出口。
  - `tests/unit/bridge-service-workflow.test.ts:401-449`：当前仅断言门禁会挡住实施，但没有断言“返回必须告知该看哪份指南”。

## 3. 影响范围

- 受影响功能：
  - 方案文档门禁拒绝后的业务反馈。
  - 计划文档门禁拒绝后的业务反馈。
  - 实施入口前计划门禁失败后的修订闭环。
- 受影响用户动作：
  - 主会话根据反馈修订方案文档。
  - 主会话根据反馈修订计划文档。
  - 用户判断系统是否已经给出清晰的下一步业务动作。
- 受影响状态或数据：
  - `WAITING_DESIGN_APPROVAL`
  - `WAITING_PLAN_APPROVAL`
  - `NEEDS_USER_INPUT`（implementation plan gate failed）
  - `document_profile`、`phase_gates`、`missing_sections` 的对外表达方式
- 不受影响范围：
  - 文档门禁本身的章节校验规则。
  - 设计/计划/实施阶段的状态机主流程。
  - `missing_sections` 的具体判定逻辑。
- 如果不修复的交付风险：
  - 主会话收到拒绝后仍无法高确定性地继续修订。
  - 用户看到的只是“缺一大块”，但不能确认系统到底希望其回看哪套规范。
  - 门禁会持续充当“只拦截不指路”的阻塞点，损伤真实业务可交付性。

## 4. 根因分析

### 4.1 直接原因

- 门禁拒绝出口只强调“当前不能继续”和“缺了哪些章节/字段”，没有把已有的指南元数据提升成下一步业务指令。

### 4.2 深层原因

- 当前实现把 `document_profile` 视为辅助数据，主要用于提示词和内部判定，没有统一封装成“文档修订指引”返回给主会话。
- `WAITING_DESIGN_APPROVAL` 和 `WAITING_PLAN_APPROVAL` 侧重表达“等待反馈/批准”，没有区分“文档已经可审阅”与“文档其实仍不合规，需要按指定指南修订”这两种业务意图。
- 实施前计划门禁失败单独走了一套 `buildImplementationPlanGateNeedsInputResponse`，导致它和设计/计划确认态之间没有共享同一套修订反馈模型。

### 4.3 为什么现有测试没有发现

- 现有测试验证了状态机会挡住不合规文档，但没有把“拒绝后必须告知对应指南”写成业务契约。
- 测试覆盖了 `missing_sections`，却没有验证 `user_message` / `next_business_action` / 结构化返回是否足以指导主会话完成下一步修订。

### 4.4 证据链

1. `src/session/bridge-service.ts` 内部 `DOCUMENT_PROFILES` 已绑定四份指南文件，说明系统知道该看哪份规范。
2. `toDocumentProfilePayload()` 已能产出 `design_guide` / `planning_guide` / relative path，说明元数据可用。
3. `WAITING_DESIGN_APPROVAL` 与 `WAITING_PLAN_APPROVAL` 当前未利用这些元数据补足业务反馈。
4. `buildImplementationPlanGateNeedsInputResponse()` 当前仅给出笼统修订提示，未指向具体指南。

## 5. 修复目标与非目标

### 5.1 修复目标

1. 为方案文档拒绝与计划文档拒绝建立统一的“文档修订指引”反馈结构。
2. 当方案文档不合规时，明确提示主会话回看对应方案指南。
3. 当计划文档不合规时，明确提示主会话回看对应计划指南。
4. 指南选择必须根据开发类型自动切换：
   - `bugfix` -> BUG 设计/计划指南
   - `feature` -> 开发设计/计划指南
5. 实施前计划门禁失败必须复用同一套修订指引，而不是单独输出笼统说明。

### 5.2 非目标

1. 不修改现有章节完整性校验规则。
2. 不扩展新的文档类型或新的阶段状态。
3. 不在本次变更中细化 `missing_sections` 到逐句或逐行级别。

## 6. 修复设计

### 6.1 状态机变化

- 不改变阶段枚举与跳转条件。
- 仅增强以下三个拒绝出口的业务反馈：
  - `WAITING_DESIGN_APPROVAL`
  - `WAITING_PLAN_APPROVAL`
  - `implementation-plan-gate-failed`

### 6.2 用户可见行为变化

1. 方案门禁拒绝后，系统要明确告诉主会话：
   - 当前处于“方案修订”
   - 应查看哪份方案指南
   - 按指南补齐缺项后，再提交反馈或再次进入后续阶段
2. 计划门禁拒绝后，系统要明确告诉主会话：
   - 当前处于“计划修订”
   - 应查看哪份计划指南
   - 按指南补齐缺项后，再提交反馈或再次进入实施
3. 即使首屏仍用业务语言表达，也要同步返回结构化修订指引，便于主会话稳定读取。

### 6.3 数据结构或接口变化

- 新增统一的 `document_revision_instruction` 结构化字段，至少包含：
  - `document_type`：`design` / `planning`
  - `development_type`：`bugfix` / `feature`
  - `guide_path`
  - `guide_relative_path`
  - `required_sections`
  - `missing_sections`
  - `next_step`
- 保留现有 `document_profile`，避免破坏兼容性。
- `user_message` 与 `next_business_action` 增强为显式引用相应指南。

### 6.4 错误处理变化

- 若缺项为空但仍需要修订，仍优先依据阶段与开发类型返回对应指南，避免主会话无指引可走。
- 若未来出现不可识别的开发类型，继续沿用现有缺上下文策略，不在本次变更里扩展兜底推断。

### 6.5 兼容性处理

- 旧字段不删除，只新增并增强反馈。
- 现有依赖 `missing_sections` 的逻辑仍可继续工作。
- 新增结构化字段后，主会话可以逐步迁移到稳定读取 `document_revision_instruction`。

### 6.6 回退方案

- 若新反馈字段影响下游兼容性，可仅保留文案增强并暂时隐藏结构化字段；但只要业务要求仍然成立，最终仍需恢复结构化指引。

## 7. 修改范围

- `src/session/bridge-service.ts`：新增统一文档修订指引构造逻辑，并接入三个拒绝出口。
- `tests/unit/bridge-service-workflow.test.ts`：新增/修改红灯测试，覆盖方案拒绝、计划拒绝、实施前计划门禁拒绝的指南指引。
- `docs/superpowers/specs/2026-05-20-document-gate-rejection-guidance-design.md`：保存本次整改设计。
- `docs/superpowers/plans/2026-05-20-document-gate-rejection-guidance-plan.md`：承接本设计的实施计划。

## 8. 自动化验证目标

- 红灯测试（先失败）：
  1. 方案确认态返回中必须带正确的方案指南指引。
  2. 计划确认态返回中必须带正确的计划指南指引。
  3. 实施前计划门禁失败时，必须带正确的计划指南指引。
  4. `bugfix` 与 `feature` 两类开发类型必须分别映射到不同指南。
- 回归测试：
  - 现有 `missing_sections`、`document_profile`、状态流转、实施门禁拦截行为保持通过。

## 9. 交付测试目标

- 真实入口：
  1. 安装当前插件。
  2. 刷新或重启 Codex 环境。
  3. 打开真实 Codex CLI。
  4. 用自然语言触发团队委派流程，并让主会话落入方案或计划修订场景。
- 真实业务语言示例：
  - “帮我用团队委派流程完成这个 BUG 修复。设计文档我已经改过一次了，你继续检查，不合规的话明确告诉我该按哪份指南修。”
  - “设计和计划已经确认，直接进入实施。如果计划不合规，请明确告诉我该看哪份计划指南。”
- 通过标准：
  - 当方案文档被拒时，真实用户或主会话能从返回中清楚知道应回看哪份方案指南。
  - 当计划文档被拒时，真实用户或主会话能从返回中清楚知道应回看哪份计划指南。
  - BUG 修改和新增功能两类场景都能命中正确指南。
  - `docs/团队委派交付测试必过表.md` 中与文档修订反馈相关的项不出现“只拦截不指路”现象。
- 失败后闭环：
  - 若真实入口仍只返回笼统缺项，则记录实际话术、阶段、开发类型、缺失指南路径，再补测试和反馈逻辑后重走同一条 CLI 链路。

## 10. 风险与回退

- 风险：
  1. 反馈字段增加后，旧调用方若做严格断言，需要同步更新测试。
  2. 若只改文案不改结构化字段，主会话后续仍可能难以稳定消费。
- 回退路径：
  1. 先保证统一的结构化修订指引存在。
  2. 若业务文案需要微调，可仅调整 `user_message` / `next_business_action`，不回退结构本身。

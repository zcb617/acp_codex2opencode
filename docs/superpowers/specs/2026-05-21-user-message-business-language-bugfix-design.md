# 团队委派入口用户提示“机器话”BUG修复设计

## 1. 问题摘要

- Bug 名称：团队委派入口提示语“机器话/内部术语外露”
- 影响对象：通过 Codex CLI 使用团队委派流程的最终用户
- 影响业务链路：用户在委派入口阶段判断与下一步选择阶段的理解与决策
- 当前失败结果：提示语夹杂内部术语（如参数名、工具层级、状态语义），用户难以直接理解“现在处于哪个业务阶段、要做什么选择”
- 修复后业务结果：用户首屏提示统一使用业务语言，能直接看懂阶段、原因、选择和影响，避免被内部实现细节干扰

## 2. 失败事实

- 触发入口：Codex CLI 自然语言触发团队委派入口
- 用户输入：要求解释当前阶段并继续推进 Windows 发布相关任务
- 实际表现：系统输出包含“高层入口、workspace_path、不能绕过底层工具”等开发者视角表达，且段落冗长
- 预期表现：系统应直接用业务语言表达“当前阶段、为什么、你现在怎么选、选完会怎样”
- 失败场景：入口判定阶段与入口受限回退说明
- 复现频率：稳定可复现（同类场景反复出现）
- 证据：用户提供的界面截图（会话内证据）

## 3. 影响范围

- 受影响功能：团队委派入口的用户可见提示文案
- 受影响用户动作：阶段确认、实施执行方选择、上下文补充决策
- 受影响状态/数据：不影响状态机流转和任务数据，仅影响用户可见表达质量
- 不受影响范围：底层委派执行逻辑、阶段判定逻辑、模型选择逻辑、交付测试状态机
- 不修复风险：用户无法快速理解系统意图，错误决策概率上升，业务推进效率下降

## 4. 根因分析

### 4.1 直接原因

- 入口与补充上下文场景的 `user_message` 文案没有统一“业务导向模板”，部分提示直接暴露实现约束。
- 参数校验报错文案（例如工作目录参数）直接使用内部字段命名，容易被上层原样转述。

### 4.2 深层原因

- 文案治理缺少“首屏只讲业务语义”的强约束与复用模板。
- 团队委派技能文档虽有业务导向原则，但缺少“入口失败/参数不足场景”的固定人话模板，导致生成时波动。

### 4.3 为什么现有测试没有发现

- 现有测试重点在状态正确性与动作集合，未对“禁止内部术语直出”的可读性要求建立断言。

### 4.4 证据链

- `src/session/bridge-service.ts`：入口阶段 `user_message` 与参数校验错误文案由此集中生成。
- `skills/team-delegate/SKILL.md`：对用户输出约束有原则，但缺少入口异常的人话模板。
- `tests/unit/bridge-service-workflow.test.ts`：目前仅覆盖部分提示关键词，缺少“内部术语外露”防回归断言。

## 5. 修复目标与非目标

### 5.1 修复目标

1. 用户首屏提示统一为“四段式”：当前阶段、进入原因、用户选择、选择影响。
2. 参数缺失/受限场景的提示改成业务可理解表达，避免直接暴露内部参数名作为主提示。
3. 团队委派技能补齐入口异常的人话模板，禁止“工具层/参数名/铁律”作为首屏主表达。
4. 增加测试断言，防止文案回退为内部术语表达。

### 5.2 非目标

1. 不改委派状态机与动作编排逻辑。
2. 不改 ACP 会话生命周期与自动跟进策略。
3. 不改业务阶段判定算法本身。

## 6. 修复设计

### 6.1 文案架构调整

- 在 `BridgeService` 的入口相关响应中统一业务文案结构，保证用户先看到业务语义再看到操作建议。
- 对“工作目录缺失/不允许”类校验错误使用业务话术：说明“当前无法开始任务”的业务原因和下一步动作。

### 6.2 术语降噪策略

- 用户首屏文案禁止直接出现内部字段名、工具名、状态枚举。
- 如确有必要提及技术点，只能在业务解释之后，且必须给中文说明。

### 6.3 技能约束补强

- 在 `skills/team-delegate/SKILL.md` 中补充“入口异常人话模板”和“禁止内部术语首屏直出”规则。

### 6.4 回退方案

- 若新文案造成流程误导或测试失败，可回退到本次变更前版本，并保留测试用例以定位误差点。

## 7. 修改范围

- `src/session/bridge-service.ts`：调整入口阶段与参数校验相关用户文案。
- `skills/team-delegate/SKILL.md`：补充入口异常的人话输出模板与约束。
- `tests/unit/bridge-service-workflow.test.ts`：新增/调整文案可读性与术语外露回归断言。
- `docs/superpowers/specs/2026-05-21-user-message-business-language-bugfix-design.md`：本设计文档。
- `docs/superpowers/plans/2026-05-21-user-message-business-language-bugfix-plan.md`：对应实施计划文档。

## 8. 自动化验证目标

- 红灯目标：在入口场景断言中先体现“旧文案包含内部术语/缺少业务四段式”导致失败。
- 绿灯目标：修复后相关断言通过，且既有流程状态测试不回归。
- 回归目标：确保 `NEEDS_MAIN_DESIGN / NEEDS_MAIN_PLANNING / NEEDS_IMPLEMENTATION_EXECUTOR / NEEDS_USER_INPUT` 关键提示仍与动作集合一致。

## 9. 交付测试目标

### 9.1 真实入口

1. 安装当前插件。
2. 重启或刷新 Codex 使用环境。
3. 打开 Codex CLI（模型按项目要求使用 `gpt-5.3-codex`）。
4. 用自然语言触发团队委派流程。

### 9.2 同链路复测

- 复测用语示例：

```text
帮我用团队委派流程处理这个任务，现在我想先确认下一步该做什么。
```

```text
如果当前不能直接开始实施，请用人话告诉我现在处于哪个阶段、我要怎么选。
```

- 通过标准：
1. 首屏先说明业务阶段。
2. 明确给出进入该阶段的原因。
3. 明确给出用户下一步选择。
4. 说明选择对后续流程的影响。
5. 不以 `workspace_path`、工具名、状态枚举作为首屏主表达。

### 9.3 必过项约束

- 每次交付测试必须再次执行并通过 `docs/团队委派交付测试必过表.md` 全部测试项；任一项失败即判定本次交付测试失败。

### 9.4 失败后整改闭环

- 若交付测试失败：记录失败话术与触发语句 -> 补充设计与计划 -> 修改文案与断言 -> 重新跑自动化验证 -> 重新执行同一真实入口复测。

## 10. 当前进展与下一步

- 当前进展：已完成失败事实、根因和修复设计定义。
- 下一步：按对应计划文档执行代码修改、自动化验证与真实入口交付测试。

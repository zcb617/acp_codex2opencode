# 实施入口未严格执行计划文档门禁-BUG修改设计

## 1. 问题摘要

- Bug 名称：实施入口未严格执行计划文档门禁，导致不合规计划可进入实施前置流程。
- 影响对象：使用 team-delegate 团队委派流程的真实用户。
- 影响业务链路：用户声明“方案和计划已确认，直接进入实施”并给出计划文档路径时，插件应先验证计划文档质量，再允许进入实施前置。
- 当前失败结果：插件先进入模型选择（或上下文补充）而非先做计划文档门禁拦截。
- 修复后应恢复结果：当 `start_phase=implementation` 且提供计划文档上下文时，必须先做计划文档门禁；不合规则返回 `NEEDS_USER_INPUT` 并给出缺项，禁止进入模型选择与实施。

## 2. 失败事实

- 触发入口：Codex CLI 真实入口（`codex exec`）。
- 用户输入：
  - “帮我用团队委派流程完成这个开发任务。方案和计划都已经确认，请直接进入实施。计划文档在 tests/2026-05-16-erp-ai-adapter-enhancement-plan.md。过程中有进展就告诉我，没动静太久再问我是否接手。”
- 实际表现：
  - 首轮返回“当前已进入计划实施阶段…请选择执行模型 1/2”，未先拦截计划文档质量。
- 预期表现：
  - 先验证计划文档结构与字段完整性；若不合规，应直接返回缺项并停留在补充阶段，不得进入模型选择。
- 失败时间或场景：2026-05-16 14:38-14:39（Asia/Hong_Kong），本机真实入口复测场景。
- 是否可复现：可复现（同类输入下稳定出现）。
- 证据：
  - `runtime/delivery-live-20260516-143845-last-message.txt`
  - 终端日志中出现“下一步只需要你做一个业务选择：本次实施用哪个执行模型”。

## 3. 影响范围

- 受影响功能：实施阶段入口门禁、计划文档质量强校验。
- 受影响用户动作：用户直接要求“进入实施”时的首轮流程判断。
- 受影响状态或数据：工作流阶段可能被推进到 `NEEDS_MODEL_*` / `RUNNING_IMPLEMENTATION` 之前，绕过计划文档质量门禁。
- 不受影响范围：
  - 方案阶段、计划阶段由 ACP 生成文档时的门禁回合（`enforceDocumentGate`）逻辑。
  - 单测层面的 `evaluateDocumentContentQuality` 与 BUG 计划章节校验函数本身。
- 不修复交付风险：
  - 不合规计划可进入实施，导致后续开发输出继续偏离文档标准；真实交付闭环被前移放行，无法保证“严格按指南执行”。

## 4. 根因分析

### 4.1 直接原因

实施入口(`start_phase=implementation`)流程在 `handleStartWithModelGate -> handleModelConfirm/Select -> startWorkflowAfterModelResolved` 中，会直接进入模型选择与实施启动，不会在入口处对“用户提供的计划文档”执行强制质量门禁。

### 4.2 深层原因

当前门禁实现主要绑定在“ACP 产出设计/计划后”的 `enforceDocumentGate` 回合，缺少“直接实施入口”的前置一致性校验分支，导致两条入口路径（先计划后实施 vs 直接实施）约束不一致。

### 4.3 为什么现有测试没有发现

- 已有测试覆盖了文档质量评估函数和计划阶段门禁，但未覆盖“真实入口 + start_phase=implementation + 用户提供不合规计划路径”的端到端准入断言。
- 缺少“禁止先进入模型选择”的业务行为断言。

### 4.4 证据链

- 真实入口证据：`runtime/delivery-live-20260516-143845-last-message.txt` 显示先询问模型选择。
- 代码证据：
  - `src/session/bridge-service.ts` 中 `handleStartWithModelGate`/`startWorkflowAfterModelResolved` 进入实施前未执行“计划文档入口门禁”。
  - `launchWorkflowByEntryPhase` 对 `implementation` 直接触发 `runImplementationPhase`。
- 规则证据：项目 workflow 明确要求“计划文档不合规不得进入实施”。

## 5. 修复目标与非目标

### 5.1 修复目标

- 目标1：对“直接实施入口”补充计划文档前置门禁，与计划阶段门禁一致。
- 目标2：检测到不合规计划时，返回 `NEEDS_USER_INPUT`，并携带可执行缺项说明（章节/字段/伪代码等）。
- 目标3：在门禁失败时，禁止进入模型选择、禁止进入实施。
- 目标4：新增自动化测试覆盖“实施入口门禁失败”和“合规放行”两条路径。

### 5.2 非目标

- 不调整模型选择策略本身。
- 不改动 ACP 实施逻辑、整改轮次逻辑。
- 不新增与本 Bug 无关的文档结构规则。

## 6. 修复设计

- 状态机变化：
  - 在 `start_phase=implementation` 且检测到计划文档来源时，先执行“实施入口计划门禁校验”。
  - 校验失败：返回 `NEEDS_USER_INPUT`（业务阶段：上下文补充），附带缺项清单与下一步动作。
  - 校验通过：继续现有模型确认/选择与实施流程。
- 用户可见行为变化：
  - 从“先问模型”调整为“先校验计划文档，缺项先补齐”。
- 数据结构或接口变化：
  - `delegate.task.execute(action=start)` 响应体增加/复用门禁失败字段（如 `missing_sections` / `missing_context` / `business_reason`）。
- 错误处理变化：
  - 门禁失败视为业务可修复失败，不抛系统错误，统一走可补充路径。
- 兼容性处理：
  - 不影响 design/planning 阶段现有门禁流程。
  - 对无文档路径但用户声称已完成计划的场景，返回可理解的补充提示。
- 回退方案：
  - 若新增入口门禁引发误拦截，可通过单次回退到原分支（删除入口校验调用）恢复旧行为。

## 7. 修改范围

- `src/session/bridge-service.ts`：新增实施入口计划文档前置门禁调用、失败响应构建与准入控制。
- `tests/unit/bridge-document-gate-quality.test.ts`：新增实施入口门禁单测。
- `tests/delivery/*`：必要时补充真实业务文案/流程断言，保证业务语言一致。
- `docs/superpowers/specs/*` 与 `docs/superpowers/plans/*`：补充本次修复闭环文档。

## 8. 自动化验证目标

- 红灯先行：新增“实施入口遇到不合规计划仍进入模型选择”的失败测试。
- 绿灯标准：修复后同测试应返回 `NEEDS_USER_INPUT` 且包含缺项说明。
- 回归要求：
  - 既有 `bridge-document-gate-quality` 全通过。
  - 相关 workflow 单测不回归。
  - delivery 测试不回归。

## 9. 交付测试目标

- 真实入口：插件本机安装后，使用 Codex CLI `codex exec` 自然语言触发团队委派。
- 真实业务语言：
  - “方案和计划都已确认，直接进入实施。计划在 tests/2026-05-16-erp-ai-adapter-enhancement-plan.md。”
- 原始失败链路：
  - 直接进入模型选择（错误放行）。
- 修复后同链路复测：
  - 同样输入应先触发计划门禁并返回缺项，不应出现模型选择提示。
- 通过标准：
  - 首屏返回 `NEEDS_USER_INPUT`（业务语义为补充/修订计划），并给出清晰缺项。
  - 未出现“请选择模型”或进入实施阶段提示。
- 复测失败继续整改：
  - 记录失败事实 -> 补充设计与计划 -> 新增回归测试 -> 重跑自动化 -> 重跑同链路真实交付测试。

## 10. 风险与回退

- 风险1：入口门禁过严，误拦截历史可用场景。
  - 应对：增加“是否有计划文档来源”的条件判断；缺来源时给补充提示而非硬错误。
- 风险2：新增判断与现有 start/model 分支耦合，导致状态流转异常。
  - 应对：在单测覆盖 `start -> model_confirm/model_select` 两条路径并验证阶段一致性。
- 风险3：只修 API 层逻辑，未校验真实入口文案。
  - 应对：补充真实入口复测并保留证据文件。
- 回退路径：
  - 回滚本次入口门禁提交，恢复旧逻辑；随后以开关化方式重新上线。

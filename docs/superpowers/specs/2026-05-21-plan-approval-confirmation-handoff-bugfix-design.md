# 设计/计划执行方选择缺失且确认回合未续接团队委派闭环 BUG 修复设计

## 1. 问题摘要

- Bug 名称：设计/计划执行方选择缺失且确认回合未续接团队委派闭环
- 影响对象：通过 Codex CLI 使用团队委派流程推进方案、计划、实施链路的最终用户
- 影响业务链路：进入方案阶段或计划阶段 -> 选择由谁执行 -> 计划阶段完成 -> 用户确认计划 -> 进入实施入口
- 当前失败结果：
  1. 进入方案阶段或计划阶段前，没有稳定停在“主会话执行 / ACP 委派执行”的执行方选择闸门
  2. 计划完成后的回复没有明确提示“当前处于计划确认阶段”，也没有要求用户回复特定确认词进入下一阶段
  3. 用户下一轮回复“同意”后，主会话没有稳定续接团队委派闭环，而是直接按普通开发流程进入实现
- 修复后业务结果：
  1. 进入方案阶段或计划阶段前，必须先显式让用户选择“主会话执行（默认）/ ACP 委派执行”
  2. 计划完成后必须先停在计划确认阶段，并明确提示“如无补充请回复‘可以/同意/确认’进入下一阶段”
  3. 用户给出确认类回复后，系统必须优先续接团队委派闭环，并先进入“实施执行方选择”，而不是直接进入主会话实施

## 2. 失败事实

- 触发入口：
  - 目标电脑上的真实 Codex 使用环境
  - 用户通过自然语言触发团队委派流程，进入方案阶段、计划阶段并推进到计划完成
- 用户输入：
  1. 用户从真实入口进入方案阶段或计划阶段
  2. 方案/计划阶段前没有收到“主会话执行 / ACP 执行”的显式选择
  3. 团队委派流程中推进到计划阶段完成
  4. 用户下一轮仅回复：`同意`
- 实际表现：
  1. 进入方案阶段或计划阶段时，没有稳定暴露“1 主会话执行（默认）/ 2 ACP 委派执行”的选择闸门
  2. 计划阶段完成后的回复没有明确告诉用户当前处于“计划确认”阶段
  3. 没有明确提示“需要确认才能进入下一阶段”
  4. 没有给出明确确认词示例，例如 `可以/同意/确认`
  5. 用户回复 `同意` 后，系统直接进入主会话实现流程，输出“现在进入实现阶段了”“切分支开始实现”等普通开发动作，而没有先进入“实施执行方选择”
- 预期表现：
  1. 进入方案或计划阶段时，系统必须先明确给出两项选择：
     - `1` 主会话执行（默认）
     - `2` ACP 委派执行
  2. 计划阶段完成后，系统必须明确说明“当前计划已经整理完成，正在等待你的确认”
  3. 必须明确提示“如无补充，请回复‘可以/同意/确认’后进入下一阶段”
  4. 用户回复确认类内容后，必须优先续接团队委派闭环
  5. 计划确认后的下一步必须先进入“实施执行方选择”
- 复现频率：
  - 已有真实截图证据，且从业务链路上可稳定解释
- 关键证据：
  1. 用户反馈：进入方案与计划阶段前，没有出现“主会话完成 / ACP 完成”的执行方选择
  2. 用户提供的计划阶段完成截图显示：回复内容只说明“实施计划文档已经写完并提交”“如果继续，下一步就该进入实现阶段了”，没有确认门禁提示和确认词示例
  3. 用户提供的下一轮截图显示：仅回复 `同意` 后，系统直接说“现在进入实现阶段了”“先从 master 切一个实现分支”，明显已经脱离团队委派闭环
  4. 当前 `skills/team-delegate/SKILL.md` 虽然已经有“方案/计划阶段只给用户两项明确选择”“计划确认”“如无补充请回复‘可以/同意/确认’”等规则，但这次真实失败说明：
     - 方案/计划入口的执行方选择没有稳定落到用户可见输出
     - 计划收口文案没有稳定落到用户可见输出
     - 确认回合没有稳定被识别为“继续已有委派会话”

## 3. 影响范围

### 3.1 受影响功能

- 团队委派流程中的方案/计划执行方选择提示
- 团队委派流程中的方案确认与计划确认用户提示
- 团队委派在审批回合的续接能力
- 计划确认后进入实施入口的业务门禁

### 3.2 受影响用户动作

- 用户在方案阶段或计划阶段前选择“主会话执行 / ACP 委派执行”
- 用户查看方案/计划产出后的下一步判断
- 用户回复 `可以/同意/确认` 等确认类内容
- 用户从计划阶段进入实施阶段的业务推进

### 3.3 受影响状态或数据

- `NEEDS_MAIN_DESIGN`
- `NEEDS_MAIN_PLANNING`
- `WAITING_DESIGN_APPROVAL`
- `WAITING_PLAN_APPROVAL`
- 计划确认后进入实施入口的续接上下文

### 3.4 不受影响范围

- `BridgeService` 内部“实施执行方选择”状态机本身的定义
- ACP 模型选择与实施闭环的后半段规则
- 上一次“插件缓存刷新”修复本身

### 3.5 不修复的交付风险

- 用户无法知道当前是在“需要先选执行方”还是“已经默认由主会话开始做”
- 用户无法知道当前是在“计划确认”而不是“已经允许直接实施”
- 用户回复确认类内容后，流程会随机脱离插件闭环，回到普通开发对话
- 原本一直存在的“方案/计划由谁执行”业务选择在真实入口上等价消失
- “计划确认后先进入实施执行方选择”这条业务规则在真实入口上无法稳定交付
- 同一套插件在不同回合中出现“有时走闭环、有时直接实现”的不确定行为

## 4. 根因分析

### 4.1 直接原因

真实入口当前同时存在两个直接原因：

1. 进入方案或计划阶段时，用户可见提示没有稳定把“主会话执行 / ACP 委派执行”作为必须停住的选择闸门暴露出来。
2. 计划阶段完成后的用户可见提示，没有把“当前处于确认门禁”和“需要回复什么内容才能进入下一阶段”明确说出来，导致用户从界面上看不到这是一个需要确认的闭环节点。

### 4.2 深层原因

这次问题实际上有三层约束没有被作为明确交付契约固定下来：

1. **方案/计划执行方选择契约缺失**
   - 虽然底层状态返回了 `NEEDS_MAIN_DESIGN / NEEDS_MAIN_PLANNING` 与 1/2 选项，但真实入口没有稳定把它呈现成“必须先选执行方”的业务闸门
   - 结果是默认值 `1` 被静默吞掉，用户看起来像是“系统自动决定由主会话执行”

2. **计划收口提示契约缺失**
   - 计划产出完成后的首屏提示，没有被强约束成“阶段说明 + 确认要求 + 确认词示例 + 下一阶段说明”的固定格式
   - 结果是模型可能只汇报“计划写完了”，却不提醒“现在需要确认”

3. **确认回合续接契约缺失**
   - 当上一轮已经处于 `WAITING_PLAN_APPROVAL` 或 `WAITING_DESIGN_APPROVAL` 时，下一轮用户只回复 `可以/同意/确认`，系统没有被明确约束为“优先继续团队委派闭环”
   - 结果是确认类回复被普通主会话当成“用户允许继续开发”，直接回落到默认开发流程

### 4.3 为什么现有测试没有发现

- 现有测试虽然验证了 `skills/team-delegate/SKILL.md` 中的部分规则文本，也验证了状态对象里存在 1/2 选项，但没有覆盖“真实入口必须把方案/计划执行方选择显式暴露给用户”
- 现有测试主要验证“确认词示例”等规则文本，但没有覆盖“计划完成后的真实用户可见输出必须包含这些提示”
- 现有交付验证没有单独覆盖这条多轮真实链路：
  1. 第一轮进入方案或计划阶段时先出现执行方选择
  2. 第一轮产出计划并停在确认
  3. 第二轮用户只回复 `同意`
  4. 系统必须先进入“实施执行方选择”
- 因此出现了“规则写在技能里，但真实回合未稳定执行”的断层

### 4.4 当前已确认事实与未确认假设

#### 已确认事实

1. 进入方案/计划阶段时，真实入口没有稳定停在执行方选择闸门
2. 计划完成后的真实回复没有明确提示确认动作
3. 用户回复 `同意` 后直接进入普通实现流程
4. 这条失败链路发生在真实用户入口，不是单元测试场景

#### 未确认假设

1. 方案阶段与计划阶段是否都以同一种方式吞掉了“执行方选择”闸门
2. 是技能触发描述过窄导致续接失败，还是计划收口文案缺失导致模型没有把回合锚定在“确认节点”
3. 是否需要同时补强技能描述、用户提示模板、执行方选择提示和真实交付测试矩阵

### 4.5 证据链

1. 用户反馈：进入方案与计划阶段前，没有出现“主会话完成 / ACP 完成”的执行方选择
2. 用户截图一：计划阶段完成回复，没有明确确认门禁提示
3. 用户截图二：回复 `同意` 后，直接进入主会话实现流程
4. 当前 `skills/team-delegate/SKILL.md` 已包含“方案/计划两项明确选择”“计划确认”“确认词示例”规则，说明问题不只是规则缺失，更是规则未稳定落到真实回合行为
5. `src/session/bridge-service.ts` 当前仍返回 `NEEDS_MAIN_DESIGN / NEEDS_MAIN_PLANNING`、`default_option=1` 和 `user_options=1/2`，说明底层状态机没删，但真实入口的显式分流没有稳定交付
6. 之前本机单轮验证只能证明“直接从一句话进入实施入口”时可以停在“实施执行方选择”，不能证明“多轮计划确认 -> 确认回复 -> 继续进入实施入口”这条链路稳定通过

## 5. 修复目标与非目标

### 5.1 修复目标

- 进入方案阶段前，必须显式让用户选择“主会话执行（默认）/ ACP 委派执行”
- 进入计划阶段前，必须显式让用户选择“主会话执行（默认）/ ACP 委派执行”
- 计划完成后的用户提示必须明确说明当前处于“计划确认”阶段
- 计划完成后的用户提示必须明确说明“需要你的确认才能进入下一阶段”
- 计划完成后的用户提示必须给出确认词示例：`可以/同意/确认`
- 当上一轮处于 `WAITING_PLAN_APPROVAL` 或 `WAITING_DESIGN_APPROVAL` 时，用户下一轮回复确认类内容，必须优先续接团队委派闭环
- 计划确认后的下一步必须先进入“实施执行方选择”，不能直接进入普通主会话实现流程
- 自动化测试和真实交付测试都要覆盖“执行方选择 + 多轮确认续接”这条失败链路

### 5.2 非目标

- 不改 `NEEDS_MAIN_DESIGN / NEEDS_MAIN_PLANNING / NEEDS_IMPLEMENTATION_EXECUTOR` 的底层状态名
- 不改“实施执行方选择”节点本身的状态定义
- 不改 ACP 模型确认与实施闭环后半段逻辑
- 不把这次问题重新定义为缓存刷新问题
- 不扩展为通用对话记忆框架，只修团队委派入口与确认回合的稳定续接契约

## 6. 修复设计

### 6.1 方案/计划执行方选择契约

进入 `NEEDS_MAIN_DESIGN` 和 `NEEDS_MAIN_PLANNING` 时，用户首屏提示必须明确把它们当成“执行方选择闸门”，至少包含：

1. 当前业务阶段
2. 为什么需要先做这一步
3. 两个明确选项：
   - `1` 主会话执行（默认）
   - `2` ACP 委派执行
4. 两个选项对后续流程的影响

不能只写“按约定由主会话执行”，也不能把默认值 `1` 静默吞掉。

### 6.2 计划/方案确认提示契约

进入 `WAITING_DESIGN_APPROVAL` 和 `WAITING_PLAN_APPROVAL` 时，用户首屏提示必须固定包含四部分：

1. 当前业务阶段
2. 为什么停在这里
3. 用户现在要回复什么
4. 回复后会进入什么下一阶段

其中计划确认提示至少要明确类似语义：

```text
当前计划已经整理完成，正在等待你的确认。
如无补充，请回复“可以 / 同意 / 确认”，我再进入下一阶段。
```

### 6.3 确认回合优先续接契约

当上一轮处于以下业务阶段时：

- 方案确认
- 计划确认
- 实施执行方选择
- 整改确认

下一轮如果用户回复的是明确确认类内容，系统必须优先把它当成“继续已有团队委派闭环”的信号，而不是当成普通主会话开发授权。

### 6.4 技能触发与续接描述补强

需要把 `team-delegate` 技能描述中的“继续已有委派会话”从抽象原则，提升为明确场景：

- 用户在方案/计划执行方选择节点只回复 `1/2`
- 用户在确认节点只回复 `可以/同意/确认`
- 用户在实施执行方选择节点只回复 `1/2`
- 用户在整改确认节点只回复确认类内容

这些都必须视为“继续当前委派任务”，不能脱离插件闭环。

### 6.5 测试护栏

需要增加两类护栏：

1. **技能与文案规则护栏**
   - 方案/计划执行方选择必须显式出现 1/2 两项选择
   - 确认提示必须包含确认动作与确认词示例
   - 技能描述必须覆盖“继续已有委派会话”的确认类回复

2. **多轮真实链路护栏**
   - 第一轮进入方案或计划阶段时，必须先出现执行方选择
   - 第一轮产出计划并停在确认
   - 第二轮用户只回复 `同意`
   - 第三步必须先进入“实施执行方选择”

### 6.6 回退方案

- 若补强后的执行方选择提示或确认提示影响现有文案测试，可先回退提示词修改，但不能回退“执行方选择显式暴露”和“确认回合优先续接委派闭环”的行为约束
- 若发现方案阶段和计划阶段需要分开处理，可拆成两个独立修复点，但当前文档先按统一入口设计

## 9. 交付测试目标

### 9.1 真实入口

1. 安装当前插件
2. 重启或刷新 Codex 使用环境
3. 打开 Codex CLI
4. 使用真实业务语言发起团队委派流程

### 9.2 真实业务语言

第一轮示例：

```text
帮我用团队委派流程处理这个开发任务。
```

第二轮示例：

```text
同意
```

### 9.3 同链路复测步骤

1. 从真实入口发起团队委派流程，检查进入方案或计划阶段前是否先出现执行方选择
2. 验证用户先看到两项明确选择：
   - `1` 主会话执行（默认）
   - `2` ACP 委派执行
3. 继续推进到计划阶段完成
4. 检查计划完成后的用户提示，确认其中明确说明：
   - 当前处于计划确认阶段
   - 需要用户确认才能进入下一阶段
   - 确认词示例是 `可以/同意/确认`
5. 用户在下一轮只回复：`同意`
6. 检查系统是否优先续接团队委派闭环
7. 验证下一步先进入“实施执行方选择”，而不是直接进入主会话实现

### 9.4 通过标准

- 进入方案/计划阶段前，稳定先出现执行方选择
- 计划完成后的提示明确要求用户确认
- 用户回复 `同意` 后，不再直接进入普通实现流程
- 计划确认后的下一步稳定进入“实施执行方选择”
- 同时通过 `docs/团队委派交付测试必过表.md` 中全部测试项

### 9.5 失败后继续整改闭环

- 记录失败截图、用户输入、实际表现、预期表现
- 判断问题属于：
  - 执行方选择缺失
  - 确认提示缺失
  - 技能续接描述不足
  - 工作流续接实现缺口
- 更新设计与计划
- 补红灯测试
- 修复后重新执行同一条真实业务链路

## 10. 风险与回退

- 风险：
  - 只补确认提示，不补执行方选择，仍会让用户失去方案/计划阶段的业务选择权
  - 只补执行方选择，不补续接契约，确认回合仍会继续脱离插件闭环
  - 只测单轮入口，不测多轮确认，仍会漏掉真实故障
- 控制措施：
  - 执行方选择、确认提示和续接契约一起修
  - 自动化测试和真实多轮交付测试一起补
- 回退路径：
  - 如本次实现引入新的误判，可回退到本次修改前版本，但必须保留本次新增的失败链路文档与测试，避免再次丢失上下文

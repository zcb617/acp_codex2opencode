# 最小验证方案设计文档：方案与计划确认节点

## 1. 背景与目标
- 背景：需要对 `team-delegate` 流程做一次最小业务验证，重点检查“方案完成后必须先等待用户确认”的门禁是否有效。
- 目标：
1. 生成可交付的方案文档。
2. 由主会话向用户发起方案确认提示。
3. 在收到用户确认前，流程不得进入计划阶段。

## 2. 非目标
- 不进入计划文档编写。
- 不进入实施阶段。
- 不执行 ACP 实施任务。
- 不做业务功能代码改造。

## 3. 范围与术语
- 范围：本次仅覆盖委派流程中的“方案制定 -> 方案确认等待”链路。
- 术语：
  - 方案确认：用户以“可以/同意/确认/通过/OK”等语义明确批准方案。
  - 确认等待态：方案完成后，系统仅提示确认并停住，等待用户反馈。

## 4. 架构与模块职责
- 主会话：负责生成方案文档、发起确认提示、等待用户反馈。
- 委派状态机：负责阶段判定与流程门禁，确保未确认不进入下一阶段。
- 文档存储：承载本次方案，作为后续计划阶段的唯一来源。

## 5. 技术选型与约束
- 采用现有 `delegate_task_execute(action=start)` 高层入口驱动状态。
- 约束：
1. 方案阶段默认主会话执行，不要求模型选择。
2. 方案文档必须落盘到固定路径。
3. 确认前禁止触发计划阶段动作。

## 6. API 契约
### 6.1 启动流程判定
- 方法：`delegate_task_execute(action=start)`
- 用途：进入方案阶段并返回文档产出要求。

请求示例：
```json
{
  "workspace_path": "D:/zhangcb/my_wiki/coding/acp_codex2opencode",
  "session_alias": "min-verify-design-plan-confirm",
  "action": "start",
  "start_phase": "design",
  "development_type": "feature"
}
```

成功响应示例：
```json
{
  "workflow_status": "NEEDS_MAIN_DESIGN",
  "business_stage": "方案制定",
  "required_output_document": {
    "relative_path": "docs/superpowers/specs/2026-05-16-min-verify-design-plan-confirm-design.md"
  }
}
```

失败响应示例：
```json
{
  "workflow_status": "FAILED",
  "user_message": "流程初始化失败，请检查输入上下文"
}
```

错误码说明：
- `FAILED`：不可继续，需人工排查后重试（不可直接重试）。
- `NEEDS_USER_INPUT`：上下文不足，可补充信息后重试。

## 7. 数据模型
| 字段名 | 类型 | 必填 | 约束/默认 | 字段作用（中文） |
|---|---|---|---|---|
| task_id | string | 是 | 同任务保持一致 | 标识同一业务任务闭环，防止串任务。 |
| session_alias | string | 是 | 本次固定别名 | 便于续接同一任务上下文。 |
| workflow_status | string | 是 | 状态机枚举 | 表示当前流程所处业务状态。 |
| business_stage | string | 是 | 业务语义文本 | 对用户说明当前所处阶段。 |
| required_output_document.relative_path | string | 是 | 由插件返回 | 规定方案文档必须落盘的路径。 |

- 本模型核心职责：约束本次最小验证在正确阶段输出正确文档，并阻止越级推进。

## 8. 主流程与状态机
1. 用户提出最小验证需求。
2. 主会话调用 `start`，进入“方案制定”。
3. 主会话生成方案文档并写入指定路径。
4. 主会话发起确认提示并进入确认等待态。
5. 若用户未确认：保持等待，不进入计划阶段。
6. 若用户确认：才允许进入下一阶段（本次验证不执行）。

## 9. 异常处理策略矩阵
| 异常层级 | 典型场景 | 处理动作 | 是否丢弃记录 | 是否重试 | 记录位置 | 对主流程影响 |
|---|---|---|---|---|---|---|
| 流程级 | `start` 返回失败 | 向用户说明失败并请求补充/重试 | 否 | 是 | 会话日志 | 暂停验证 |
| 文档级 | 方案文档写入失败 | 立即停止并提示修复路径 | 否 | 是 | 本地执行日志 | 无法进入确认 |
| 交互级 | 用户反馈非确认词 | 视为反馈并修订同一文档后再次确认 | 否 | 是 | 会话日志 + 文档历史 | 持续停在确认环节 |

## 10. 幂等与去重规则
- 同一任务使用同一 `task_id/session_alias`。
- 确认前重复催促不触发阶段推进。
- 用户补充意见时，仅增量修订同一路径文档，不创建 v2 文件。

## 11. 测试策略
- 单元层：不新增业务代码，本次不涉及。
- 集成层：验证 `start` 返回 `NEEDS_MAIN_DESIGN` 及产物路径。
- 端到端层：以真实用户语句触发流程，确认提示后停住等待。
- 并发层：同一任务重复触发确认，不得跳过等待门禁。

## 12. 验收标准
1. 方案文档成功生成在指定路径。
2. 用户收到明确的方案确认提示。
3. 在用户确认前，不出现进入计划阶段的动作或提示。
4. 用户若给补充意见，系统要求修订并再次确认。

## 13. 发布与回滚 Runbook
- 发布：本次为流程验证文档任务，无发布动作。
- 回滚：删除或回退本次新增方案文档变更即可恢复。

## 14. SLO 与告警
- 方案阶段响应目标：主会话在一次交互内完成方案生成与确认提示。
- 门禁正确率目标：确认前越级推进率为 0%。
- 告警条件：出现“未确认进入计划阶段”即判定失败。

## 15. 数据保留与清理策略
- 保留：方案文档作为流程审计证据保留在 `docs/superpowers/specs/`。
- 清理：仅在用户明确要求时清理历史验证文档。

## 17. 开发实施规范
- 本次任务仅允许文档变更，不允许代码实现变更。
- 若收到补充意见，只能在同一文档内增量修订受影响段落，必须保持文件路径不变。
- 禁止整篇重写文档；必须保留已确认章节结构与已确认结论，仅更新被反馈影响的段落。
- 禁止新建 `v2`、`新版` 等替代文档覆盖原确认链路；所有修订必须落在当前文件。
- 每次修订后必须再次发起方案确认；用户未给出确认词前，流程不得进入计划阶段。
- 未收到确认前，不得推进到计划阶段。

## 18. 交付测试对齐设计方案
| 设计承诺 | 来源章节 | 项目类型 | 真实入口 | 用例卡 | 证据要求 |
|---|---|---|---|---|---|

### 用例卡 DT-01
- 前置条件：已进入方案制定阶段。
- 操作步骤：
1. 生成方案文档。
2. 向用户发送“请确认方案”的业务提示。
3. 用户暂不确认。
- 预期结果：流程停在方案确认环节，不进入计划阶段。
- 证据：文档文件、确认提示、无下一阶段推进记录。

### 异常流转示例：用户补充而非确认
1. 触发条件：用户回复“请补充 XXX 约束/示例”，未给出“可以/同意/确认”等确认词。
2. 判定结果：该输入判定为“反馈”，不是“确认通过”。
3. 处理动作：
   - 在当前文件内增量修订对应章节；
   - 不重写全文，不创建 `v2` 文档；
   - 修订后再次发送方案确认提示。
4. 状态约束：在用户确认前，流程持续停留在方案确认环节，不进入计划阶段。

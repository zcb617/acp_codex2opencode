# NEEDS_USER_DECISION 超时等待自推进 BUG 修改设计文档

## 1. 问题摘要

团队委派流程在实施阶段进入 `NEEDS_USER_DECISION` 后，当前规则会驱动主会话在同一轮里自行执行倒计时并默认继续等待，导致用户还未完成选择，主会话已继续推进。

这会破坏“先停住等待用户输入，再按超时策略推进”的业务预期，用户感知为“系统自己往下走了”。

修复后应恢复为：先出现二选一并停住等待用户输入；若 60 秒仍未收到用户选择，系统再按默认策略继续等待，但不允许主会话在当前轮通过阻塞命令自推进。

## 2. 失败事实

- 触发入口：Codex CLI 真实入口，使用团队委派流程持续跟进实施任务。
- 用户输入：用户在“继续等待/主会话接手”决策提示后未立即选择。
- 实际表现：主会话在同一轮中执行等待命令并自动调用默认继续，产生“主会话自己往下走了”的现象。
- 预期表现：决策提示出现后主会话应停住等待用户输入；超时默认继续应在后续决策周期触发，不应由同一轮自推进实现。
- 复现频率：稳定复现。
- 证据：用户提供的会话截图，显示决策提示后主会话连续执行 `Start-Sleep -Seconds 60` 并自动继续。

## 3. 影响范围

- 受影响功能：实施阶段无进展决策提示、超时默认继续等待逻辑、用户决策交互体验。
- 受影响用户动作：用户尚未选择时的等待阶段。
- 受影响状态或数据：`NEEDS_USER_DECISION` 阶段的提示语义与默认继续触发时机。
- 不受影响范围：模型选择闸门、设计/计划审批、交付测试与整改状态机主流程。
- 交付风险：用户对流程失去控制感，误判系统忽略用户选择，导致流程可信度下降。

## 4. 根因分析

### 4.1 直接原因

`team-delegate` skill 与 `bridge-service` 的用户可见指引都要求“同一轮提示 + 同一轮倒计时 + 同一轮默认 continue_wait”，从而驱动主会话在当前轮自推进。

### 4.2 深层原因

当前设计把“超时默认策略”与“当前轮交互输出”耦合，缺少“先停住等待选择”的明确边界和可持久化的决策等待窗口语义。

### 4.3 为什么现有测试没有发现

现有自动化测试主要验证状态机字段和计数器逻辑（`allow_timeout_default`、连续默认继续次数），未验证“主会话同轮不得自推进”的业务交互约束。

### 4.4 证据链

1. `skills/team-delegate/SKILL.md` 现有规则明确要求同一轮等待并默认继续。
2. `src/session/bridge-service.ts` 在 `NEEDS_USER_DECISION` 返回文案中要求“立即提示并启动 60 秒倒计时”。
3. 用户实际会话截图出现同轮 `Start-Sleep` + 自动继续，符合上述规则导向。

## 5. 修复目标与非目标

### 5.1 修复目标

- 决策提示后主会话必须先停住等待用户输入，禁止同轮自推进。
- 仍保留 60 秒无人选择默认继续（`timeout_default`）机制。
- 将默认继续触发从“当前轮阻塞等待”改为“决策等待窗口超时后的状态机动作”。
- 保持连续默认继续次数计数、上限和清零规则不变。

### 5.2 非目标

- 不调整 1-2 分钟持续跟进节奏策略。
- 不改变 `continue_wait` / `handoff_to_main` 动作定义。
- 不修改模型选择、设计/计划审批和交付整改主流程。

## 6. 修复设计

### 6.1 状态机与数据快照

在 `TaskWorkflowState` 中增加决策等待窗口字段（首次提示时间、超时时间、最近一次自动默认继续时间），并纳入快照持久化与恢复。

### 6.2 `NEEDS_USER_DECISION` 行为调整

- 进入 `NEEDS_USER_DECISION` 时记录决策等待窗口。
- 返回业务文案改为“先停住等待用户选择”。
- 不再在文案中要求主会话“同一轮立即倒计时并默认继续”。

### 6.3 超时默认继续触发

- 保留 `decision_source=timeout_default` 机制。
- 在后续 `status` 跟进时，如果已超过决策等待窗口且允许默认继续，则由插件状态机自动执行一次等价于 `continue_wait(timeout_default)` 的状态迁移。
- 自动触发后更新计数并记录触发时间。

### 6.4 Skill 规则调整

`team-delegate` 明确禁止使用 `Start-Sleep` 等阻塞命令在当前轮模拟倒计时；改为“先提示并停住，超时默认继续由后续跟进周期触发”。

### 6.5 兼容与回退

- 对历史快照缺失决策窗口字段的情况，按首次进入该状态时初始化窗口。
- 如需回退，可恢复旧文案与 skill 规则，但将重新引入同轮自推进问题。

## 7. 修改范围

- `src/session/bridge-service.ts`：决策等待窗口字段、状态迁移、返回文案与策略字段。
- `skills/team-delegate/SKILL.md`：等待与默认继续规则修订。
- `tests/unit/bridge-service-workflow.test.ts`：新增/调整业务语义断言。
- `tests/delivery/team-delegate-skill.delivery.test.ts`：更新 skill 规则断言。

## 8. 自动化验证目标

- 红灯验证：覆盖“决策提示后同轮自推进”规则不再成立（改为停住等待）。
- 回归验证：`timeout_default` 计数递增、上限限制、用户明确选择清零、ACP 新进展清零等既有规则继续成立。
- 文案验证：`NEEDS_USER_DECISION` 的业务提示从“立即倒计时执行”改为“先停住等待”。

## 9. 交付测试目标

- 真实入口：安装插件并在 Codex CLI 使用自然语言触发团队委派实施链路。
- 真实业务语言：实施无进展后触发用户决策提示，不立即输入选择。
- 同链路复测目标：
  1. 决策提示出现后主会话停住，不在当前轮自行执行倒计时或继续动作。
  2. 60 秒无人选择后，系统按默认策略继续等待（由后续跟进周期触发）。
  3. 用户在超时前明确选择时，按用户选择执行，不触发默认动作。
- 通过标准：无“主会话自己往下走”体验，默认继续仍可用。
- 失败整改：记录失败会话证据，补充状态机/skill 规则并复测同链路。

## 11. 附加根因与修复（2026-05-15 补充）

### 11.1 附加失败事实

在真实入口交付测试中，同一任务 `silence-probe-minimal-change` 出现以下现象：

- 当 `workspace_path` 使用 `D:/...` 时，`status` 能命中历史在途流程；
- 当 `workspace_path` 使用 `D:\\...` 时，返回 `WORKFLOW_NOT_FOUND`。

这会让“60 秒默认继续”链路在一部分入口写法下看似失败，实质是同一工作区路径被识别为不同流程键。

### 11.2 附加根因

`workflow_key` 当前由 `workspacePath + "::" + sessionAlias` 直接拼接生成，未对路径做统一归一化。  
因此 `D:/repo::task` 与 `D:\\repo::task` 会写入/查询不同 key。

### 11.3 修复目标

- 工作流键生成统一使用归一化路径（Windows 下统一分隔符与大小写）。
- 按 `task_id` 恢复、历史清理等 workspace 比较逻辑统一使用归一化路径。
- 对历史旧键（未归一化）提供兼容恢复并迁移到新键，避免老任务断裂。

### 11.4 修改范围（补充）

- `src/session/bridge-service.ts`
  - workflow key 生成归一化
  - 旧键兼容恢复与迁移
  - `findWorkflowByTaskId` / 过期清理按归一化路径比对

### 11.5 交付复测点（补充）

真实入口必须同时覆盖两种路径写法：

1. `workspace_path=D:/...` 能恢复同一任务；
2. `workspace_path=D:\\...` 也能恢复同一任务；
3. 两种写法都不再触发假性 `WORKFLOW_NOT_FOUND`。

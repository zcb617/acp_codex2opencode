# 业务交付闭环设计方案

## 1. 当前业务问题

当前插件把 ACP 实施完成当成业务完成。只要实施阶段返回 `STATUS: DONE`，服务端就会进入 `COMPLETED`。这会导致一个关键断层：没有强制执行真实业务交付测试，也没有在交付测试失败后形成整改方案、整改计划、再次实施、再次测试的闭环。

用户看到的结果可能是“实施完成”，但实际业务可能仍未通过真实入口验证。这不符合当前项目的交付测试定义。

## 2. 现有流程缺口

当前链路实际是：

```text
方案制定 -> 计划制定 -> 计划实施 -> ACP 表示完成 -> COMPLETED
```

缺口：

- 实施完成后没有进入交付测试节点。
- 插件没有要求主会话从真实 Codex CLI 入口跑业务测试。
- 交付测试失败后没有结构化记录失败位置、用户输入、实际表现和预期表现。
- 失败没有生成整改方案和整改实施计划。
- 整改实施后没有强制回到同一条业务交付测试链路。
- 完成 3 次整改后没有明确用户决策分支。

## 3. 本次业务目标

本次新增“业务交付闭环”能力。插件最终完成标准必须从“ACP 实施完成”调整为“真实业务交付测试通过”。

目标链路：

```text
方案制定
-> 计划制定
-> 计划实施
-> 等待业务交付测试
-> 测试通过
-> 完成
```

失败链路：

```text
方案制定
-> 计划制定
-> 计划实施
-> 等待业务交付测试
-> 测试失败
-> 形成失败记录
-> 形成整改方案
-> 形成整改计划
-> 整改实施
-> 再次业务交付测试
-> 直到通过或完成 3 次整改
-> 超过 3 次仍未通过时，由用户选择主会话接手整改或取消后续工作
```

## 4. 非目标

本次不做以下内容：

- 不直接内置某个项目专属测试脚本。
- 不替代主会话执行真实业务测试。
- 不把单元测试、集成测试或字段检查当成交付测试。
- 不取消现有 Design / Planning 审批节点。
- 不改变用户已经确认的模型选择机制。

## 5. 业务状态设计

新增状态：

- `NEEDS_DELIVERY_TEST`：实施或整改实施完成，等待主会话执行真实业务交付测试。
- `DELIVERY_TEST_FAILED`：交付测试失败，等待形成整改方案和整改计划。
- `RUNNING_REMEDIATION`：ACP 正在按整改方案和计划执行整改。
- `NEEDS_REMEDIATION_DECISION`：固定 3 次整改后仍未通过，需要用户选择主会话接手整改或取消后续工作。
- `CANCELLED`：用户选择取消后续工作，插件关闭 ACP 会话，不声明交付完成。

保留状态：

- `RUNNING_IMPLEMENTATION`
- `NEEDS_USER_DECISION`
- `TRANSFERRED_TO_MAIN`
- `COMPLETED`
- `FAILED`

完成条件变更：

- `RUNNING_IMPLEMENTATION` 结束后不得直接进入 `COMPLETED`。
- 只有 `delivery_test_pass` 被确认后，才能进入 `COMPLETED`。

## 6. 用户可见业务动作

新增动作：

- `delivery_test_pass`：主会话已经完成真实业务交付测试，测试通过。
- `delivery_test_fail`：主会话已经完成真实业务交付测试，测试失败，并提交失败材料。
- `remediation_approve`：用户确认整改方案和整改计划后继续实施。
- `handoff_to_main`：固定 3 次整改后仍未通过，用户选择由主会话接手后续整改。
- `cancel_follow_up`：固定 3 次整改后仍未通过，用户选择取消后续工作。

用户可见表达必须是业务语言，例如：

```text
计划实施已经完成，但还不能判定交付完成。现在必须从真实 Codex CLI 入口执行交付测试。
```

```text
交付测试失败，当前不能声明完成。我会先整理失败位置、实际表现和预期表现，再形成整改方案和整改计划。
```

## 7. 失败材料结构

`delivery_test_fail` 必须携带或形成以下信息：

- 失败位置。
- 用户输入。
- 实际表现。
- 预期表现。
- 影响范围。
- 复现步骤。
- 已确认不是交付通过的原因。

如果主会话无法提供这些信息，插件不得进入整改实施，应要求补充失败材料。

## 8. 整改方案与整改计划

交付测试失败后，插件必须先形成整改方案，再形成整改实施计划。

整改方案必须说明：

- 根因假设。
- 需要修改的业务行为。
- 不改变的既有能力。
- 风险与回退。

整改计划必须说明：

- 修改范围。
- 测试范围。
- 重新执行的同一条业务交付测试链路。
- 通过标准。

整改方案和整改计划可以由 ACP 生成，也可以由主会话生成；但进入整改实施前必须对用户可见，并等待确认。

## 9. 状态机规则

1. `RUNNING_IMPLEMENTATION` 完成后，进入 `NEEDS_DELIVERY_TEST`。
2. `NEEDS_DELIVERY_TEST` 只接受 `delivery_test_pass` 或 `delivery_test_fail`。
3. `delivery_test_pass` 后进入 `COMPLETED`。
4. `delivery_test_fail` 后进入 `DELIVERY_TEST_FAILED`，记录失败材料。
5. `DELIVERY_TEST_FAILED` 必须产出整改方案和整改计划。
6. 用户确认整改方案和整改计划后，进入 `RUNNING_REMEDIATION`。
7. `RUNNING_REMEDIATION` 完成后，回到 `NEEDS_DELIVERY_TEST`。
8. 整改次数由插件固定控制为 3 次，不允许由 LLM 或调用方自行决定。
9. 第 1 到第 3 次整改后仍失败时，继续形成整改方案和整改计划，用户确认后进入下一次整改实施。
10. 第 3 次整改后的交付测试仍失败，进入 `NEEDS_REMEDIATION_DECISION`。
11. 用户选择主会话接手整改，进入 `TRANSFERRED_TO_MAIN`；用户选择取消后续工作，进入 `CANCELLED`。

## 11. 自动化验证目标

必须新增自动化测试覆盖：

- 实施完成后不会直接进入 `COMPLETED`。
- 实施完成后进入 `NEEDS_DELIVERY_TEST`。
- `delivery_test_pass` 后才能进入 `COMPLETED`。
- `delivery_test_fail` 后必须进入整改方案和整改计划节点。
- 整改实施完成后必须再次进入 `NEEDS_DELIVERY_TEST`。
- 固定 3 次整改后仍未通过，必须要求用户在“主会话接手整改”和“取消后续工作”之间决策。
- Skill 文案必须明确“实施完成不等于交付完成”。

## 12. 交付测试目标

本次功能的交付测试必须使用本机真实环境和 Codex CLI 真实入口。

真实入口：

```text
安装当前插件 -> 打开 Codex CLI -> 用户用自然语言触发 $team-delegate -> 插件进入计划实施 -> 执行交付测试闭环
```

真实业务语言示例：

```text
$team-delegate 当前已经有方案和计划，直接进入实施。实施完成后必须先跑真实交付测试；如果测试失败，先形成整改方案和整改计划，最多由 ACP 整改 3 次；超过 3 次仍未通过时，由主会话接手整改或取消后续工作。
```

交付测试必须至少覆盖一条失败再通过链路：

1. 首次实施故意留下一个可观察业务缺口。
2. 主会话执行真实业务交付测试并判定失败。
3. 插件记录失败材料。
4. 插件形成整改方案和整改计划。
5. 用户确认整改。
6. ACP 执行整改实施。
7. 主会话重新执行同一条真实业务交付测试。
8. 测试通过后，插件才进入 `COMPLETED`。

通过标准：

- Codex CLI 中自然语言能触发完整闭环。
- 实施完成后不会直接宣布交付完成。
- 测试失败时不会绕过整改方案和整改计划。
- 整改后会重新执行同一条业务交付测试。
- 只有业务交付测试通过后才显示完成。
- 用户可见输出全程业务导向。

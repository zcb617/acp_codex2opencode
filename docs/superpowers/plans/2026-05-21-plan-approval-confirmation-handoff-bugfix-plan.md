# 计划确认提示缺失且确认回合未续接团队委派闭环 BUG 修复计划

## 1. Bug 与设计来源

- Bug 名称：
  - 计划确认提示缺失且确认回合未续接团队委派闭环
- 设计文档：
  - `docs/superpowers/specs/2026-05-21-plan-approval-confirmation-handoff-bugfix-design.md`
- 当前失败链路：
  1. 用户从真实入口推进到计划阶段完成
  2. 计划完成后的回复没有明确说明“当前需要确认”
  3. 用户下一轮只回复 `同意`
  4. 系统没有继续团队委派闭环，而是直接进入普通主会话实现流程
  5. 用户看不到“实施执行方选择”
- 本计划目标：
  - 固化计划/方案确认提示契约
  - 固化确认回合优先续接团队委派闭环的行为契约
  - 用自动化测试和真实多轮交付测试恢复“计划确认 -> 实施执行方选择”链路
- 本计划不处理：
  - 插件缓存刷新
  - 实施执行方选择节点本身的状态定义
  - ACP 实施闭环后半段逻辑

## 3. 实施任务拆分

### Task 01：补齐确认阶段用户提示契约

**业务目标：**

让用户在计划或方案完成后，明确知道当前不是“已经直接开始实施”，而是“正在等待确认”。

**对应设计目标：**

- 计划完成后的提示必须明确进入确认阶段
- 计划完成后的提示必须明确给出确认词示例

**修改范围：**

- `src/session/bridge-service.ts`
- 相关确认阶段提示生成逻辑

**实施步骤：**

1. 定位方案确认和计划确认阶段的用户提示生成位置。
2. 补齐固定提示结构：
   - 当前阶段
   - 为什么停在这里
   - 需要用户回复什么
   - 回复后会进入什么阶段
3. 把确认词示例显式写入提示，至少包含 `可以/同意/确认`。
4. 确保实现入口提示与业务规则一致，不再出现“如果继续就进入实现阶段”这种绕过确认门禁的表达。

**伪代码：**

```text
输入：当前 workflow 处于 WAITING_DESIGN_APPROVAL 或 WAITING_PLAN_APPROVAL
if 进入确认节点:
  user_message = 当前阶段说明
  + 需要确认的原因
  + 如无补充请回复“可以/同意/确认”
  + 确认后进入下一阶段说明
输出：用户可直接理解和执行的确认提示
```

**自动化验证：**

- 确认阶段用户提示断言测试

**交付测试影响：**

- 用户知道下一轮该回复什么，减少误入普通实现流程

**完成标准：**

- 计划与方案确认提示都明确包含确认门禁和确认词示例

### Task 02：修复确认回合的闭环续接行为

**业务目标：**

用户在确认阶段只回复 `同意` 时，系统必须继续当前团队委派任务，而不是回到普通主会话开发流程。

**对应设计目标：**

- 确认回合必须优先续接团队委派闭环
- 计划确认后下一步必须先进入实施执行方选择

**修改范围：**

- `skills/team-delegate/SKILL.md`
- 可能涉及的工作流续接逻辑
- 相关测试文件

**实施步骤：**

1. 补强技能描述，把“继续已有委派会话”的确认类回复场景写成明确规则。
2. 明确当上一轮处于确认节点时，下一轮 `可以/同意/确认` 必须被视为继续当前委派任务。
3. 校验计划确认后的继续路径是否稳定进入“实施执行方选择”。
4. 如实现层存在续接缺口，补齐对应逻辑。

**伪代码：**

```text
输入：上一轮业务阶段 + 当前用户回复
if 上一轮处于 WAITING_PLAN_APPROVAL 或 WAITING_DESIGN_APPROVAL:
  if 当前回复属于确认类内容:
    继续当前委派闭环
    推进到下一业务节点
else:
  按普通入口判定处理
输出：不脱离插件闭环的续接结果
```

**自动化验证：**

- 多轮确认续接测试

**交付测试影响：**

- 用户确认后能稳定看到“实施执行方选择”

**完成标准：**

- 确认类回复不再触发普通主会话实现流程

## 6. 真实业务交付测试计划

### DT-01：计划确认提示复测

**业务目标：**

让用户在计划阶段结束时明确知道现在要做确认，而不是默认直接实施。

**真实环境：**

- 本机真实 Codex CLI
- 当前插件安装版本
- 使用项目要求模型完成真实入口验证

**真实入口：**

1. 安装当前插件
2. 重启或刷新 Codex
3. 打开 Codex CLI
4. 使用自然语言发起团队委派流程并推进到计划阶段完成

**用户语言：**

```text
帮我用团队委派流程完成这个开发任务。
```

**操作步骤：**

1. 让流程走到计划阶段完成
2. 观察计划完成后的首屏提示

**期望用户可见结果：**

- 明确说明当前处于计划确认阶段
- 明确说明需要确认才能进入下一阶段
- 明确给出 `可以/同意/确认` 作为确认词示例

**失败判定：**

- 任一项缺失都判失败

### DT-02：计划确认后回复同意的同链路复测

**业务目标：**

证明确认类回复会继续当前团队委派闭环，而不是进入普通实现流程。

**真实环境：**

- 同 DT-01

**真实入口：**

- 复用 DT-01 已推进到计划确认的真实会话

**用户语言：**

```text
同意
```

**操作步骤：**

1. 在计划确认节点仅回复 `同意`
2. 观察系统下一步业务阶段

**期望用户可见结果：**

- 系统优先继续团队委派闭环
- 下一步先进入“实施执行方选择”
- 不出现“现在进入实现阶段了”“切分支开始实现”等普通主会话实现提示

**失败判定：**

- 直接进入普通实现流程即判失败

### 必过项约束

- 每次交付测试必须同时通过 `docs/团队委派交付测试必过表.md` 的全部测试项；任一项失败即判本次交付测试失败

## 7. 交付测试失败整改与再计划机制

如果 DT-01 或 DT-02 失败，必须执行以下闭环：

1. 记录失败事实：
   - 触发语句
   - 用户看到的原文
   - 预期与实际差异
2. 判断失败属于：
   - 确认提示模板缺失
   - 技能续接描述缺失
   - 工作流实现缺口
3. 更新设计文档和计划文档
4. 补红灯测试
5. 实施修复
6. 重新执行自动化验证
7. 重新执行 DT-01 和 DT-02 同链路复测

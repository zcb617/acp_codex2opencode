## 5. 业务交付场景

### DS-PLAN-01 计划生成后确认停住

- 业务目标：计划产出后先确认，不越级进入实施。
- 前置条件：
1. 已有并确认方案文档：`docs/superpowers/specs/2026-05-16-min-verify-design-plan-confirm-design.md`。
2. 用户当前请求为进入计划制定。
- 输入数据：
1. 用户业务输入：`team-delegate 现在基于已确认方案文档 ... 进入计划制定`。
2. 确认约束：`计划文档生成后必须发确认提示并停住，不进入实施`。
- 操作步骤：
1. 主会话读取已确认方案文档。
2. 生成计划文档并写入目标路径。
3. 主会话向用户发送计划确认提示（示例确认词：`可以/同意/确认`）。
4. 在收到确认前停止推进，不进入实施。
- 期望输出：
1. 计划文档存在且内容完整。
2. 用户可见确认提示已发出。
3. 无实施推进动作。
- 失败处理：
1. 若计划写入失败：记录失败事实并修复写入后重试本场景。
2. 若发生越级推进：立即判定失败，回退到计划确认等待态并修复流程。
- 对应开发任务：Task 01、Task 02、Task 03。

### DS-PLAN-02 用户补充意见后的二次确认

- 业务目标：补充意见触发修订并重新确认，不越级推进。
- 前置条件：DS-PLAN-01 已完成到确认等待态。
- 输入数据：用户提供补充意见（非确认词）。
- 操作步骤：
1. 将用户输入判定为“反馈”而非“确认”。
2. 在同一计划文档内增量修订受影响章节。
3. 再次发送确认提示并继续停在确认等待态。
- 期望输出：
1. 仍为同一路径计划文档。
2. 修订后再次确认。
3. 仍未进入实施。
- 失败处理：若出现新建替代文档或直接推进实施，判定失败并整改。
- 对应开发任务：Task 03。

## 7. 真实业务交付测试计划

### 7.1 真实入口

1. 安装插件。
2. 重启或刷新 Codex 使用环境。
3. 打开 Codex CLI。
4. 使用自然语言触发：
   - `帮我用团队委派流程进入计划制定，计划写完先让我确认，不要进入实施。`

### 7.2 验证步骤

1. 指定已确认方案文档路径。
2. 触发计划制定。
3. 观察是否生成计划文档并发出确认提示。
4. 在不回复确认词情况下观察流程：不得进入实施。
5. 输入补充意见，观察是否修订同一文档并再次确认。

### 7.3 通过标准

1. 计划文档生成成功。
2. 确认提示清晰并要求确认后再推进。
3. 用户未确认前不进入实施。
4. 补充意见触发修订与再次确认。

### 7.4 失败标准

任一情况发生即失败：

1. 计划生成后直接进入实施。
2. 需要内部工具名才能推进流程。
3. 补充意见后未修订、未再次确认，或新建替代文档绕过原链路。

## 8. 失败整改与复测机制

1. 记录失败位置、用户输入、实际表现、预期表现。
2. 在同一路径文档修订对应内容，不重写全文。
3. 重新执行同一条真实业务链路（DS-PLAN-01 / DS-PLAN-02）。
4. 未通过前不得声明完成。

## 9. 技术与职责边界

- 主会话：负责计划文档生成、确认提示、等待与修订。
- 委派状态机：负责确认前不推进实施。
- 文档存储：提供单一事实来源，供后续实施阶段读取。

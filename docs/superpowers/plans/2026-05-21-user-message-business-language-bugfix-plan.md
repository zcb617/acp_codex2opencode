# 团队委派入口用户提示“机器话”BUG修复计划

## 1. Bug 与设计来源

- Bug 名称：团队委派入口用户提示“机器话/内部术语外露”
- 设计文档：`docs/superpowers/specs/2026-05-21-user-message-business-language-bugfix-design.md`
- 当前失败链路：用户从 Codex CLI 用自然语言进入团队委派流程时，首屏提示混入内部术语，用户难以判断当前业务阶段与下一步动作
- 本计划目标：把入口关键提示统一为业务语言，并建立可读性回归测试
- 本计划不处理：委派状态机算法、ACP 执行逻辑、自动跟进策略

## 3. 实施任务拆分

### Task 01：入口阶段用户文案业务化

**业务目标：**
让用户一眼看懂当前阶段与下一步，而不是看到状态机或工具约束。

**对应设计目标：**
四段式业务文案。

**修改范围：**
- `src/session/bridge-service.ts`

**实施步骤：**
1. 定位 `NEEDS_USER_INPUT / NEEDS_MAIN_DESIGN / NEEDS_MAIN_PLANNING / NEEDS_IMPLEMENTATION_EXECUTOR` 的 `user_message`。
2. 把文案改成四段式，避免内部术语直出。
3. 保持 `workflow_status` 与 `next_action_required` 不变，避免行为回归。

**伪代码：**
```text
输入：当前阶段响应对象
读取：business_stage, business_reason, next_business_action
if 当前文案存在内部术语首屏直出:
  替换为四段式业务表达
保持：状态字段与动作字段原样
输出：新的 user_message（用户可直接决策）
```

**自动化验证：**
更新并运行入口相关单测。

**交付测试影响：**
用户在真实入口更容易理解并选择下一步。

**完成标准：**
关键入口状态文案均符合四段式，且状态机测试通过。

### Task 02：工作目录校验报错业务化

**业务目标：**
入口失败时给用户可执行建议，不要求用户理解内部参数名。

**对应设计目标：**
参数受限场景人话提示。

**修改范围：**
- `src/session/bridge-service.ts`

**实施步骤：**
1. 调整 `validateWorkspace` 报错文案。
2. 用“当前无法开始任务 + 需要提供可用项目目录”替代“字段名为空/不在白名单”。
3. 确保错误码与可重试语义不变。

**伪代码：**
```text
输入：workspace_path
if 空值:
  抛出业务可读错误（缺少项目目录）
if 不在允许范围:
  抛出业务可读错误（目录不可用，需切换到允许目录）
输出：一致的错误码 + 更易懂错误信息
```

**自动化验证：**
新增错误文案断言测试。

**交付测试影响：**
入口失败时用户能立即知道怎么做，而不是被技术字段阻断。

**完成标准：**
入口受限场景消息可读且可执行。

### Task 03：团队委派技能输出规则补强

**业务目标：**
防止模型在异常场景输出“工具层解释文案”。

**对应设计目标：**
技能模板化约束。

**修改范围：**
- `skills/team-delegate/SKILL.md`

**实施步骤：**
1. 增加入口异常的人话模板。
2. 明确禁止把内部参数名、工具名、状态枚举作为首屏主表达。
3. 保留调试场景下可补充内部信息的例外规则。

**伪代码：**
```text
输入：入口异常场景
先输出：当前阶段 + 原因 + 用户选择 + 影响
if 需要补充技术信息:
  放到业务说明之后并加中文解释
禁止：首屏直接暴露参数名或工具名
输出：统一的业务导向话术
```

**自动化验证：**
文档关键规则检查与单测联动。

**交付测试影响：**
CLI 对话中的解释风格稳定为“人话版”。

**完成标准：**
技能规则明确可执行，且不与现有流程规则冲突。

### Task 04：测试与回归护栏

**业务目标：**
防止后续回退到“机器话”。

**对应设计目标：**
防回归断言。

**修改范围：**
- `tests/unit/bridge-service-workflow.test.ts`

**实施步骤：**
1. 为关键入口状态增加文案断言。
2. 增加“禁止内部术语首屏直出”断言（重点检查 `workspace_path` 等）。
3. 保留原有业务关键词断言，确保行为不变。

**伪代码：**
```text
执行：start 进入关键入口状态
读取：data.user_message
assert 包含业务阶段表达
assert 包含用户下一步动作
assert 不包含内部参数名首屏主提示
输出：通过/失败
```

**自动化验证：**
运行目标单测文件并确认全部通过。

**交付测试影响：**
确保真实对话输出长期保持可读。

**完成标准：**
新增断言稳定通过，且不破坏既有测试。

## 6. 真实业务交付测试计划

### DT-01 入口阶段可读性复测

- 业务目标：用户能在入口阶段直接理解当前状态与下一步。
- 真实环境：本机 Codex CLI + 当前插件安装版本。
- 真实入口：插件安装 -> 刷新环境 -> Codex CLI 自然语言触发团队委派。
- 用户语言：

```text
帮我用团队委派流程处理这个任务，先告诉我现在该做什么。
```

- 预期结果：首屏提示包含阶段、原因、选择、影响，不出现内部术语主提示。

### DT-02 入口受限场景可恢复性复测

- 业务目标：入口无法继续时，用户能得到可执行动作。
- 用户语言：

```text
现在不能直接进入实施的话，请告诉我我该怎么处理。
```

- 预期结果：提示明确“为什么不能继续”和“下一步怎么做”，不把参数名当主表达。

### DT-03 实施执行方选择可读性复测

- 业务目标：用户看懂“主会话实施 vs ACP 实施”的业务差异。
- 用户语言：

```text
设计和计划都确认后，下一步让我选择谁来实施时，请用人话说明差别。
```

- 预期结果：用户能直接理解两个选项影响，不需要理解内部实现。

### 必过项

- 每次交付测试必须同时通过 `docs/团队委派交付测试必过表.md` 的全部项目；任一失败即判定交付测试失败。

## 7. 交付测试失败整改记录机制

- 记录失败事实：触发语句、首屏输出、预期与实际差异。
- 归因：是文案模板问题、技能约束缺口，还是状态分支遗漏。
- 整改：补设计/补计划 -> 改代码 -> 补测试。
- 再验证：重复自动化验证与同链路 DT-01~DT-03。

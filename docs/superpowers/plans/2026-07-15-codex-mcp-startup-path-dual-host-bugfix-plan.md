# Codex MCP 启动路径与双宿主安装修复计划

## 1. Bug 与设计来源

- Bug 名称：Codex 插件安装后 MCP 启动失败与重复登记。
- 设计文档：`docs/superpowers/specs/2026-07-15-codex-mcp-startup-path-dual-host-bugfix-design.md`。
- 当前失败链路：用户本地安装插件后，从非插件目录打开真实 Codex CLI；内置 MCP 的相对入口没有插件工作目录，且安装器额外登记第二个全局 MCP 服务，最终出现启动失败。
- 本计划目标：让 Codex 插件以缓存根目录启动唯一的内置 MCP，并以标准插件命令完成安装、升级和卸载。
- 本计划不处理：Claude Code 的独立安装机制、共享 ACP 业务代码、工作流状态机、OpenCode 模型与模型配置。
- 双宿主约束：`.claude-plugin/`、`mcp-servers.json`、`scripts/install-claude.mjs` 与 `scripts/uninstall-claude.mjs` 不做业务性改动。

## 3. 实施任务拆分

### Task 01：先建立 MCP 启动与安装生命周期的红灯测试

**业务目标：** 让“插件装好了但不能启动”的失败在自动化阶段被阻止，避免再次靠用户现场发现。

**对应设计目标：** 工作目录、单一 MCP、回归测试覆盖。

**修改范围：** `tests/plugin/install.plugin.test.ts`，必要时新增同目录的安装契约测试。

**实施步骤：**

1. 解析 `.mcp.json` 的委派服务配置。
2. 断言相对入口同时声明 `cwd: "."`。
3. 读取 Codex 安装与卸载脚本，断言不再拼接 `[mcp_servers.acp_codex2opencode_plugin]`。
4. 断言安装脚本使用 `codex plugin add`，卸载脚本使用 `codex plugin remove`，并对旧全局服务做迁移清理。
5. 断言安装器只删除与项目技能内容完全一致的旧版全局副本；若同名内容不同，则必须报错而不是删除。
6. 保留 Claude 文件存在与名称契约，防止修复越界。

**伪代码：**

```text
输入：插件清单、MCP 配置、Codex 安装脚本、Claude 专属文件
读取委派 MCP 服务配置
if cwd 不是 ".":
  断言失败，提示相对入口没有插件工作目录
读取安装脚本并检查是否构造全局 mcp_servers 表
if 发现手工全局服务或缺少 plugin add/remove:
  断言失败，阻止进入修复实现
输出：覆盖根因的红灯测试结果
```

**自动化验证：** 在尚未修改生产文件前执行 `npm run test:plugin-install`，新增断言必须失败。

**交付测试影响：** UT-01 和 UT-02 是真实 CLI 安装复测的前置门禁，不能替代 DT-01。

**完成标准：** 当前代码因缺少 `cwd` 和手工全局 MCP 注入而红灯；失败信息能明确对应真实根因。

### Task 02：修复 Codex MCP 工作目录与安装/卸载链路

**业务目标：** 用户只需按标准方式安装插件，在任何项目工作目录打开 Codex 都能使用团队委派能力。

**对应设计目标：** 单一插件 MCP、旧版残留清理、双宿主边界。

**修改范围：** `.mcp.json`、`scripts/install-local.mjs`、`scripts/uninstall-local.mjs`。

**实施步骤：**

1. 为 `acp-codex2opencode` 配置 `cwd: "."`。
2. 删除安装器直接读写 `~/.codex/config.toml` 的实现和手工 `mcp_servers` 生成逻辑。
3. 安装前通过 CLI 移除旧版本插件，并清理旧版 `acp_codex2opencode_plugin` 全局 MCP 条目。
4. 注册本地 Marketplace 后，调用 `codex plugin add acp-codex2opencode@acp-local` 安装并启用插件。
5. 插件安装成功后，只删除 `SKILL.md` 与本项目资源完全一致的旧版全局同名技能目录；内容不同则中止安装，避免用户自定义技能继续遮蔽插件缓存或被误删。
6. 卸载时调用 `codex plugin remove`，清理旧版全局 MCP 残留和本安装器创建的 Marketplace，不删除 Claude 配置或用户自定义全局技能。

**伪代码：**

```text
输入：本地插件源码与当前 Codex 安装状态
构建插件并验证 .mcp.json 的 cwd 指向插件根目录
尝试移除旧插件和旧全局 MCP 条目，不存在时继续
生成并注册本地 Marketplace
调用 Codex 插件安装命令安装唯一的插件实例
检查同名全局技能是否是旧安装器原样副本
if 是原样副本:
  移除该副本，让 Codex 从插件缓存加载技能
if 内容不同:
  报错并保留用户文件，禁止宣告安装完成
if 安装或验证失败:
  返回失败并禁止输出安装完成
输出：由插件清单管理的单一 MCP 服务
```

**自动化验证：** UT-01 至 UT-04、UT-06、`npm run typecheck`、`npm run prepare:plugin`。

**交付测试影响：** DT-01 将从非插件工作树启动真实 Codex CLI，确认相对入口不再漂移。

**完成标准：** `codex mcp list` 不再显示旧全局服务；插件服务的 `cwd` 解析为已安装缓存根目录；缓存 MCP 标准握手成功。

### Task 03：同步用户安装说明、缓存更新与双宿主边界检查

**业务目标：** 用户能用同一条清晰流程完成安装、重新安装、验证和回退，不会再把全局 MCP 配置当作必需步骤。

**对应设计目标：** 安装说明、回退、Claude 兼容。

**修改范围：** `README.md`、`docs/superpowers/runbooks/plugin-local-install.md`、安装契约测试；Codex 清单版本的本地缓存标识。

**实施步骤：**

1. 删除“全局 MCP 兜底配置”的用户说明，替换为插件自身负责 MCP 生命周期的业务说明。
2. 记录单一服务的验证标准：插件已启用、MCP 工作目录已解析、真实 CLI 不报启动错误。
3. 明确升级前清理旧版全局服务是迁移动作，不是正常运行配置。
4. 说明旧版全局同名技能若与本项目资源一致会在升级时迁移，内容不同的用户自定义目录不会被删除。
5. 按插件更新规范为 `.codex-plugin/plugin.json` 写入一次性 `+codex.<cachebuster>`，用于本地重新安装后加载新文件。
6. 校验 Codex 版本基础号与 `package.json` 基础版本一致；Claude 版本、清单和 MCP 配置不被修改。

**伪代码：**

```text
输入：更新后的 Codex 插件文件与现有用户安装说明
更新安装说明为标准 Marketplace -> plugin add 流程
if 文档仍声明手工全局 MCP 为正常步骤:
  失败并回到文档修订
运行 cachebuster 工具更新 Codex 插件清单版本
检查 Claude 专属文件没有进入变更列表
输出：可执行的双宿主安全安装与回退说明
```

**自动化验证：** 文档契约测试、`plugin-creator` 校验、`codex plugin list`。

**交付测试影响：** 用户在新任务中按真实业务语言使用插件，安装说明不暴露内部实现配置作为主操作。

**完成标准：** 文档不再要求用户写入全局 MCP 配置；本地更新后新任务加载的是新插件版本；Claude 专属文件无功能回归。

## 4. TDD 与红灯测试计划

## 6. 真实业务交付测试计划

### DT-01：安装后从真实 Codex CLI 进入团队委派

**业务目标：** 用户安装后可以直接开始团队委派，不遭遇 MCP 启动错误。

**真实环境：** 本机真实 Windows、`gpt-5.3-Codex`、可丢弃 Git worktree；插件源始终为本项目，worktree 仅作为插件要处理的测试工程。

**真实入口：** 安装当前插件，重启或新建真实 Codex CLI 任务，在 worktree 根目录发起自然语言请求。

**用户语言：**

```text
帮我用团队委派流程完成这个开发任务。先根据当前工程的实际情况制定方案和计划，确认后再实施。
```

**操作步骤：**

1. 创建并核对可丢弃 worktree，构造一个真实、可修复的小任务，不污染主工程。
2. 运行更新后的本地安装入口，确认插件显示为已安装启用。
3. 用 `codex mcp list` 记录本插件只保留一个服务，且其工作目录已解析到缓存插件根目录。
4. 从 worktree 启动真实 Codex CLI，以以上用户语言发起任务。
5. 观察 MCP 加载和业务阶段提示；不调用内部 MCP 工具、不用开发者语言绕过流程。

**期望用户可见结果：** 系统能理解“团队委派”业务目标并推进到正常的方案/计划阶段；不显示 `MCP startup failed`。

**辅助证据：** CLI 输出、`codex plugin list`、`codex mcp get acp-codex2opencode`、缓存工作目录与握手检查。

**通过标准：** 用户不需要手工修路径、再登记全局 MCP 或重新触发工具，即可进入团队委派业务流程。

**失败判定：** 出现任意 MCP 启动错误、同一服务重复登记、或用户自然语言无法触发团队委派。

**失败后整改：** 将真实输出记录到第 7 节，补充根因测试和修复任务后重新安装、重新从同一 worktree 复测。

## 7. 交付测试失败整改记录

### Round 1

**失败场景：** 按项目约定用 `gpt-5.3-Codex` 从真实 Codex CLI 进入非插件目录验证。
**用户输入：** `只确认当前会话中的工具均已准备就绪；不要调用任何工具，不要修改文件。`
**实际表现：** 当前 ChatGPT 登录方式返回“该模型不受支持”，任务在模型启动前失败。
**预期表现：** 使用指定模型进入真实 CLI 后继续完成 worktree 团队委派验收。
**证据：** CLI 返回 HTTP 400，明确说明 `gpt-5.3-Codex` 不受当前 ChatGPT account 支持；未出现 MCP startup failed。
**根因判断：** 外部账户/模型可用性限制，不是本插件、路径配置或共享 MCP 运行核心错误。
**新增任务：** 用当前可用默认模型补做同一 MCP 启动复测，但不能把该补测记为指定模型交付测试通过。
**新增验证：** 真实 CLI 默认模型从非插件目录启动，确认无 MCP startup failed。
**复测结果：** 已完成；CLI 正常完成只读请求，未出现 MCP 启动错误。

### Round 2

**失败场景：** 在可丢弃 worktree 中用自然语言发起团队委派。
**用户输入：** 请求处理“Codex 插件安装后 MCP startup failed”的 Bug，并要求从方案制定开始。
**实际表现：** MCP 已正常加载，但 Codex 读取了 `C:\Users\zhang\.codex\skills\team-delegate\SKILL.md`，而非插件缓存中的同名技能。
**预期表现：** Codex 从刚安装插件的 cache 加载 `team-delegate`，不受旧版全局副本遮蔽。
**证据：** 全局 `team-delegate/SKILL.md` 与仓库资源 SHA-256 完全一致；旧版安装器历史实现明确把该目录复制到全局技能目录。
**根因判断：** 旧版 Codex 安装器的全局技能复制残留；新安装器此前没有迁移该残留。
**新增任务：** 实施仅针对内容完全一致副本的安全迁移，并补充 UT-06 与安装说明。
**新增验证：** 重装后从同一 worktree 自然语言入口确认读取插件 cache 的同名技能。
**复测结果：** 已完成最终重装复测。真实 CLI 明确读取 `C:\Users\zhang\.codex\plugins\cache\acp-local\acp-codex2opencode\0.2.0+codex.20260715041821\skills\team-delegate\SKILL.md`；旧全局路径不存在。`codex mcp list` 只保留一个本插件服务且 `cwd` 指向同一缓存版本，标准 MCP 握手返回 `MCP_HANDSHAKE_OK`。当前可用默认模型能以业务语言给出“修复方案制定”入口判断，未出现 MCP startup failed。严格指定模型与 DT-01 至 DT-13 全量验收仍受 Round 1 的账户模型限制而未通过。

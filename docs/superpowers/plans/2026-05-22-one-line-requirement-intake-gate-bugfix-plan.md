# 团队委派一句话需求误入方案阶段 BUG 修复计划

## 1. Bug 与设计来源

- Bug 名称：团队委派一句话需求误入方案阶段
- 设计文档：`docs/superpowers/specs/2026-05-22-one-line-requirement-intake-gate-bugfix-design.md`
- 当前失败链路：用户从 Codex CLI 输入一句话新增需求后，系统直接进入方案制定，没有先做任务定位，也没有先判断是否需要需求深挖
- 本计划目标：把入口判定改为“先定位、再判断是否深挖、最后才允许进入方案”，并补足自动化与真实交付验证
- 本计划不处理：状态机枚举、实施阶段自动跟进机制、交付测试闭环主流程

## 3. 实施任务拆分

### Task 01：更新团队委派技能入口规则

**业务目标：**
让一句话需求在首轮就先做正确分流，而不是靠后续方案阶段兜底。

**对应设计目标：**
入口“先定位、再判深挖”的硬规则。

**修改范围：**
- `skills/team-delegate/SKILL.md`

**实施步骤：**
1. 在 `NEEDS_USER_INPUT` 规则中补充“纯一句话新增需求”的硬条件。
2. 写清入口先做任务定位，再判断是否进入需求深挖。
3. 写清信息不足时不得直接进入 `design`。

**伪代码：**
```text
输入：用户自然语言需求
先判断：这是现有功能升级还是新功能开发
if 连任务定位都不稳定:
  进入上下文补充
else if 只有一句话且缺少边界/验收/约束/优先级:
  进入上下文补充或询问是否需求深挖
else:
  允许继续判定是否进入 design/planning/implementation
输出：入口阶段业务分流规则
```

**自动化验证：**
技能规则文本测试、安装产物测试。

**交付测试影响：**
真实入口不再把信息不足的需求直接推入方案阶段。

**完成标准：**
技能文档明确出现新规则，且规则语义与现有流程不冲突。

### Task 02：补一句话需求拦截与文案规则断言

**业务目标：**
防止一句话需求再次直接掉进方案阶段。

**对应设计目标：**
纯一句话新增需求不得直接进方案。

**修改范围：**
- `tests/plugin/install.plugin.test.ts`
- `tests/delivery/team-delegate-skill.delivery.test.ts`

**实施步骤：**
1. 增加针对一句话需求的规则断言。
2. 断言技能文档包含“不得直接进入方案”的限制。
3. 保留现有需求深挖门禁测试，避免行为回归。

**伪代码：**
```text
读取：团队委派技能文本
assert 包含“一句话新增需求”规则
assert 包含“不得直接进入 design/方案阶段”规则
执行：既有 need_user_input 门禁测试
assert 仍然通过
输出：规则存在且门禁未回退
```

**自动化验证：**
目标测试文件精准回归。

**交付测试影响：**
用户看到的入口判断会先收口，不再直接起方案。

**完成标准：**
相关断言通过，且既有门禁测试保持通过。

### Task 03：前移轻量任务定位约束

**业务目标：**
进入方案前必须先知道是在改老功能还是做新功能。

**对应设计目标：**
进入方案前明确区分现有功能升级/新功能开发。

**修改范围：**
- `skills/team-delegate/SKILL.md`

**实施步骤：**
1. 在入口阶段显式增加任务定位步骤。
2. 对现有功能升级补“先找代码证据”的要求。
3. 对新功能开发补“最小业务信息不全先补信息”的要求。

**伪代码：**
```text
输入：用户需求
if 可确认是现有功能升级:
  先找现有代码证据
  if 范围说不清:
    回到补充上下文
else if 可确认是新功能开发:
  检查最小业务信息是否齐全
  if 不齐全:
    回到补充上下文或需求深挖
else:
  回到补充上下文
输出：允许或禁止进入方案阶段
```

**自动化验证：**
规则文本断言 + 现有流程测试回归。

**交付测试影响：**
用户会先看到定位逻辑，而不是直接进入写方案。

**完成标准：**
技能文档已明确任务定位顺序，相关测试通过。

### Task 04：补安装测试与交付测试护栏

**业务目标：**
确保插件安装后的实际技能内容与交付验证都包含新规则。

**对应设计目标：**
防止安装产物与交付级规则回退。

**修改范围：**
- `tests/plugin/install.plugin.test.ts`
- `tests/delivery/team-delegate-skill.delivery.test.ts`

**实施步骤：**
1. 增加安装产物断言，检查技能文件包含新入口规则。
2. 增加交付级技能测试断言，检查一句话需求分流规则被打包。
3. 保持断言和真实入口文案一致。

**伪代码：**
```text
安装或读取打包后的插件技能文件
assert 包含“先定位”
assert 包含“纯一句话新增需求不得直接进方案”
assert 包含“先补最小业务信息或进入需求深挖”
输出：安装产物与交付级规则一致
```

**自动化验证：**
插件安装测试与交付测试文件。

**交付测试影响：**
真实安装后的插件仍会遵守新入口规则。

**完成标准：**
安装测试与交付级测试全部通过。

## 6. 真实业务交付测试计划

### DT-01 一句话新增需求入口复测

- 业务目标：一句话需求不再直接进入方案阶段。
- 真实入口：安装插件 -> 刷新环境 -> 打开 Codex CLI -> 输入自然语言一句话需求。
- 用户语言：

```text
帮我用团队委派流程做一个新功能：增加截图翻译和当前选中行翻译。
```

- 预期结果：先做任务定位，再判断是否需要补充边界、成功标准、约束、优先级，或询问是否进入需求深挖；不得直接说“开始做方案”。

### DT-02 现有功能升级定位复测

- 业务目标：已有功能升级场景先收集代码证据，而不是直接写方案。
- 用户语言：

```text
帮我用团队委派流程优化现有的插件安装提示，让用户更容易看懂。
```

- 预期结果：系统先判断这是现有功能升级，并要求先定位现有代码路径或补充范围；如果证据不足，先补充上下文。

### DT-03 安装后技能规则生效复测

- 业务目标：真实安装后的插件仍然带着新规则。
- 操作方式：完成安装后从真实 CLI 重新触发 DT-01 场景。
- 预期结果：安装后首屏行为与新规则一致，没有回退到旧逻辑。

### 必过项

- 每次交付测试必须同时通过 `docs/团队委派交付测试必过表.md` 全部项目；任一失败即判交付测试失败。

## 7. 交付测试失败整改记录机制

- 记录失败事实：用户语句、首屏回复、进入阶段、预期阶段。
- 判断归属：入口技能规则缺失、测试护栏缺失，还是安装产物未同步。
- 整改动作：补设计/补计划 -> 修规则 -> 补测试 -> 重新跑自动化验证 -> 重新执行 DT-01~DT-03。

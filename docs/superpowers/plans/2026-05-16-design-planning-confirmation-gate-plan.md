# 设计与计划确认闸门改造计划（2026-05-16）

## 1. 目标与范围

### 1.1 业务目标

在团队委派流程中，方案阶段和计划阶段都必须先经历“用户确认”再进入下一阶段；若用户补充信息，则修订文档并重新确认，直到用户明确确认。

### 1.2 本次范围

1. 更新 `skills/team-delegate/SKILL.md`，新增主会话方案/计划确认闭环规则。
2. 更新 `skills/team-delegate/SKILL.md`，明确确认类输入与补充类输入的判定逻辑。
3. 更新 `tests/delivery/team-delegate-skill.delivery.test.ts`，新增确认闭环断言，防止规则回退。

### 1.3 非目标

1. 不修改 ACP 低层会话 API。
2. 不新增插件内部状态枚举或数据库结构。
3. 不改动实施阶段的持续跟进节奏逻辑。

## 2. 实施任务拆分

### Task 01：补充技能规则

1. 在 `NEEDS_MAIN_DESIGN / NEEDS_MAIN_PLANNING` 中加入“文档生成后先确认”的硬约束。
2. 加入确认提示模板（包含“可以/同意/确认”示例）。
3. 加入确认类/补充类判定规则与“补充->修订->重新确认”闭环规则。

完成标准：技能文档明确写出上述规则，且可被测试断言覆盖。

### Task 02：补充交付测试断言

1. 新增测试用例，断言技能文档包含方案确认、计划确认、确认词、补充重修和重复确认关键语义。

完成标准：新增用例通过，且不会破坏现有用例。

## 3. 自动化验证计划

1. 执行：`npm run test -- tests/delivery/team-delegate-skill.delivery.test.ts`
2. 判定：全部用例通过。

## 4. 真实业务交付测试目标

从 Codex CLI 真实入口使用自然语言执行以下链路：

1. 触发团队委派流程进入方案制定。
2. 方案文档生成后，主会话提示“请审核，回复可以/同意/确认或补充意见”。
3. 用户先给补充意见，主会话修订方案并再次发起确认。
4. 用户确认后进入计划制定。
5. 计划文档生成后重复同样确认闭环。
6. 用户确认后才进入计划实施阶段。

通过标准：任一阶段在未确认前都不会推进；补充意见会触发文档修订并重新确认。

## 5. 失败整改与复测机制

1. 若交付测试发现流程提前推进或漏掉确认，记录失败输入、实际表现、预期表现。
2. 回到技能规则修订并补充测试断言。
3. 重新执行自动化测试与同一条真实业务链路复测。

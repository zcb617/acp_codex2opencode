# 可交付开发计划编写指南

## 1. 编写目标

开发计划不是单纯的任务拆解，也不是单独的验收清单。

开发计划必须保存为 Markdown 文档文件，默认路径为 `docs/superpowers/plans/<YYYY-MM-DD>-<session_alias>-plan.md`；禁止只在对话中输出一段计划文字。

开发计划必须基于已经确认的设计方案展开。若设计方案由主会话生成，计划阶段必须读取对应的设计文档文件路径；若设计方案由用户直接提供，计划阶段必须以用户提供的方案正文为依据。计划文档必须写明方案来源，不能脱离方案另写一套计划。

一份完整的开发计划必须同时回答两个问题：

1. 要开发什么，怎么开发，改哪些文件，如何分阶段完成。
2. 开发完成后，业务上如何证明它真的可用。

因此，完整开发计划的定义是：

> 完整开发计划 = 开发实施计划 + 业务交付验收计划 + 失败修复与复测机制

开发只是把功能做出来，交付验收才证明功能能被真实使用。计划中必须把这两部分合在一起，允许分章节表达，但不能拆成互不关联的两份文档。

## 2. 核心原则

### 2.1 业务优先

计划必须从业务使用链路出发，而不是从内部模块出发。

例如服务端样本版本发布与分发功能，不能只写：

- 实现上传接口
- 实现清洗逻辑
- 实现版本发布
- 实现下载接口

还必须写清楚业务如何验证：

- 客户端如何上传样本数据。
- 服务端如何接收、落库、清洗、统计。
- 如何生成候选版本。
- 如何发布正式版本。
- 客户端如何拉取清单、下载补丁包、校验签名。
- 客户端如何回放补丁、验证样本版本已更新。
- 异常时如何回滚和复测。

### 2.2 开发内容不能缺失

业务导向不等于只写验收场景。计划仍然必须保留完整开发内容，包括：

- 模块边界。
- 数据结构。
- API 合约。
- 文件变更清单。
- 核心函数签名。
- 任务拆分。
- 测试文件。
- 验证命令。
- 预期失败与预期通过标准。

验收标准是在开发计划基础上补充，而不是替换开发计划。

### 2.3 交付测试是最终完成标准

单元测试、集成测试、编译通过只能证明局部正确。最终完成标准必须是业务交付测试通过。

交付测试不是功能测试、代码测试、自测，也不是验证内部函数或工具调用。交付测试是站在最终使用者视角，从真实入口开始，使用真实业务语言、真实操作路径和真实环境，把完整业务链路跑一遍，确认交付物可以直接使用。

“可以直接使用”的含义是：最终使用者能够按照设计目标完成业务，过程中没有卡壳、绕路、额外解释、内部操作依赖或设计以外的现象。

例如：

- 涉及安装的交付物，要从安装、配置、启动开始验证。
- 涉及用户操作的交付物，要验证点击、输入、拖拽、快捷键、文件选择等真实操作可用。
- 涉及数据处理的交付物，要验证输入、处理、输出、持久化、回滚和重复执行的一致性。
- 涉及系统间协作的交付物，要验证上游输入、中间处理、下游消费和异常恢复的完整链路。

不能只因为代码实现完成、界面好看、接口返回 200、自动化测试通过，就判定功能已交付。自动化测试只有在完整模拟真实入口、真实业务路径和真实业务目标时，才可以作为交付测试的一部分。

### 2.4 失败必须闭环

计划必须规定：

1. 自测失败时不能结束任务。
2. 必须记录失败场景、输入、期望结果、实际结果、根因分析和修复方案。
3. 修复代码后必须重新执行同一套业务交付测试。
4. 只有业务交付测试通过后，才允许声明完成。

## 3. 必须包含的文档结构

推荐开发计划使用以下结构。

### 3.1 项目与目标

写清楚本计划解决什么业务问题。

必须包含：

- 功能名称。
- 业务目标。
- 使用对象。
- 当前痛点。
- 交付后应达到的效果。
- 不做什么。

示例：

```markdown
## 模板章节（1）项目与目标

本计划实现服务端样本版本发布与分发能力，目标是让客户端可以上传样本数据，服务端完成清洗、统计、候选版本生成、正式发布和增量包分发，客户端能够拉取并应用更新包。

本计划不处理客户端 UI 改版，不处理人工运营后台的复杂权限体系。
```

### 3.2 硬约束

写清楚执行计划时必须遵守的限制。

本项目至少应包含：

- 文档必须使用中文。
- 开发或修改代码前必须先汇报方案并获得用户批准。
- 开发代码必须新建分支。
- 禁止使用 `git worktree`。
- 未经用户授权禁止执行 `git push`。
- 用户未要求打包时不得自行打包。
- 开发完成后必须编译。
- 不允许让用户看日志代替自己分析日志。

### 3.3 范围与非范围

范围说明本次要交付什么，非范围说明本次明确不做什么。

写法要求：

- 范围必须可验证。
- 非范围不能隐藏必要工作。
- 每个范围项后续必须能映射到开发任务和验收场景。

模板：

```markdown
## 模板章节（2）范围

### 2.1 本次交付

- 客户端样本上传接口。
- 服务端样本清洗与统计。
- 候选版本生成。
- 正式版本发布。
- 客户端版本清单查询。
- 增量包下载与校验。
- 失败回滚与重试。

### 2.2 本次不交付

- 多租户计费。
- 复杂运营审批流。
```

### 3.4 业务交付定义

这是计划中最重要的部分之一。必须写清楚什么叫“可以交付”。

示例：

```markdown
## 模板章节（3）交付完成定义

只有同时满足以下条件，才能判定交付完成：

- 客户端上传样本数据成功。
- 服务端生成可发布版本。
- 客户端能够获取版本清单。
- 客户端能够下载更新包。
- 客户端能够校验并应用更新包。
- 重复执行不会产生错误版本。
- 异常输入不会污染正式版本。
- 真实业务交付测试通过。
- 自动化测试作为辅助验证全部通过。
```

### 3.5 业务交付场景

业务交付场景必须用真实用户或客户端操作来写，不要只写内部函数。

真实入口包括但不限于：安装、配置、启动、登录、导入数据、打开页面、输入自然语言需求、点击按钮、执行客户端命令、连接外部系统。只要最终使用者在真实业务中必须经过，就属于交付测试范围，不能为了测试方便跳过。

场景步骤必须使用业务语言表达，而不是内部实现语言。不要把“调用某个内部函数”“检查某个内部字段”“直接触发某个内部工具”写成交付步骤。真实用户不会这样使用交付物。

交付场景必须从设计方案倒推。计划中的每个交付测试用例都要引用设计文档里的具体承诺、章节或矩阵项，包括设计目标、业务流程、UI/交互契约、API 契约、状态机、数据模型、配置项、权限规则、异常处理矩阵、验收标准和需求到验收映射。设计中承诺的行为必须进入交付矩阵；测试中出现但设计中没有定义的行为，必须先补设计或删除该测试。

项目类型只决定执行入口和证据形态，不能替代设计对齐：

- 服务器端程序：用真实 API、CLI、任务调度、队列消费或服务重启链路验证设计中的接口、鉴权、数据、配置和后台处理承诺。
- 桌面端程序：用真实窗口、菜单、按钮、托盘、快捷键、安装包、启动项和本地配置验证设计中的交互与本机状态承诺。
- APP 端程序：用真机或等价设备环境验证设计中的页面流、权限弹窗、账号状态、本地存储、前后台切换、离线和网络变化承诺。
- 网页端程序：用浏览器真实点击、输入、刷新、登录态变化和部署入口验证设计中的页面、表单、接口、权限和构建发布承诺。

发布、打包、容器交付是交付测试前置门禁：

- 客户端程序：计划必须写明项目中约定的完整打包流程，并把打包命令、产物生成、安装或启动验证纳入交付测试步骤。打包流程未跑通，交付测试结论必须是“不通过”。
- 服务器端程序：如果项目通过 Docker 容器交付，计划必须写明镜像制作（`docker build`）和镜像运行（`docker run`）步骤。交付测试必须基于新构建的新容器执行；镜像不能构建、容器不能运行、或新容器内业务链路不能跑通，交付测试结论必须是“不通过”。
- Web 程序：计划必须写明项目中约定的完整发布流程，并把发布命令、发布产物、部署入口或发布环境验证纳入交付测试步骤。发布流程未跑通，交付测试结论必须是“不通过”。
- 未找到项目约定的打包、容器或发布流程时，计划必须要求用户提供流程；或者要求用户明确确认本次交付测试不包含对应发布、打包或部署流程。没有用户提供流程或明确豁免，禁止声明交付测试通过。

七点兜底规则用于证明交付测试真的通过：每个功能必须有用例卡（前置条件、操作步骤、预期结果、配置或持久化期望变化）；一律跑真实链路，不使用 monkeypatch、不 mock 保存逻辑；保存相关用例先备份原配置或原状态，测试后恢复；每个用例产出执行前状态快照、执行后状态快照、键级或字段级 diff 和实际结论；不只跑单测，还要做 UI/CLI/API/任务入口等真实触发级测试与落盘/落库核对；通过门槛是全量矩阵，任一项失败整体就是“不通过”；最终只允许输出“逐项通过（附证据）”或“逐项失败（附原因与修复项）”。

每个场景必须包含：

- 业务目标。
- 前置条件。
- 输入数据。
- 操作步骤。
- 期望输出。
- 数据校验。
- 失败处理。
- 对应开发任务。

模板：

```markdown
### DS-01 客户端上传样本数据

**业务目标：**
客户端可以把本地采集的样本数据上传到服务端。

**前置条件：**
服务端已启动，客户端持有有效设备标识和版本号。

**输入数据：**
- 客户端版本：1.0.0
- 样本条数：100
- 样本字段：text、locale、source、timestamp

**操作步骤：**
1. 客户端调用上传接口。
2. 服务端校验请求参数。
3. 服务端保存原始样本。
4. 服务端返回上传批次号。

**期望输出：**
- 接口返回成功。
- 返回 batch_id。
- 原始样本进入 raw_samples 表。

**数据校验：**
- raw_samples 中记录数与上传条数一致。
- batch_id 可用于后续清洗任务。

**失败处理：**
- 参数缺失时返回明确错误。
- 错误数据不能进入正式发布链路。

**对应开发任务：**
Task 03、Task 04、Task 11。
```

### 3.6 自测命令

计划必须提供一条或一组可执行的自测命令，作为交付前门禁。

示例：

````markdown
## 模板章节（4）自测命令

交付前必须执行：

```bash
npm run test:delivery
npm run test
npm run build
```

通过标准：

- 所有业务交付场景通过。
- 所有单元测试通过。
- 所有集成测试通过。
- 编译成功。
````

### 3.7 失败修复与复测机制

计划必须明确失败时怎么处理。

模板：

```markdown
## 模板章节（5）失败修复与复测机制

如果任一自测命令失败：

1. 停止声明完成。
2. 在 fix_bug_work 目录记录失败分析。
3. 定位根因。
4. 修改代码。
5. 重新执行失败的测试。
6. 重新执行完整业务交付测试。
7. 全部通过后才能进入完成说明。
```

失败记录模板：

```markdown
# 问题名称-1

## 失败场景

## 输入数据

## 期望结果

## 实际结果

## 根因分析

## 修复方案

## 复测命令

## 复测结果
```

### 3.8 技术设计与模块边界

这一部分保留开发计划的核心内容。

必须写清楚：

- 模块分层。
- 每个模块职责。
- 模块之间如何调用。
- 数据如何流转。
- 错误如何传播。
- 哪些能力是新增，哪些是复用。

模板：

```markdown
## 模板章节（6）技术设计

### 6.1 模块划分

- API 层：接收客户端上传、版本查询、包下载请求。
- Service 层：处理样本清洗、版本计算、发布状态流转。
- Repository 层：封装数据库读写。
- Storage 层：保存发布包和清单文件。
- Worker 层：执行异步清洗和包生成任务。

### 6.2 数据流

客户端上传 -> 原始样本入库 -> 清洗 -> 统计 -> 候选版本 -> 正式发布 -> 清单生成 -> 客户端下载 -> 客户端应用
```

### 3.9 API、数据模型与配置

计划中不能只说“实现接口”，必须写明接口合约。

至少包含：

- 请求方法。
- 路径。
- 入参。
- 出参。
- 错误码。
- 幂等规则。
- 权限或鉴权要求。
- 数据表或实体结构。
- 环境变量。

示例：

````markdown
### POST /api/sample-batches

用途：客户端上传样本批次。

请求：

```json
{
  "clientVersion": "1.0.0",
  "deviceId": "device-001",
  "samples": []
}
```

响应：

```json
{
  "batchId": "batch_001",
  "status": "accepted"
}
```
````

### 3.10 开发任务拆分

每个开发任务必须能执行，不能只写方向。

每个任务应包含：

- 目标。
- 设计来源（对应方案章节或设计目标编号）。
- 涉及文件。
- 创建文件。
- 修改文件。
- 测试文件。
- 实施步骤。
- 伪代码（最少 5 行有效步骤，且必须体现控制结构或调用链，并体现输入/处理/输出语义）。
- 验证命令。
- 对应业务交付场景。

模板：

````markdown
## Task 03: 实现客户端样本上传接口

**目标：**
客户端可以提交样本批次，服务端完成参数校验并保存原始样本。

**设计来源：**
设计文档《样本上传链路》章节 4.2「上传接口与参数校验」。

**对应交付场景：**
DS-01、DS-02。

**文件：**

- 新增：src/server/api/sampleBatches.ts
- 修改：src/server/routes.ts
- 新增测试：tests/integration/sampleBatches.test.ts

**实施步骤：**

1. 定义上传请求 schema。
2. 注册 POST /api/sample-batches 路由。
3. 校验 clientVersion、deviceId、samples。
4. 调用 repository 保存 raw samples。
5. 返回 batchId。

**伪代码：**

```text
输入：request(clientVersion, deviceId, samples)
if clientVersion/deviceId/samples 缺失:
  return 参数错误
payload = normalize(samples)
batchId = repository.saveRawSamples(payload)
输出：return { batchId, status: "accepted" }
```

**验证：**

```bash
npm run test -- sampleBatches
```
````

### 3.11 测试策略

测试策略必须分层，但最终以业务交付测试为准。

推荐层级：

- 单元测试：验证纯函数、数据转换、边界条件。
- 集成测试：验证数据库、接口、服务组合行为。
- 端到端测试：验证跨模块链路。
- 业务交付测试：模拟真实用户或客户端操作，验证最终可用。

测试策略中可以包含自动化命令，但不能把自动化命令本身等同于交付测试。自动化测试如果没有覆盖真实入口、真实操作路径和完整业务目标，只能作为辅助证据。

写法示例：

```markdown
## 模板章节（8）测试策略

- 单元测试覆盖样本清洗、版本号计算、manifest 生成。
- 集成测试覆盖上传、候选版本生成、正式发布、下载接口。
- 业务交付测试模拟客户端完整链路：上传 -> 发布 -> 拉取 -> 下载 -> 校验 -> 应用。

最终完成门禁是真实业务交付测试通过。

如果提供 npm run test:delivery，它必须完整模拟真实入口和完整业务链路；否则只能作为辅助验证，不能单独作为交付完成依据。
```

### 3.12 需求到验收映射

计划必须提供映射表，证明每个需求都有开发任务和验收方式。

模板：

```markdown
| 需求 | 开发任务 | 验收场景 | 自动化验证 |
|---|---|---|---|
| 客户端上传样本 | Task 03 | DS-01 | tests/delivery/clientUpload.test.ts |
| 生成发布版本 | Task 07 | DS-04 | tests/delivery/releasePackage.test.ts |
| 客户端下载更新包 | Task 09 | DS-06 | tests/delivery/clientDownload.test.ts |
```

### 3.13 最终交付清单

计划最后必须有交付清单。

模板：

```markdown
## 模板章节（12）最终交付清单

- [ ] 代码实现完成。
- [ ] 单元测试通过。
- [ ] 集成测试通过。
- [ ] 业务交付测试通过。
- [ ] 编译通过。
- [ ] 失败记录已处理。
- [ ] 文档已更新。
- [ ] 未执行未经授权的打包。
- [ ] 未执行未经授权的 git push。
```

## 4. 推荐写作顺序

编写计划时按以下顺序推进：

1. 先写业务目标和交付完成定义。
2. 再写业务交付场景。
3. 然后写技术设计和模块边界。
4. 再拆开发任务。
5. 给每个开发任务绑定交付场景。
6. 写自动化测试和自测命令。
7. 写失败修复与复测机制。
8. 最后补需求到验收映射表。

不要先从文件列表开始写。文件列表只能说明会改什么，不能说明业务是否可用。

## 5. 服务端功能示例链路

服务端类计划应优先写完整客户端业务链路。

示例：

```markdown
客户端上传样本
-> 服务端保存原始样本
-> 清洗任务处理样本
-> 统计任务生成样本质量报告
-> 生成候选版本
-> 人工或自动发布正式版本
-> 服务端生成 manifest
-> 客户端查询最新版本
-> 客户端下载增量包
-> 客户端校验 hash 和签名
-> 客户端应用更新包
-> 客户端上报应用结果
```

计划中每一步都要能找到：

- 对应接口。
- 对应数据表。
- 对应服务函数。
- 对应测试。
- 对应验收场景。

## 6. 界面功能示例链路

界面或桌面端功能不能只验收视觉效果。

例如画布、编辑器、输入法、交互工具类功能，计划必须验证真实操作：

- 左键点击是否选中目标。
- 右键是否打开正确菜单。
- 鼠标移动是否更新悬停或坐标状态。
- 拖拽是否改变目标位置。
- 滚轮是否缩放或滚动正确区域。
- 键盘快捷键是否触发正确命令。
- 边界情况下是否不会误触、卡死或丢失状态。

示例场景：

```markdown
### DS-UI-01 鼠标滚轮缩放画布

**业务目标：**
用户可以通过滚轮缩放画布并继续编辑内容。

**操作步骤：**
1. 打开编辑页面。
2. 将鼠标移动到画布区域。
3. 向上滚动滚轮。
4. 向下滚动滚轮。
5. 左键点击画布元素。

**期望输出：**
- 画布缩放比例变化。
- 元素位置不发生异常偏移。
- 缩放后仍能点击选中元素。
```

## 7. 常见错误

### 7.1 只有开发任务，没有交付场景

错误写法：

```markdown
- 实现上传接口
- 实现下载接口
- 实现版本表
```

问题：

这只能说明要写代码，不能证明业务可用。

### 7.2 只有验收场景，没有开发明细

错误写法：

```markdown
- 客户端可以上传
- 客户端可以下载
- 版本可以发布
```

问题：

这不能指导开发人员落地，也不能判断涉及哪些文件、接口和测试。

### 7.3 把单元测试当成交付完成

错误写法：

```markdown
单元测试通过即完成。
```

问题：

单元测试通过不代表客户端完整链路可用。

### 7.4 失败后只修局部，不跑完整交付测试

错误写法：

```markdown
修复失败用例后结束。
```

问题：

局部修复可能破坏其他业务链路。必须重新执行完整业务交付测试。

### 7.5 把内部验证当成交付测试

错误写法：

```markdown
直接调用内部函数，确认返回字段正确。
```

问题：

这只能证明内部链路局部可用，不能证明最终使用者可以直接完成业务。

### 7.6 跳过真实入口

错误写法：

```markdown
环境已经准备好，直接执行核心功能验证。
```

问题：

如果真实业务需要安装、配置、启动、登录、导入或接入外部环境，这些步骤都属于交付范围。跳过真实入口会掩盖交付时最容易卡壳的问题。

### 7.7 使用开发者语言描述用户场景

错误写法：

```markdown
用户调用内部工具并检查状态字段。
```

问题：

交付场景必须接近真实用户会说的话、会点的按钮、会输入的内容、会看到的结果。开发者语言会让测试脱离真实业务。

## 8. 评审清单

提交开发计划前，用以下清单自查：

- [ ] 是否说明了业务目标。
- [ ] 是否保留了完整开发实现内容。
- [ ] 是否补充了业务交付验收内容。
- [ ] 是否有真实用户或客户端操作步骤。
- [ ] 是否从真实入口开始验证，而不是从内部环节开始。
- [ ] 是否使用真实业务语言描述场景，而不是内部实现语言。
- [ ] 是否覆盖安装、配置、启动、使用、结果确认等完整路径。
- [ ] 是否有明确输入数据和期望输出。
- [ ] 是否有接口、数据表、配置和文件清单。
- [ ] 是否每个任务都能执行。
- [ ] 是否每个核心需求都有验收场景。
- [ ] 是否提供了自测命令。
- [ ] 是否区分了辅助测试和最终交付测试。
- [ ] 是否规定失败后的修复与复测流程。
- [ ] 是否明确业务交付测试是最终完成门禁。
- [ ] 是否符合项目约束。

## 10. 结论

开发计划必须能指导开发，也必须能指导验收。

写计划时要始终确认三件事：

1. 开发人员知道怎么做。
2. 测试人员知道怎么验。
3. 业务人员能够判断这个功能是否真的可用。

只有同时满足这三点，这份计划才是完整的可交付开发计划。

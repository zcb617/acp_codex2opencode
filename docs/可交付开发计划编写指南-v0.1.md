# 可交付开发计划编写指南

## 1. 编写目标

开发计划不是单纯的任务拆解，也不是单独的验收清单。

开发计划必须保存为 Markdown 文档文件，默认路径为 `docs/superpowers/plans/<YYYY-MM-DD>-<session_alias>-plan.md`；禁止只在对话中输出一段计划文字。

开发计划必须基于已确认的设计方案展开。若设计方案由主会话生成，计划阶段必须引用对应设计文档路径；若设计方案由用户直接提供，计划阶段必须以用户提供的方案正文为依据，并在计划文档中写明方案来源。

一份完整的开发计划必须同时回答两个问题：

1. 要开发什么，怎么开发，改哪些文件，如何分阶段完成。
2. 开发完成后，业务上如何证明它真的可用。

完整定义：

> 完整开发计划 = 开发实施计划 + 业务交付验收计划 + 失败修复与复测机制

## 2. 核心原则

### 2.1 业务优先

计划必须从业务使用链路出发，而不是从内部模块出发。

### 2.2 开发内容不能缺失

业务导向不等于只写验收场景。计划仍必须包含完整开发信息：模块边界、数据结构、API 合约、文件变更、任务拆分、测试与验证命令。

### 2.3 交付测试是最终完成标准

单元测试、集成测试、编译通过只能证明局部正确。最终完成标准必须是业务交付测试通过。

### 2.4 失败必须闭环

计划必须规定失败记录、修复、复测和重新执行完整业务链路的机制。未闭环不得宣告完成。

## 3. 必须包含的文档结构

本章只描述“计划里必须写什么”。完整可复制模板统一放在第 9 章。

### 3.1 项目与目标

必须包含：

- 功能名称
- 业务目标
- 使用对象
- 当前痛点
- 交付后效果
- 本次不做什么

对应模板章节：第 1 节。

### 3.2 硬约束

必须包含项目执行硬约束，至少覆盖：

- 文档语言要求
- 方案先行与用户确认要求
- 分支策略
- `git push` 授权要求
- 打包/发布授权要求
- 开发后编译与验证要求

对应模板章节：第 2 节。

### 3.3 范围与非范围

必须同时写清“本次交付”和“本次不交付”，并保证每个范围项可映射到开发任务与验收场景。

对应模板章节：第 3 节。

### 3.4 业务交付定义

必须给出交付完成门槛，明确“什么才算可交付”，并强调业务交付测试是最终门禁。

对应模板章节：第 4 节。

### 3.5 业务交付场景

必须用真实业务语言描述真实入口链路，禁止以内部函数、内部字段、工具调用替代用户操作。

每个场景至少包含：

- 业务目标
- 前置条件
- 输入数据
- 操作步骤
- 期望输出
- 数据校验
- 失败处理
- 对应开发任务

对应模板章节：第 5 节。

### 3.6 自测命令

必须提供交付前门禁命令，并给出通过标准。命令应覆盖：

- 精准回归验证
- 相关模块验证
- 全量测试或关键链路验证
- 构建/编译检查

对应模板章节：第 6 节。

### 3.7 失败修复与复测机制

必须明确失败后的闭环动作：记录失败事实、定位根因、修复、复测、重跑完整业务交付测试。

对应模板章节：第 7 节。

### 3.8 技术设计与模块边界

必须写清：

- 模块分层
- 模块职责
- 模块调用关系
- 数据流转
- 错误传播
- 新增与复用边界

对应模板章节：第 8 节。

### 3.9 API、数据模型与配置

必须明确接口/模型/配置契约，至少覆盖：

- 请求方法与路径
- 入参与出参
- 错误码
- 幂等规则
- 权限或鉴权
- 数据表或实体结构
- 环境变量

对应模板章节：第 9 节。

### 3.10 开发任务拆分

每个任务必须可执行，至少包含：

- 任务目标
- 涉及文件（新增/修改/测试）
- 实施步骤
- 验证命令
- 对应业务交付场景

对应模板章节：第 10 节。

### 3.11 测试策略

必须分层描述测试，并明确：自动化测试是辅助证据，最终门禁是真实业务交付测试。

对应模板章节：第 11 节。

### 3.12 需求到验收映射

必须提供映射表，证明每个核心需求都有：开发任务、验收场景、自动化验证。

对应模板章节：第 12 节。

### 3.13 最终交付清单

必须提供最终 checklist，覆盖代码、测试、交付测试、文档、授权边界等。

对应模板章节：第 13 节。

## 4. 推荐写作顺序

建议按下列顺序编写，避免只写实现不写可交付：

1. 先写第 1 节项目与目标、第 4 节交付完成定义。
2. 再写第 3 节范围与非范围、第 5 节业务交付场景。
3. 再写第 8 节技术设计、第 9 节 API/模型/配置。
4. 然后写第 10 节开发任务拆分。
5. 再写第 11 节测试策略、第 6 节自测命令。
6. 再写第 7 节失败修复与复测机制。
7. 最后写第 12 节映射与第 13 节最终交付清单。

## 5. 服务端功能示例链路

服务端类计划应优先写完整客户端业务链路。

示例：

```text
客户端上传样本
-> 服务端保存原始样本
-> 清洗任务处理样本
-> 统计任务生成样本质量报告
-> 生成候选版本
-> 人工或自动发布正式版本
-> 服务端生成 manifest
-> 客户端查询最新版本
-> 客户端下载增量包
-> 客户端校验 hash 和签名
-> 客户端应用更新包
-> 客户端上报应用结果
```

每一步都应在计划中可追踪到：接口、数据表、服务函数、测试和验收场景。

## 6. 界面功能示例链路

界面或桌面端功能不能只验收视觉效果，必须覆盖真实交互操作。

典型操作应覆盖：

- 左键点击
- 右键菜单
- 鼠标移动
- 拖拽
- 滚轮
- 键盘快捷键
- 边界条件下的稳定性

示例场景：

```text
DS-UI-01 鼠标滚轮缩放画布
业务目标：用户可通过滚轮缩放画布并继续编辑。
操作步骤：打开编辑页 -> 鼠标移入画布 -> 向上滚轮 -> 向下滚轮 -> 点击元素。
期望输出：缩放比例变化正确、元素不异常偏移、缩放后仍可选中元素。
```

## 7. 常见错误

### 7.1 只有开发任务，没有交付场景

问题：只能说明要写代码，不能证明业务可用。

### 7.2 只有验收场景，没有开发明细

问题：无法指导落地，也无法判断文件、接口和测试范围。

### 7.3 把单元测试当成交付完成

问题：单元测试通过不代表完整业务链路可用。

### 7.4 失败后只修局部，不跑完整交付测试

问题：局部修复可能破坏其他链路，必须全链路复测。

### 7.5 把内部验证当成交付测试

问题：只能证明局部内部行为，不能证明用户可交付体验。

### 7.6 跳过真实入口

问题：会掩盖安装、配置、启动、登录等最常见交付卡点。

### 7.7 使用开发者语言描述用户场景

问题：场景脱离真实业务，不具备交付验收价值。

## 8. 评审清单

提交开发计划前，用以下清单自查：

- [ ] 是否说明业务目标。
- [ ] 是否保留完整开发实现内容。
- [ ] 是否补充业务交付验收内容。
- [ ] 是否有真实用户或客户端操作步骤。
- [ ] 是否从真实入口开始验证。
- [ ] 是否使用真实业务语言，而非内部实现语言。
- [ ] 是否覆盖安装、配置、启动、使用、结果确认完整路径。
- [ ] 是否有明确输入数据和期望输出。
- [ ] 是否有接口、数据表、配置和文件清单。
- [ ] 是否每个任务都可执行。
- [ ] 是否每个核心需求都有验收场景。
- [ ] 是否提供自测命令。
- [ ] 是否区分辅助测试与最终交付测试。
- [ ] 是否规定失败后的修复与复测流程。
- [ ] 是否明确业务交付测试是最终门禁。
- [ ] 是否符合项目硬约束。

## 10. 结论

可交付开发计划必须同时满足：

1. 开发人员知道怎么做。
2. 测试人员知道怎么验。
3. 业务人员能够判断是否真的可用。

只有同时满足这三点，这份计划才是完整的可交付开发计划。

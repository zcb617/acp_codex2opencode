# 可交付BUG修改设计文档编写指南

## 1. 编写目标

Bug 修改设计文档不是简单记录“哪里坏了”和“准备怎么改”。

一份合格的 Bug 修改设计文档必须回答三个问题：

1. 真实业务中哪里失败了。
2. 为什么会失败，证据是什么。
3. 修复后如何证明同一条业务链路已经恢复可交付。

因此，Bug 修改设计文档的定义是：

> Bug 修改设计文档 = 失败事实记录 + 根因分析 + 修复设计 + 同链路复测目标

Bug 修复不能只看局部函数或报错堆栈。最终完成标准必须是同一条真实业务链路复测通过。

## 2. 核心原则

### 2.1 先复现，再设计

没有复现或证据的 Bug，不允许直接进入修复设计。

文档必须写清：

- 用户如何触发问题。
- 使用了什么真实入口。
- 输入了什么业务语言或执行了什么业务操作。
- 实际看到了什么结果。
- 预期应该是什么结果。
- 问题是否稳定复现。

如果无法稳定复现，也必须写清已掌握的证据、缺失证据和下一步采集方式。

### 2.2 修根因，不修表象

Bug 修改设计必须明确根因分析。

不能只写：

- 调整提示词。
- 加一个判断。
- 捕获异常。
- 延长等待时间。

必须说明：

- 错误数据或错误状态从哪里产生。
- 哪个业务判断失效。
- 哪个状态转换不符合业务目标。
- 为什么现有测试没有覆盖。
- 修复点为什么能阻断同类问题。

### 2.3 业务恢复优先

Bug 修复不是让测试变绿，而是让业务恢复可用。

设计文档必须写清修复后的业务状态：

- 用户是否能继续推进任务。
- 系统是否能给出符合业务语义的提示。
- 失败后是否有接手路径。
- 是否避免旧问题再次出现。
- 是否需要补充业务交付测试。

### 2.4 同链路复测

Bug 修复后必须重新执行触发问题的同一条业务链路。

复测不能只做以下动作：

- 只跑单元测试。
- 只检查字段。
- 只调用内部 API。
- 只证明新函数返回正确。

复测必须尽量还原用户发现问题时的入口、语言、操作路径和业务目标。

## 3. 必须包含的文档结构

### 3.1 问题摘要

用业务语言说明这个 Bug 造成什么影响。

必须包含：

- Bug 名称。
- 影响对象。
- 影响业务链路。
- 当前失败结果。
- 修复完成后应恢复的业务结果。

示例：

```markdown
## 1. 问题摘要

团队委派插件在 ACP 实施完成后直接显示完成，但没有执行真实业务交付测试。
这会导致用户以为任务已经可交付，实际业务链路可能仍未验证。
修复后，实施完成必须进入交付测试；只有交付测试通过后才能显示完成。
```

### 3.2 失败事实

记录已经观察到的失败事实，不做猜测。

必须包含：

- 触发入口。
- 用户输入。
- 实际表现。
- 预期表现。
- 失败时间或场景。
- 是否可复现。
- 截图、日志、输出或文件证据。

模板：

```markdown
## 2. 失败事实

- 触发入口：
- 用户输入：
- 实际表现：
- 预期表现：
- 复现频率：
- 证据：
```

### 3.3 影响范围

说明问题影响哪些业务能力，哪些不受影响。

必须包含：

- 受影响功能。
- 受影响用户动作。
- 受影响状态或数据。
- 不受影响范围。
- 如果不修复会造成什么交付风险。

### 3.4 根因分析

根因分析必须有证据链。

建议按以下结构写：

```markdown
## 4. 根因分析

### 4.1 直接原因

### 4.2 深层原因

### 4.3 为什么现有测试没有发现

### 4.4 证据链
```

根因不明确时，不能伪造结论。必须写成：

- 当前已确认的事实。
- 当前未确认的假设。
- 需要补充的诊断步骤。

### 3.5 修复目标与非目标

修复目标必须可验证。

示例：

```markdown
## 5. 修复目标与非目标

### 5.1 修复目标

- 实施完成后不能直接进入完成状态。
- 必须进入交付测试节点。
- 交付测试失败后必须形成整改方案和整改计划。

### 5.2 非目标

- 不改变模型选择机制。
- 不新增项目专属测试脚本。
```

### 3.6 修复设计

修复设计必须说明改哪里、为什么这样改、失败如何回退。

必须包含：

- 状态机变化。
- 用户可见行为变化。
- 数据结构或接口变化。
- 错误处理变化。
- 兼容性处理。
- 回退方案。

### 3.7 修改范围

列出预计修改的文件和责任。

模板：

```markdown
## 7. 修改范围

- `src/...`：修改状态流转。
- `skills/...`：修改用户可见流程规则。
- `tests/...`：新增失败复现和回归测试。
- `docs/...`：更新业务规则。
```

### 3.8 自动化验证目标

自动化测试必须覆盖根因，而不是只覆盖实现细节。

必须写清：

- 哪个测试先失败。
- 修复后哪个测试通过。
- 哪些旧测试必须保持通过。
- 是否需要新增交付测试辅助脚本。

### 3.9 交付测试目标

这是 Bug 修改设计文档的最终门禁。

必须写清：

- 真实入口。
- 真实业务语言。
- 复现失败的原始业务链路。
- 修复后要重新执行的同一条业务链路。
- 通过标准。
- 如果复测失败，如何继续整改。

模板：

```markdown
## 9. 交付测试目标

真实入口：

用户语言：

原失败链路：

复测链路：

通过标准：

失败后整改闭环：
```

### 3.10 上下文恢复说明

文档末尾必须写清上下文恢复信息，保证上下文压缩后仍能继续。

必须包含：

- 当前 Bug 是什么。
- 已确认的失败事实。
- 当前处于哪个阶段。
- 下一步应该做什么。
- 哪些约束不能破坏。

## 4. 推荐模板

```markdown
# <Bug 名称> 修改设计文档

## 1. 问题摘要

## 2. 失败事实

## 3. 影响范围

## 4. 根因分析

### 4.1 直接原因

### 4.2 深层原因

### 4.3 现有测试缺口

### 4.4 证据链

## 5. 修复目标与非目标

### 5.1 修复目标

### 5.2 非目标

## 6. 修复设计

## 7. 修改范围

## 8. 自动化验证目标

## 9. 交付测试目标

## 10. 风险与回退

## 11. 上下文恢复说明
```

## 5. 禁止写法

以下写法不合格：

- “修一下异常处理。”
- “加个判断即可。”
- “跑测试通过就行。”
- “问题应该是某某原因。”
- “看起来已经好了。”
- “用户再试一下。”

必须替换为：

- 明确失败事实。
- 明确根因证据。
- 明确修复设计。
- 明确同链路复测。
- 明确交付测试通过标准。

## 6. 完成标准

只有同时满足以下条件，Bug 修改设计文档才算完成：

- 失败事实清楚。
- 根因分析有证据。
- 修复目标可验证。
- 修改范围明确。
- 自动化验证目标明确。
- 交付测试目标明确。
- 失败后继续整改的闭环明确。
- 上下文恢复说明完整。

没有满足这些条件，不允许进入编码实施。

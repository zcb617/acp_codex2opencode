# 可交付BUG修改计划编写指南

## 1. 编写目标

Bug 修改计划不是重新写一份设计文档，也不是简单列出“改哪些文件”。

Bug 修改计划的目标是把已经确认的 Bug 修改设计，转成可执行、可验证、可交付的实施路线。

因此，Bug 修改计划的定义是：

> Bug 修改计划 = 设计承诺落实表 + 实施任务拆分 + 自动化验证计划 + 真实业务交付测试计划 + 失败整改闭环

Bug 修改设计文档回答“为什么失败、要怎么修、如何证明恢复”；Bug 修改计划回答“按什么顺序做、每一步产出什么、怎样证明设计内容全部做完、交付测试失败后如何继续整改”。

计划不能降低设计要求。设计文档中写过的修复目标、非目标、修改范围、自动化验证目标和交付测试目标，必须在计划中全部落到任务、检查项和复测动作。

## 2. 与 BUG 设计指南的关系

Bug 修改计划必须以 `docs/可交付BUG修改设计文档编写指南-v0.1.md` 产出的设计文档为输入。

两份文档的关系如下：

| 文档 | 解决的问题 | 不能缺失的内容 |
|---|---|---|
| Bug 修改设计文档 | 为什么失败、为什么这样修、修复后如何证明业务恢复 | 失败事实、根因分析、修复设计、同链路复测目标 |
| Bug 修改计划文档 | 如何把设计完整实施并验证到可交付 | 任务拆分、设计覆盖表、验证顺序、真实业务交付测试、失败整改闭环 |

计划文档不能绕过设计文档。没有设计文档，不能直接写计划并进入实施。

计划文档也不能只引用设计文档后不展开。计划必须明确说明设计中的每个目标如何被实施、如何被测试、如何被交付验证。

## 3. 核心原则

### 3.1 设计内容必须全部做完

Bug 修改计划的第一责任是防止“只修了其中一个现象，却遗漏设计里的其他承诺”。

计划中必须建立设计覆盖关系：

- 每个修复目标对应至少一个实施任务。
- 每个修改范围对应明确文件或模块。
- 每个自动化验证目标对应明确测试命令或测试用例。
- 每个交付测试目标对应真实业务复测步骤。
- 每个风险或回退点对应检查方式或处置方式。

如果某个设计目标暂时不能实施，必须在计划中明确原因、影响、替代方案和是否需要用户重新确认。

### 3.2 交付测试是计划的重点

Bug 修改计划的重点不是“代码怎么改”，而是“修复后如何证明业务已经恢复”。

自动化测试是必要辅助，但不能替代交付测试。

交付测试必须从真实入口开始，使用真实业务语言，执行同一条失败链路或等价业务链路，确认用户最终能继续推进任务。

计划必须写清：

- 真实入口是什么。
- 用户真实会怎么表达。
- 原失败链路是什么。
- 修复后怎样按同链路复测。
- 用户应该看到什么业务结果。
- 如果复测失败，如何记录、整改、再复测。

### 3.3 失败后必须继续闭环

Bug 修复中出现新的失败，不代表计划结束，也不能把失败解释成“测试环境问题”后跳过。

如果交付测试失败，计划必须要求：

1. 记录新的失败事实。
2. 判断它是否属于当前 Bug 的交付闭环。
3. 更新设计文档或计划文档。
4. 补充红灯测试或交付契约测试。
5. 实施整改。
6. 重新执行自动化验证。
7. 重新执行真实业务交付测试。

直到真实业务链路通过，或者用户明确选择取消后续工作。

### 3.4 业务语言优先

计划中的用户可见步骤必须使用业务语言。

不能写成：

- 调用某个 MCP 工具。
- 检查某个内部字段。
- 执行某个内部 action。
- 查看某个枚举状态是否正确。

必须写成：

- 用户从真实入口继续任务。
- 用户选择继续等待。
- 系统提示当前无法继续等待，需要主会话接手。
- 用户确认主会话接手后，流程停止依赖原执行端。

内部字段可以作为辅助证据，但不能成为交付测试主步骤。

## 4. 必须包含的文档结构

### 4.1 Bug 与设计来源

说明本计划承接哪份 Bug 修改设计文档。

必须包含：

- Bug 名称。
- 设计文档路径。
- 设计文档版本或日期。
- 当前失败链路摘要。
- 本计划要完成的修复边界。

模板：

```markdown
## 1. Bug 与设计来源

- Bug 名称：
- 设计文档：
- 当前失败链路：
- 本计划目标：
- 本计划不处理：
```

### 4.2 设计目标覆盖表

这是 Bug 修改计划的核心。

必须把设计文档中的修复目标逐条映射到实施任务和验证方式。

模板：

```markdown
## 2. 设计目标覆盖表

| 设计目标 | 实施任务 | 自动化验证 | 交付测试验证 | 状态 |
|---|---|---|---|---|
| 恢复后不返回流程丢失 | Task 01 | UT-01 | DT-01 | 待实施 |
| 恢复后给出接手路径 | Task 02 | UT-02 | DT-02 | 待实施 |
```

状态建议使用：

- 待实施。
- 已实施待验证。
- 自动化已验证。
- 交付测试已验证。
- 失败需整改。

### 4.3 实施任务拆分

实施任务必须从设计目标反推，不能从“我想改哪个文件”开始。

每个任务必须包含：

- 业务目标。
- 设计来源。
- 修改范围。
- 实施步骤。
- 验证方式。
- 完成标准。

模板：

```markdown
### Task 01: 任务名称

**业务目标：**

**对应设计目标：**

**修改范围：**

**实施步骤：**

1. 
2. 
3. 

**自动化验证：**

**交付测试影响：**

**完成标准：**
```

### 4.4 TDD 与红灯测试计划

Bug 修改必须先证明测试能抓住问题。

计划必须写清：

- 哪个失败现象要先写成红灯测试。
- 预期失败信息是什么。
- 失败是否对应真实 Bug，而不是测试写错。
- 修复后该测试如何变绿。

模板：

```markdown
## 4. TDD 与红灯测试计划

| 测试编号 | 覆盖失败 | 红灯表现 | 修复后绿灯标准 |
|---|---|---|---|
| UT-01 | 进程恢复后流程丢失 | 返回 WORKFLOW_NOT_FOUND | 返回业务恢复状态 |
```

如果某些真实业务问题无法完全自动化，也必须补充最接近根因的自动化测试，并说明真实交付测试如何补足。

### 4.5 自动化验证计划

自动化验证计划必须分层。

至少包含：

- 精准回归测试：只跑本次新增或修改的测试。
- 相关模块测试：覆盖受影响模块。
- 全量测试：确认没有破坏旧能力。
- 编译或构建：确认交付物可生成。
- 插件或安装检查：如果真实业务涉及安装，必须包含。

模板：

```markdown
## 5. 自动化验证计划

1. 红灯测试：

```bash
npm run test:unit -- tests/unit/xxx.test.ts -t "xxx"
```

2. 相关模块测试：

```bash
npm run test:unit
```

3. 全量验证：

```bash
npm test
npm run build
npm run prepare:plugin
```
```

计划必须说明每条命令通过后证明什么，不能只列命令。

### 4.6 真实业务交付测试计划

这是 Bug 修改计划最重要的部分。

必须写得足够具体，保证执行人不需要再猜“怎么测才算交付测试”。

必须包含：

- 真实环境。
- 真实入口。
- 用户业务语言。
- 前置准备。
- 操作步骤。
- 期望用户可见结果。
- 辅助证据。
- 失败判定。
- 失败后整改动作。

模板：

```markdown
## 6. 真实业务交付测试计划

### DT-01 同链路复测场景名称

**业务目标：**

**真实环境：**

**真实入口：**

**用户语言：**

```text
用户真实会输入的话
```

**操作步骤：**

1. 
2. 
3. 

**期望用户可见结果：**

**辅助证据：**

**通过标准：**

**失败判定：**

**失败后整改：**
```

辅助证据可以包括数据库、日志、文件、截图、审计记录，但这些不能替代用户可见结果。

### 4.7 失败整改与再计划机制

计划必须预设失败后的处理方式。

如果交付测试失败，应按以下流程更新计划：

1. 在计划文档中追加“第 N 轮交付测试失败”。
2. 写清失败事实：用户输入、实际表现、预期表现、证据。
3. 判断根因是否已在原设计范围内。
4. 如果在原设计范围内，补充实施任务和测试。
5. 如果超出原设计范围，更新设计文档并让用户确认。
6. 整改后重新执行自动化验证。
7. 整改后重新执行真实业务交付测试。

模板：

```markdown
## 7. 交付测试失败整改记录

### Round 1

**失败场景：**

**用户输入：**

**实际表现：**

**预期表现：**

**证据：**

**根因判断：**

**新增任务：**

**新增验证：**

**复测结果：**
```

### 4.8 设计完成核对清单

计划结束前必须核对设计内容是否全部完成。

模板：

```markdown
## 8. 设计完成核对清单

- [ ] 设计中的失败事实已被测试覆盖或交付测试覆盖。
- [ ] 设计中的每个修复目标已完成。
- [ ] 设计中的非目标没有被越界实施。
- [ ] 设计中的修改范围已完成或明确取消原因。
- [ ] 设计中的自动化验证目标已执行。
- [ ] 设计中的交付测试目标已执行。
- [ ] 交付测试失败后的整改记录已闭环。
- [ ] 最终用户可见结果符合业务目标。
```

### 4.9 上下文恢复说明

计划末尾必须写清当前推进状态，保证上下文压缩后能继续。

必须包含：

- 当前 Bug 是什么。
- 当前设计文档在哪里。
- 当前计划执行到哪一步。
- 已完成哪些任务。
- 哪些测试已通过。
- 最近一次交付测试结果。
- 下一步必须做什么。
- 哪些约束不能破坏。

## 5. 从本次 BUG 修改抽象出的标准流程

本次“Codex CLI 恢复后委派流程丢失”Bug 修改暴露出一个完整的可交付 Bug 修复流程。

可抽象为以下 SOP：

1. **记录真实失败。**
   从真实业务入口复现问题，记录用户输入、实际表现、预期表现和证据。

2. **形成 Bug 修改设计。**
   写清失败事实、根因、修复目标、非目标、修改范围、自动化验证目标和交付测试目标。

3. **形成 Bug 修改计划。**
   把设计目标拆成实施任务，并明确每个任务如何验证，尤其是如何做真实业务交付测试。

4. **先写红灯测试。**
   对核心根因写失败测试，确认当前代码确实会失败。

5. **实施最小修复。**
   只围绕设计目标修复，不顺手做无关重构。

6. **自动化验证。**
   先跑精准测试，再跑相关测试、全量测试、构建和安装检查。

7. **真实业务交付测试。**
   使用真实入口和真实业务语言复测同一失败链路。

8. **交付测试失败时继续整改。**
   失败不能结束任务。必须记录新失败事实，判断是否属于当前设计范围，补充任务和测试后再复测。

9. **最终收口。**
   只有真实业务链路达到通过标准，才可以声明交付测试通过。

这套流程的重点不是“第一次修复就成功”，而是即使真实交付测试连续暴露新问题，也能持续形成整改、实施、复测，直到业务闭环。

## 7. 常见错误

### 7.1 计划没有覆盖设计目标

错误写法：

```markdown
Task 01：修改状态判断。
Task 02：补测试。
```

问题：

看不出设计里的每个修复目标是否都被完成。

正确做法：

用设计目标覆盖表逐条映射。

### 7.2 把自动化测试当成交付测试

错误写法：

```markdown
npm test 通过后 Bug 修复完成。
```

问题：

自动化测试不能证明真实用户入口已经恢复。

正确做法：

自动化测试通过后，还必须执行真实业务交付测试。

### 7.3 交付测试失败后停止

错误写法：

```markdown
交付测试失败，记录为已知问题。
```

问题：

Bug 修改没有闭环，不能交付。

正确做法：

补充失败记录、整改任务、验证方式，并重新复测同一链路。

### 7.4 用内部语言写业务复测

错误写法：

```markdown
调用 delegate_task_execute，检查 workflow_status。
```

问题：

真实用户不会这样使用产品。

正确做法：

写真实入口和真实用户语言，内部状态只作为辅助证据。

### 7.5 只验证原 Bug，不验证修复带来的新路径

错误写法：

```markdown
确认不再报原错误即可。
```

问题：

原错误消失后，用户仍可能卡在新的业务节点。

正确做法：

继续验证用户是否能理解当前状态并推进下一步。

## 8. 完成标准

只有同时满足以下条件，Bug 修改计划才算完成：

- 已绑定一份合格的 Bug 修改设计文档。
- 设计目标覆盖表完整。
- 每个设计目标都有实施任务。
- 每个实施任务都有验证方式。
- 红灯测试计划能覆盖核心失败。
- 自动化验证计划能证明局部修复和回归安全。
- 真实业务交付测试计划从真实入口开始。
- 交付测试使用真实业务语言。
- 交付测试失败后的整改机制明确。
- 设计完成核对清单可以逐项验收。
- 上下文恢复说明足以让后续会话继续执行。

不满足这些条件，不允许声明 Bug 修改计划完成。
